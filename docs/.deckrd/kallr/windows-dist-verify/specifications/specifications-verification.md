## 1. 概要

### 1.1 目的

Windows で OS の予約通知を、未パッケージ + HKCU 登録の配布形式で利用できるかを確認する。
この仕様書は、その検証のうち **手動検証の手順と結果の記録に関する規則** を定める。
対象は次の 6 項目。

- kill 後の通知表示 (W2)
- 置換の方式と失敗状態の記録 (W4 の d と e)
- 再起動またはログオフ→ログイン後の記録 (W7)
- 任意の測定の記録と、結果の追記
- 全体の合否
- PoC コードの置き場所

### 1.2 範囲

この仕様書は、Windows Distribution Verify (verification) の **振る舞いの規則** と **分類の意味** を定める。
実装の詳細は対象外とする。

本ファイルが扱う FR は REQ-F-003 / 008 / 009 / 012 / 013 / 014 / 015 / 018 の 8 件。
ほかの FR は Section 6 に示すファイルが扱う。
用語は universal-dictionary.md (UD-RSV-001 から UD-REC-003) に従う。

## 2. 設計方針

### 2.1 分類方針

- 合否は、観測できる値 (予約一覧、通知履歴、終了コード) で判定する。
- 値の良し悪しを問わず記録するだけの項目と、合否に使う項目を分ける。
- 手動検証では、実機で観測した事実だけを記録する。観測していない値は「記載なし」と書き、推測で埋めない。
- 記録は追記のみとする。過去の PoC の結果を書き換えない。
- 全体の合否は、個々の確認項目の結果から機械的に決まるゲートとする。検証担当者の印象で上書きしない。

### 2.2 設計上の前提

- 検証担当者が実機 (Windows 11 の実環境) で手順を実施する。自動化できるのは、予約一覧の取得などの観測だけとする。
- 予約一覧は OS が持つ予約の一覧 (UD の予約一覧) であり、通知履歴とは別のものとする。
- 通知履歴を未パッケージのアプリで取得できるかは未確認とする (Section 7)。
- 通知の無効設定、集中モード、ロック状態では、通知を表示できない場合がある。この限界は結果に記録する。
- W1、W3、W4 の a から c は、手順と合格条件を `specifications-schedule.md` と `specifications-tag.md` が定める。本ファイルは、それらの結果を全体の合否の判定に使う立場である。

### 2.3 外部設計の概要

> **根拠**: 外部設計の対話 (Phase E) と、利用者が確認した設計方針 (Phase D) に基づく。

### 2.4 対象外

> **根拠**: 以下はすべて REQUIREMENTS の「Out of Scope」に基づく。

- 任意の測定の合否を判定しない ← REQ: Out of Scope (任意の測定の合否判定)
- `apps/` と `packages/` へ PoC コードを配置しない ← REQ: Out of Scope
- MSIX + Dart と AOT exe を検証しない (未確認事項として Section 7 に残す) ← REQ: Out of Scope
- Windows 以外の OS を対象にしない ← REQ: Out of Scope

### 2.7 DD を DR に昇格する基準

> **目的**: DD を正式な DR に昇格するかどうかを判断するための指針。昇格は人が判断し、自動では行わない。

**昇格を検討する場合:**

1. 複数の仕様またはモジュールに影響する
2. 将来の設計の選択肢を縛る
3. 実際に複数の選択肢があった
4. 外部の関係者によるレビューが必要

**DD のまま残す場合:**

- この仕様の中だけで完結する
- 大きな代替案がなかった
- 根拠が文脈から明らかである

> **Action**: 昇格するときは `/deckrd dr --add` を実行し、DD の Status を `Promoted → DR-xx` に更新する。

## 3. 振る舞いの仕様

### 3.1 入力

- 入力の種類: 検証担当者が実機で観測した値と、その観測の条件 (kill や停止をした段階、再起動かログオフかの別)
  - 観測する値: 予約一覧、通知履歴、検証担当者の目視、add や一括再登録の終了コード
- 前提:
  - 予約は、対応表と予約一覧の両方に記録される前提で作成される (`specifications-schedule.md`)。
  - 観測の前に、通知できる状態 (AUMID の登録、DisplayName、通知設定) が整っている。
  - 観測できない値は、入力に含めない。

### 3.2 出力と終了コード

- 出力の意味: 各確認項目の記録 (観測した値、観測条件、判定の根拠) と、全体の合否。
- 取りうる結果:
  - W2: 合格 / 合格にしない。合格のときは、判定の根拠が「通知履歴」か「予約一覧 + 目視」かを併記する。
  - W4 (d) 置換の方式と AddToSchedule 単独の挙動: 観測した結果の記録 (合否に使わない)。
  - W4 (e) 失敗状態: 4 つの状態のうち観測した 1 つと、停止させた段階 (合否に使わない)。
  - W7: 再起動またはログオフの後の予約の有無と、一括再登録による復旧の可否。合否はなく、記録の有無だけをゲートに使う。
  - 任意の測定: 測定結果の記録 (合否なし)。
  - 全体の合否: 合格 / 合格にしない。W4 の判定に使うのは (a)、(b)、(c) だけ。
  - 配置: PoC コードが poc/ 配下にのみある状態。

## 4. 判定規則

Evaluation MUST follow this order:

| Rule ID   | Step | Condition                                                                                            | Outcome                                                                                                                                                                                                                                                                                  |
| --------- | ---: | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| VER-R-001 |    1 | W2: add が予約を作成し、そのプロセスを kill した後に --at の時刻に到達した。かつ通知履歴を取得できる | 次の両方を満たせば W2 を合格とする。(1) 予約一覧から該当の予約が消えた。(2) 通知履歴に該当の通知が存在する。どちらかが欠ければ合格にしない                                                                                                                                               |
| VER-R-002 |    2 | W2: VER-R-001 の前提のうち、通知履歴を取得できない                                                   | 次の両方を満たす場合に限り W2 を合格とする。(1) 予約一覧から該当の予約が消えた。(2) 検証担当者が通知の表示を目視で確認した                                                                                                                                                               |
| VER-R-003 |    3 | W2: VER-R-001 または VER-R-002 で合格とした                                                          | 判定の根拠 (通知履歴 / 予約一覧 + 目視) を記録する。目視の場合は、「通知の内容・AUMID・Tag の対応を機械的に検証できない」限界も記録する                                                                                                                                                  |
| VER-R-004 |    4 | W4 (d): W4 (a) の置換を実施した                                                                      | 採用した置換の方式 (置換後の予約を追加してから置換前の予約を削除) とその結果を記録する。参考として、同じ Tag と Group での AddToSchedule 単独の挙動 (置換されるか、重複するか) も記録する。どちらも W4 の合否を決めない (VER-DD-06)                                                      |
| VER-R-005 |    5 | W4 (e): 置換の途中でプロセスを停止させ、停止後の予約一覧を確認した                                   | 次の 4 つのうち観測された 1 つを、停止させた段階 (schedule 3.5 の段階 1〜4) とともに記録する。「置換前の予約だけが残る」「置換後の予約だけが残る」「両方が残る」「どちらも残らない」。段階を特定できない場合は、段階の欄を「記載なし」とする。この記録は W4 の合否を決めない (VER-DD-06) |
| VER-R-006 |    6 | W7: 予約が存在する状態で、再起動、またはログオフ→ログインを実施した                                  | 次の 3 点を記録する。実施した操作 (再起動か、ログオフ→ログインか。片方だけでも W7 の記録になる)、その後の予約の有無、一括再登録で復旧できたかどうか                                                                                                                                      |
| VER-R-007 |    7 | 任意の測定 (過去時刻、予約一覧、配信猶予) を実施した                                                 | 測定結果を記録のみとして残す。W1 から W4 の合否には含めない                                                                                                                                                                                                                              |
| VER-R-008 |    8 | W1 から W5 および W7 の確認が完了し、結果をまとめる                                                  | 結果を poc-results-windows.md に追記する。既存の記述は書き換えない                                                                                                                                                                                                                       |
| VER-R-009 |    9 | 全体の合否を判定する                                                                                 | 次の 3 つをすべて満たす場合に限り合格とする。(1) W1 から W4 がすべて成功 (W4 は (a)、(b)、(c) だけで判定)。(2) W5 の 3 項目がすべて明確。(3) W7 の結果が記録されている (再起動、ログオフ→ログインのどちらか 1 つ以上)。1 つでも欠ければ合格にしない                                      |
| VER-R-010 |   10 | 本検証の成果物 (PoC コード) を作成する                                                               | PoC コードを poc/ 配下にのみ置く。apps/ と packages/ には置かない                                                                                                                                                                                                                        |

規則の順序は変更しない。

VER-R-009 の判定対象の補足:

- 「W1 から W4 の成功」は、W1、W2、W3 の合格条件と、W4 の a から c の合格条件を指す。
- W4 の (d) 置換の方式の記録 (REQ-F-008) と (e) 失敗状態の記録 (REQ-F-009) は、記録するだけで合否を決めない。記録の内容や有無は合否を左右しない (VER-DD-06)。
- W7 は、再起動、またはログオフ→ログインの後の結果が、実施した操作とともに 1 つ以上記録されていることだけを条件にする。両方の実施は求めない。予約が残っていたか、復旧できたかは問わない。
- W5 の 3 項目の明確化は `specifications-environment.md` が定める。「記載なし」の欄が 1 つでも残る場合、W5 は明確化されたとみなさない。
- 「記載なし」の検査のうち W5 の 3 欄は、w5-check が機械的に行い、未明確の欄を報告する (ENV-R-019)。W4 (e) の段階欄と W7 の記録は、合否に使わないか、操作の記録だけが条件のため、検査しない。
