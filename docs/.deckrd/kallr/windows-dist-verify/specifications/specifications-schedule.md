## 1. 概要

### 1.1 目的

予約の追加 (add)、取り消し (cancel)、置換、一覧 (list)、一括再登録 (re-register-all) の振る舞いを定める。
あわせて、各操作が使用する対応表の保存内容と、CLI が返す終了コードを定める。
対象の要求は REQ-F-001、REQ-F-004、REQ-F-005、REQ-F-006、REQ-F-020 の 5 件。

### 1.2 範囲

本書は、Windows Distribution Verify の振る舞いの規則と分類の意味を定める。実装の詳細は対象外とする。

扱う範囲は次のとおり。

- add / cancel / list / re-register-all の振る舞いと終了コード
- 置換 (追加してから削除) の手順と、置換の失敗状態
- 対応表の保存内容 (SQLite) と、その不変条件

Tag の書式と生成、通知可否の確認、検証の手順と記録は別の仕様書が扱う (6 章を参照)。
用語は `universal-dictionary.md` (UD-RSV-001〜UD-REC-003) に従う。

## 2. 設計方針

### 2.1 分類方針

add は、対応表と予約一覧を突き合わせて、「新規」か「置換」かを分類する。
分類の根拠は、対応表の項目の有無と、その Tag が予約一覧にあるかどうかの 2 点だけにする。

対応表と予約一覧は別々の保存先で、途中で停止すると食い違うことがある。
そのため、各操作は次の方針で段階の順序を決める。

- 予約を失うより、予約が重複するほうを許容する (追加を先、削除を後にする。DR-05)
- 取り消しでは、予約の削除を先、対応表の削除を後にする。停止しても、発火する予約が対応表から外れた状態を作らない
- 失敗したら後続の段階を実行しない。自動の巻き戻しはしない
- 不正な入力と破損した保存内容には、代替値を使わず、エラーで終了する

### 2.2 設計上の前提

- 同時に動く CLI のプロセスは 1 つだけとする。同時実行は対象外とし、SQLite のトランザクションは保存内容を壊さないためにだけ使う
- OS 固有の部分 (OS の予約、通知可否の確認、対応表の保存) はインターフェースの背後に置き、Mock に差し替えられる。本書の規則は、Mock に差し替えても同じに成り立つ
- Group は `kallr` の固定値とする (DR-04)。Tag の書式は `specifications-tag.md` に従う
- 予約一覧は、Group が `kallr` の予約だけを対象にする
- 他のアプリの予約は、予約一覧に現れない (AUMID 単位で分かれる)

### 2.3 外部設計の概要

> **根拠**: 外部設計の対話 (Phase E) と、利用者が確認した設計方針 (Phase D) に基づく。

各部品の責務は次のとおり。

#### 機能の分割

| Unit               | Responsibility                                                        | REQ Coverage                        |
| ------------------ | --------------------------------------------------------------------- | ----------------------------------- |
| コマンド入口 (CLI) | 引数の検査、操作の呼び出し、例外の終了コードへの一括変換              | REQ-F-001, REQ-F-004                |
| 予約の管理         | add (新規・置換) / cancel / list / re-register-all の手順と順序の管理 | REQ-F-001, 004, 005, 006            |

#### 構成要素の関係

```text
+---------+     +----------------+     +-----------------+
|  CLI    | --> | 予約の管理     | --> | 通知可否の確認  |  (add の最初。失敗なら全体を止める)
+---------+     +----------------+     +-----------------+
                  |    |    |
                  |    |    +--------> +-----------------+
                  |    |               | Tag の生成      |
                  |    v               +-----------------+
                  |  +----------+
                  |  | 対応表   |  <-- 検索・更新・削除・全件取得
                  |  +----------+
                  v
              +----------------+
              | OS の予約      |  <-- 追加・削除・一覧 (Group=kallr)
              +----------------+
```

各操作の段階の順序は次のとおり。

- add: 通知可否の確認 → 対応表の検索と予約一覧の取得 → Tag の生成と重複確認 → 予約の追加 → 対応表の更新 → 置換前の予約の削除 (置換のみ)
- cancel: 対応表の検索 → 予約の削除 → 対応表の削除

#### データの流れ

```text
[add の引数] --> [引数の検査] --> [通知可否の確認] --> [新規 / 置換の分類]
                     |                  |                     |
                     v                  v                     v
                [終了コード 1]     [終了コード 3]    [Tag 生成と重複確認]
                                                              |
                                                              v
                                          [予約の追加] --> [対応表の更新] --> [置換前の予約の削除 (置換のみ)]
                                                |                 |                     |
                                                v                 v                     v
                                          [失敗: コード 2]  [失敗: コード 2]      [失敗: コード 2 / 成功: コード 0]
```

### 2.7 DD を DR に昇格する基準

> **目的**: DD を正式な DR に昇格するかどうかを判断する指針。昇格は人が判断し、自動では行わない。

**昇格を検討する場合:**

1. 複数の仕様またはモジュールに影響する
2. 将来の設計の選択肢を縛る
3. 実際に複数の選択肢があった
4. 外部の関係者によるレビューが必要

**DD のまま残す場合:**

- この仕様の中だけで完結する
- 大きな代替案がなかった
- 根拠が文脈から明らかである

> **Action**: 昇格するときは `/deckrd dr --add` を実行し、DD の Status を `Promoted → DR-xx` に更新する。

## 3. 振る舞いの仕様

### 3.1 入力

- 入力の種類: CLI のコマンドとオプション

| コマンド        | 必須のオプション                         | 任意のオプション |
| --------------- | ---------------------------------------- | ---------------- |
| add             | --batch, --alarm, --at, --title, --aumid | --db             |
| cancel          | --batch, --alarm, --aumid                | --db             |
| list            | --aumid                                  | --db             |
| re-register-all | --aumid                                  | --db             |

- 前提:
  - `--batch` と `--alarm` は UTF-8 の空でない文字列。既定値は無い (SCH-DD-03)
  - `--at` はオフセット付きの日時、またはオフセットの無い日時。後者はマシンのローカル時刻として扱う (SCH-DD-04)
  - `--title` は UTF-8 の文字列 (REQ-NF-004)
  - `--aumid` は空でない文字列で、既定値は無い (SCH-DD-11)。add と re-register-all では通知可否の確認に渡す。cancel と list では OS の予約の操作の対象を決める
  - `--db <path>` は対応表の保存先を差し替える。省略時は既定の保存先を使う (SCH-DD-12)
  - show / register-reg / unregister-reg / w5-check は本書の対象外 (`specifications-environment.md`)。これらも `--aumid` は必須で、既定値は無い

### 3.2 出力と終了コード

- 出力の意味: 終了コードは操作結果の種類を表す。標準出力と標準エラーには、結果の確認に必要な値と理由を出す。
- 取りうる結果:

| 終了コード | 意味                                                                                                                                                                              |
| ---------: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
|          0 | 成功                                                                                                                                                                              |
|          1 | 使い方の誤り (必須オプションの欠落、空の識別子、解釈できない `--at`)                                                                                                              |
|          2 | 失敗 (OS の予約の失敗、保存先の失敗、Tag の重複の再生成の上限超過、見つからない、一括再登録での個別の失敗、w5-check の記録の不一致または未明確。w5-check は environment が定める) |
|          3 | 通知できない状態 (AUMID が未登録、DisplayName が空、通知設定が無効)                                                                                                               |

終了コード 3 は、通知可否の確認が不可のときに返す。本書では add と re-register-all が返す。
cancel と list は通知可否の確認をしないため、終了コード 3 を返さない。
cancel で対応表に無いキー (見つからない) は終了コード 2 とする (SCH-DD-06)。

  NotFoundException / DuplicateTagException / ScheduleException(OS のエラー値) / RegistryException(win32 code) -> 2。

### 3.3 対応表の保存内容

対応表は SQLite に保存する。1 件の予約につき 1 行を持つ。

| 項目         | 意味                                        | 制約                                                           |
| ------------ | ------------------------------------------- | -------------------------------------------------------------- |
| batchId      | 予約のまとまりの識別子 (`--batch` の値)     | 空でない。(batchId, alarmId) の組でキーになる                  |
| alarmId      | まとまりの中の予約の識別子 (`--alarm` の値) | 空でない。同上                                                 |
| tag          | 予約に付けた Tag (40 文字)                  | 空でない。対応表の全体で一意                                   |
| at           | 通知時刻                                    | 絶対時刻として保存し、再登録で同じ時刻を復元できる             |
| title        | 通知に表示する文字列                        | UTF-8 の文字列をそのまま保存する                               |
| registeredAt | 登録時刻 (ローカル日時)                     | tag の日時部分の元。置換では新しい値になる。再登録では変えない |

- マシン ID も同じ保存先に 1 つだけ持つ。仕様は `specifications-tag.md` に従う
- 保存先は、既定ではユーザーごとのアプリケーションデータ領域の 1 ファイルとし、`--db <path>` で差し替えられる (SCH-DD-12, SCH-R-029)。既定のファイルの具体的な場所と名前は実装で決める (7 章 #3)
- 初回の利用で保存先が無いときは、空の対応表として作る。存在するのに読めない、または壊れているときは作り直さずエラーにする (SCH-R-027)

<!-- impl-note:

| re-register-all | 最初にする (SCH-R-034) | なし                                 | 欠けている予約の追加         |

### 3.5 置換の失敗状態

置換の手順は 3 つの段階からなる。

1. 置換後の予約を、新しい Tag で OS に追加する
2. 対応表を、置換後の Tag・通知時刻・title・登録時刻に更新する
3. 置換前の予約を OS から削除する

各段階で停止または失敗したときの状態を次に示す。状態の名称は UD-RPL-004 に従う。

| 停止・失敗した段階       | OS の予約一覧    | 対応表の指す Tag | 置換の失敗状態         | 備考                                 |
| ------------------------ | ---------------- | ---------------- | ---------------------- | ------------------------------------ |
| 段階 1 の前              | 置換前の予約だけ | 置換前           | 置換前の予約だけが残る | 何も変わらない                       |
| 段階 1 の失敗            | 置換前の予約だけ | 置換前           | 置換前の予約だけが残る | OS が追加を拒否した。終了コード 2    |
| 段階 1 の後・段階 2 の前 | 両方             | 置換前           | 両方が残る             | 置換後の予約は対応表に無い。発火する |
| 段階 2 の失敗            | 両方             | 置換前           | 両方が残る             | 同上。終了コード 2                   |
| 段階 2 の後・段階 3 の前 | 両方             | 置換後           | 両方が残る             | 置換前の予約は対応表に無い。発火する |
| 段階 3 の失敗            | 両方             | 置換後           | 両方が残る             | 同上。終了コード 2                   |
| 段階 3 の完了            | 置換後の予約だけ | 置換後           | (失敗状態ではない)     | 終了コード 0                         |

- 「置換後の予約だけが残る」は、段階 3 の完了後 (成功) と、段階 3 の前に置換前の予約が発火した場合に現れる
- 「どちらも残らない」は、この手順からは到達しない想定とする。実機での観測は未確認 (`specifications-verification.md` の W4 (e))
- 段階 3 で OS が「対象が無い」(発火済み) を返した場合は成功として扱う (SCH-R-030)。このとき置換前の予約はすでに消えており、結果は「置換後の予約だけが残る」になる
