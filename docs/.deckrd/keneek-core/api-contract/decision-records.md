## DR-01: 共通エラー形式に RFC 9457 を採用し、`type` と `code` を 1 対 1 で対応させる - 2026-11-14 06:41:00

**Phase**: review-harden
**Status**: Accepted

### Context

通知 REST API の契約には、共通エラー形式がまだ決まっていない。
REQ-F-003 は、すべてのエラーレスポンスに共通する単一の形式を求めている。
その形式は、HTTP ステータスコードとエラー識別子をメンバーとして持ち、拡張メンバーの追加を許容しなければならない。
また REQ-F-003 は、RFC 9457 (Problem Details for HTTP APIs) を第一候補として評価し、採否と理由を記録することを求めている。

共通エラー形式が決まらないと、Specifications で次を定められない。

- 各エラーケースのエラー識別子と HTTP ステータスコード (REQ-F-004)
- エラー識別子の命名規則と拡張規則 (REQ-F-006)

契約には、検証の環境による制約がある。
契約は、ネットワーク接続と外部 URL への参照を必要とせずに、開発者の端末上で検証する (REQ-F-012)。

RFC 9457 の仕様には、本決定に関わる次の性質がある (一部の抜粋)。

- `type` は、Problem Type を識別する URI 参照である。省略すると `about:blank` とみなす
- `type` の URI は、参照先を解決できなくてもよい
- `status` メンバーは任意である
- 拡張メンバーを追加できる

### Decision

1. 決定 1: 共通エラー形式は RFC 9457 に従う。メディアタイプは `application/problem+json` とする。
2. 決定 2: `type` は、RFC 9457 に従う Problem Type の URI として使う。
3. 決定 3: `code` は、Keneek が独自に定める安定したエラー識別子を表す拡張メンバーとする。
   `code` は、requirements.md 1.3 Terms の「エラー識別子」にあたる。
   `code` は、`type` の URI の命名方式から独立させる。
4. 決定 4: `type` と `code` は 1 対 1 で対応させる。対応は Specifications の 1 か所で管理する。
5. 決定 5: `type` の URI に、参照先を解決できることを要求しない。
6. 決定 6: `type` の URI も契約の一部とする。`type` の URI を変えるときは、後方互換性への影響を評価する。
7. 決定 7: `status`・`type`・`code` は、Keneek のエラー契約の必須メンバーとする。
   `status` の値は、HTTP レスポンスのステータスコードと一致させる。
   Specifications は、この 2 点を必須として明記する。

### Scope

- Applies to: 通知 REST API の契約が定義するすべてのエラーレスポンス
- Not decided here:
  - `type` の URI の方式と具体的な値 → specifications
  - `code` の命名規則と具体的な値 → specifications (REQ-F-006)
  - `type` と `code` の対応を管理する場所 → specifications
  - `status`・`type`・`code` 以外の必須メンバーの一覧 → specifications
  - 各エラーケースの HTTP ステータスコード → specifications (REQ-F-004)
  - エラー区分と、変更の互換性の分類 → 未定 (エラー区分を決める DR を追加する)

### Alternatives Considered

- 独自のエラー形式を定める。既存の標準とツールを再利用できず、クライアントとリンタの実装が増えるため不採用。
- `type` だけを使い、`code` を設けない。識別子を二重管理せずに済む利点はある。
  しかし、Keneek が独自に定めるエラー識別子を、URI の命名方式から独立して持つことができない。そのため不採用。
- `code` だけを使い、`type` を使わない。`type` は RFC 9457 が定める Problem Type の標準の識別子である。
  使わないと RFC 9457 の標準的な使い方から外れるため不採用。
- RFC 9457 に従わず、`status` と `code` だけの最小形式にする。将来の拡張メンバーとの整合を自前で保つ必要があるため不採用。

### Rationale

RFC 9457 を採用する最大の理由は、HTTP API のエラー表現の標準に従い、実装・検証・ドキュメントの重複を減らせる点にある。
RFC 9457 は拡張メンバーを許す。
そのため、REQ-F-003 が求める拡張メンバーの追加と、REQ-F-006 が求めるエラー識別子の追加を、標準の範囲で表せる。

`code` を `type` と別に持つ目的は、URI の命名方式とアプリケーションのエラー識別子を切り離すことにある。
`type` は Problem Type の URI として RFC 9457 に従わせる。
`code` は Keneek のエラー識別子として、URI の方式とは別に安定させる。
2 つの識別子の食い違いは、対応を 1 か所で 1 対 1 に管理することで防ぐ。

`type` の URI に解決できることを要求しない理由は、契約をネットワーク接続なしで検証するためである (REQ-F-012)。
RFC 9457 は、解決できない `type` の URI を許している。

`status` を必須にする根拠は REQ-F-003 にある。REQ-F-003 は、HTTP ステータスコードをメンバーとして持つことを求めている。
RFC 9457 では `status` は任意だが、必須にしても RFC 9457 に反しない。
`status` の値が HTTP レスポンスのステータスコードと食い違うと、1 つのレスポンスから 2 つの異なるステータスを読み取れてしまう。両者を一致させる理由はこの点にある。

`type` と `code` を必須にする理由は、両者を決定 2〜4 で識別子として定めたことにある。
`type` を省略すると `about:blank` とみなされ、`type` と `code` の 1 対 1 の対応が失われる。

### Consequences

- Positive:
  - クライアントは、RFC 9457 に対応した既存のエラー処理とツールを再利用できる
  - `code` は `type` の URI の方式に依存しないため、クライアントは安定した識別子で分岐できる
  - 契約の検証が、`type` の URI の参照先に依存しない
  - エラーレスポンスは常に `status`・`type`・`code` を持ち、`status` は HTTP レスポンスのステータスコードと一致する
- Negative:
  - メディアタイプが `application/json` と異なるため、OpenAPI で明示的に定義する必要がある
  - `type` と `code` の 2 つの識別子を、対応を保ったまま管理する負担がある
  - `type` の URI の変更も、後方互換性を評価する対象になる
- Revisit Trigger:
  - `type` と `code` の 1 対 1 対応を維持できないエラー要件が発生したら、本 DR を見直す
  - 新しい通信方式またはメディアタイプの追加によって、RFC 9457 に基づく共通エラー形式を維持できなくなったら、本 DR を見直す

## DR-02: バッチ登録のレスポンスは all-or-nothing の形状とし、部分成功を表す形状を持たない - 2026-11-14 06:42:57

**Phase**: review-harden
**Status**: Accepted

### Context

バッチ登録のレスポンスを all-or-nothing の形状にする理由が、まだ記録されていない。
バッチ登録は、リクエストで `notifications` 配列を受け取り、複数の通知を 1 回で登録する操作とする (REQ-F-001)。
REQ-F-001 と AC-010 は、レスポンスを all-or-nothing を前提とした形状にすることを要件として定めている。
一方で requirements.md v1.1.0 の Design Decisions の要約では、この方針に対応する Decision Record が無い。

requirements.md v1.1.0 の REQ-F-001 の Rationale は、形状を固定する理由を次のように書いていた。

- 形状を先に固定しておけば、バッチ登録の振る舞いを担う兄弟 issue が all-or-nothing や冪等性を実装するときに、契約を変更せずに済む

セカンドオピニオンのレビューは、この理由が弱いと指摘した。
冪等性とセキュリティは、ヘッダーとエラーに影響する。
そのため、レスポンスの形状を固定しても、契約を変えずに済むとは限らない。

requirements.md v1.1.0 の時点では、バッチ登録の振る舞いについて、本契約と兄弟 issue の間に次の境界を置いていた (REQ-F-007、requirements.md 1.2 Scope の Out of Scope)。

- 本契約は、レスポンスの形状をインターフェースとして定義する
- all-or-nothing の実現方法、冪等性、バリデーションルールは、バッチ登録の振る舞いを担う兄弟 issue が定義する

### Decision

1. 決定 1: バッチ登録のレスポンスは all-or-nothing の形状とする。
   レスポンスは、バッチ全体の成功と失敗の 2 つの形状だけを持つ。
2. 決定 2: 成功時のレスポンスは、入力の各要素に 1 対 1 で、入力と同じ順序で対応する通知ごとの結果を持つ。
   通知ごとの結果は、通知 ID と状態を含む。
3. 決定 3: 失敗時のレスポンスは、共通エラー形式 (DR-01) の単一のエラーとする。
   要素ごとの結果は含まない。
4. 決定 4: 一部の要素だけが成功したことを表すレスポンス形状は定義しない。

### Scope

- Applies to: 通知 REST API の契約が定義するバッチ登録のレスポンスの形状。本 DR が決めるのはレスポンスの形状だけとする
- Not decided here:
  - 再送時の振る舞い (冪等性) → DR-03 決定 6。冪等性は、本 DR とは別の保証として扱う
  - 登録処理の原子性は、責務によって次の 2 つに分けて委ねる。レスポンスの形状は、登録処理の原子性を保証しない
    - 外部から観測できる原子性の保証 → API 契約として specifications (DR-03 決定 1、REQ-F-001)
    - 登録処理での原子性の実現と保証 → バッチ登録の振る舞いを担う兄弟 issue #4 (REQ-F-007)
  - all-or-nothing の実現方法 (トランザクションなど) → バッチ登録の振る舞いを担う兄弟 issue #4 (REQ-F-007)
  - バリデーションルール (requirements.md 1.3 Terms) は、責務によって次の 2 つに分けて委ねる
    - 入力を受け付ける条件・拒否する条件と、拒否に使うエラー識別子 → specifications (REQ-F-007)。外部から観測できる判定結果として、API 契約が定義する
    - 判定アルゴリズムと内部の検証処理 → バッチ登録の振る舞いを担う兄弟 issue #4 (REQ-F-007)
  - 通知ごとの結果の具体的なメンバーと、成功時の HTTP ステータスコード → specifications
  - 失敗時のエラー識別子と HTTP ステータスコード → specifications (REQ-F-004)

### Alternatives Considered

- 部分成功を表すレスポンスにする。クライアントが要素ごとの結果を解釈する必要があり、再送の扱いも複雑になるため不採用。
- レスポンスの形状をバッチ登録の実装に委ねる。契約が実装の後に変わり、PWA の開発を先行できなくなるため不採用。
- 成功時に通知 ID の配列だけを返す。状態を別に取得する必要があり、入力との対応も曖昧になるため不採用。

### Rationale

all-or-nothing を採用する理由は、クライアントがバッチ全体の成功と失敗を一意に解釈できる点にある。
レスポンスが成功と失敗の 2 つの形状しか持たないため、クライアントは部分成功を表すレスポンス形状を解釈する必要がない。
ただし、実際に一部だけが登録された状態が生じないことはレスポンス形状だけでは保証できず、兄弟 issue #4 の登録処理の原子性保証を前提とする。
成功時は、入力と同じ順序で 1 対 1 に結果が並ぶ。そのため、クライアントは各結果がどの入力要素のものかを、追加の照合なしに特定できる。
失敗時は、共通エラー形式 (DR-01) の単一のエラーが返る。そのため、クライアントは他の操作と同じエラー処理でバッチの失敗を扱える。

requirements.md v1.1.0 の REQ-F-001 の Rationale にあった「契約を変更せずに済む」は、採用の理由にしない。
冪等性とセキュリティはヘッダーとエラーに影響する。そのため、レスポンスの形状を固定するだけでは契約の変更を防げない。
再送時の振る舞いは、本 DR と切り離し、外部から観測できる保証として DR-03 決定 6 で扱う。

### Consequences

- Positive:
  - クライアントは、バッチ全体の成功と失敗を一意に解釈できる
  - 成功時の結果を、入力の要素と順序で対応付けられる
  - 失敗時のレスポンスを、他の操作と同じ共通エラー形式の処理で扱える
  - レスポンス形状の契約テストでは、バッチ全体の成功形状と失敗形状を検証し、部分成功形状を要求しない
- Negative:
  - 部分成功を表すレスポンス形状が無いため、クライアントは要素ごとの成功と失敗の情報を得られない
  - 登録処理の原子性は、レスポンスの形状だけでは保証されない。外部から観測できる原子性の保証は API 契約に含まれる。
    登録処理での原子性は、バッチ登録の振る舞いを担う兄弟 issue #4 が実現し、保証しなければならない
- Revisit Trigger:
  - バッチ登録の API 契約において、要素単位の成功・失敗を区別して返す必要が生じたら、本 DR を見直す

- requirements/requirements.md: REQ-F-007
- requirements/requirements.md: AC-010
- decision-records.md: DR-01
- decision-records.md: DR-03
- GitHub Issue: #3

## DR-03: 外部から観測できる振る舞いの保証を API 契約に含め、内部の実現方法は兄弟 issue に委ねる - 2026-11-14 06:50:35

**Phase**: review-harden
**Status**: Accepted

### Context

契約がどこまでを定めるかの境界が、外部から観測できる振る舞いについて決まっていない。
requirements.md v1.1.0 の REQ-F-007 は、契約をインターフェースの定義に限定している。
同じ要件は、冪等性、照会・キャンセルの判定ロジック、状態管理 (状態遷移)、ローカルセキュリティなどを兄弟 issue の責務として契約から外している。
本 DR に関わる兄弟 issue は次の 3 つとする (Out of Scope に挙がる兄弟 issue の一部)。

- #4 (バッチ登録)
- #5 (照会・キャンセル)
- #6 (ローカルセキュリティ)

セカンドオピニオンのレビューは、この境界では外部から観測できる事項まで兄弟 issue の決定に任されると指摘した。
指摘した事項は次の 3 つとする。

- 冪等性は、再送時のヘッダーと衝突エラーに影響する
- 認証は、資格情報の渡し方に影響する
- キャンセルは、結果の意味に影響する

これらを兄弟 issue の決定に任せると、契約が後から変わる。

バッチ登録の再送時の振る舞いも、この境界の上にある。
DR-02 は、バッチ登録のレスポンスを all-or-nothing の形状に決めた。
DR-02 は、冪等性をレスポンスの形状とは別の保証として扱い、再送時の振る舞いを外部から観測できる保証を決める DR に委ねている。

### Decision

1. 決定 1: 外部から観測できる振る舞いの保証は、API 契約に含める。
2. 決定 2: 保証を内部でどう実現するかは契約に定めず、兄弟 issue に委ねる。
3. 決定 3: 保証ごとに独自の状態 (`Agreed`・`Provisional` など) を付けて管理する方式は導入しない。
4. 決定 4: 未確定の事項は Open Questions として管理する。合意した判断は DR に記録する。
5. 決定 5: 契約を確定する前に、兄弟 issue との整合を確認する。
6. 決定 6: バッチ登録の再送時の振る舞い (冪等性) のうち、外部から観測できる部分は決定 1 に従って契約に含める。
   冪等性は、DR-02 が決めたレスポンスの形状とは別の保証として扱う。

### Scope

- Applies to: 通知 REST API の契約が定義するすべての操作の、外部から観測できる振る舞い。
  バッチ登録の再送時の振る舞い、キャンセルの結果、認証の資格情報の渡し方を含む
- Not decided here:
  - 契約に含める保証の具体的な一覧 → specifications (未確定の間は Open Questions で管理する)
  - 再送時の振る舞いの具体的な内容 (再送の結果が属するレスポンスの区分、再送を識別するリクエストヘッダーの有無など) → specifications
  - キャンセルの結果の具体的な意味 (キャンセル後の通知の状態、キャンセル済みの通知を再びキャンセルしたときに成功とするかエラーとするか) → specifications
  - 認証に必要なリクエスト上の情報、資格情報の送信形式 (HTTP ヘッダー名・配置を含む)、認証失敗時の外部応答 → specifications
    - 資格情報の発行・保存・検証など、認証メカニズムの内部実装 → 兄弟 issue #6
    - 認証方式によって外部仕様が変わる場合は、仕様を確定する前に issue #6 と整合を確認する
  - REQ-F-007 の要件文の改訂 (1.3 Terms の「インターフェース」「振る舞い」との整合を含む)、AC-004・US-003 の改訂、および REQ-C-005 の認証責務との整合確認 → requirements.md (4 本の DR の完成後にまとめて実施する。本 DR では変更しない)
  - 兄弟 issue との整合を確認する具体的な方法 → 未定 (契約を確定するまでに決める)
    - 整合確認は兄弟 issue の実装完了や内部設計の確定を要求しない
    - API 契約の各保証について、兄弟 issue の責務、実現可能性、既知の制約に矛盾がないことを確認する
  - 冪等性、照会・キャンセルの判定ロジック、状態管理 (状態遷移)、認証メカニズムの実現方法 → 各兄弟 issue (#4、#5、#6)

### Alternatives Considered

- 契約をインターフェースの定義だけに保ち、兄弟 issue が後から契約に保証を追加する。
  契約の変更が破壊的になりやすく、クライアントへの影響を管理できないため不採用。
- 契約が振る舞いをすべて定義する。兄弟 issue と責務が重複し、記述が矛盾する可能性のため不採用。
- 兄弟 issue の内部設計や実装の完了を待ってから契約を確定する。
  契約が実装の基準にならず、PWA の開発を先行できないため不採用。
  ただし、Decision 5 に従う責務・実現可能性・既知の制約の整合確認は、契約確定前に実施する。
- 外部から観測できる保証を契約に含め、保証ごとに `Agreed`・`Provisional` の状態を付ける。
  未確定と合意済みの区別は、Open Questions と DR ですでに表せる。
  独自の状態を加えると、同じ区別を 2 つの仕組みで持つことになるため不採用。

### Rationale

外部から観測できる振る舞いを契約に含める最大の理由は、契約が後から変わる原因を、契約の側で先に押さえること。
再送時のヘッダー、衝突エラー、資格情報の渡し方、キャンセルの結果の意味は、いずれもクライアントがレスポンスやリクエストを通して直接扱う。
これらを兄弟 issue が後から決めると、契約の変更が破壊的になりやすい。
破壊的変更には、新しい API メジャーバージョンと移行手順の記述が必要になる (REQ-F-011)。

内部の実現方法を兄弟 issue に委ねる理由は、REQ-F-007 が避けようとした責務の重複と矛盾を、改訂後も避けることにある。
契約が定めるのは結果として観測できる点に限る。
トランザクションや判定ロジックは、契約で定めた保証を満たす範囲で兄弟 issue が選べる。
認証に必要なリクエスト上の情報、資格情報の送信形式、認証失敗時の外部応答はクライアントが扱う API 契約として specifications に定義する。
資格情報の発行・保存・検証などの内部メカニズムは issue #6 に委ねる。認証方式が外部仕様に影響する場合は、issue #6 と整合を確認する。

独自の状態管理を導入しない理由は、未確定の事項と合意した判断を、既存の Open Questions と DR で区別できることにある。
Open Questions は requirements.md などにある未解決事項を管理し、DR は合意した設計判断とその理由を記録する。
specifications は、確定した API の動作仕様を管理する。
DR の `Accepted` はその DR の設計方針が採用されたことを意味し、関連する個別仕様のすべてが確定したことを意味しない。
Open Questions の事項を解決した際には、必要な判断を DR に記録し、具体的な API 契約を specifications に反映する。

契約の確定前に兄弟 issue との整合を確認する理由は、契約が定める保証を実現するのが兄弟 issue であることにある。
整合確認は兄弟 issue の実装や内部設計の完了を待つものではなく、契約上の保証に対する責務、実現可能性、既知の制約の矛盾を確認するものとする。
確定前に整合を確かめれば、確定後に契約を変える必要を減らせる。
確定後に兄弟 issue が契約の変更を必要とした場合は、REQ-F-009 に従い契約を先に更新する。

### Consequences

- Positive:
  - 兄弟 issue の決定によって、確定後の契約が破壊的に変わる可能性が下がる
  - クライアントは、再送、キャンセル、認証の結果を契約だけを見て扱える
  - 兄弟 issue は、外部から観測できる保証を満たす範囲で実現方法を選べる
  - 未確定の事項と合意した判断の管理が、Open Questions と DR に一本化される
- Negative:
  - 契約されている範囲が広がり、specifications で決める事項が増える
  - 契約を確定する前に、兄弟 issue との整合を確認する手間がかかる
  - REQ-F-007 の要件文、AC-004、US-003 は「インターフェースのみ」を前提にしているため、本 DR に合わせて改訂する必要がある
  - REQ-C-005 は認証メカニズムとクライアント向け認証インターフェースの境界について整合性を確認する必要がある
  - requirements.md の改訂は 4 本の DR が完成した後にまとめて行うため、それまでは既存記述との不整合が残る
- Revisit Trigger:
  - 外部から観測できる振る舞いと内部の実現方法の責務分離が成立せず、API 契約と兄弟 issue の責務が重複または欠落する場合、本 DR を見直す
  - 兄弟 issue の実現方法の変更が、契約に含めた保証の変更を繰り返し求めるようになったら、本 DR を見直す

## DR-04: エラーの分類とクライアントの対処を分離し、エラー識別子の追加を無条件に後方互換としない - 2026-11-14 07:06:34

**Phase**: review-harden
**Status**: Accepted

### Context

エラーの区分と、エラー識別子の変更の互換性が決まっていない。
DR-01 は、この 2 つを、エラー区分を決める DR に委ねている。

requirements.md v1.1.0 の REQ-F-006 は、エラー識別子の追加を常に後方互換な変更として扱う。
同じ要件は、クライアントが未知のエラー識別子を受け取ったときに、HTTP ステータスコードで処理を続けられることを求めている。
AC-012 は、識別子の追加を契約バージョンの MAJOR を上げずに行えることとしている。

requirements.md 1.3 Terms は、後方互換性を「既存クライアントが変更なしに動作し続けられること」と定義している。
その対象は、リクエスト、レスポンス、エラー形式、エラー識別子とする。
破壊的変更のときは、新しい API メジャーバージョンを導入する (REQ-F-011)。

セカンドオピニオンのレビューは、REQ-F-006 について次の 2 点を指摘した。

- HTTP ステータスコードへのフォールバックだけでは、クライアントが再試行・再認証・入力の修正のどれを選ぶかを保てない場合がある
- 「識別子の追加」と「既存の操作の意味の変更」を区別しなければならない。たとえば、以前は成功したリクエストが新しいエラーを返すようになる変更がある

ハードニングのレビューは、分類を 5 つに固定し、5xx を再試行の分類とする案を出した。
本 DR は、この案を採らずに、分類とクライアントの対処を分ける。

再送時の振る舞いについては、DR-03 決定 6 が、外部から観測できる部分を契約に含めると決めている。

### Decision

1. 決定 1: エラーの分類と、クライアントの対処方法を分離する。各エラー識別子は、ちょうど 1 つの分類に属する。
2. 決定 2: クライアントの対処方法は、エラー識別子 (`code`) ごとに、API 契約の一部として specifications に定める。
   RFC 9457 のエラーレスポンスに、対処方法を表す拡張メンバー (`retryable`・`action` など) を加えない。
3. 決定 3: クライアントの対処方法では、次の 3 つを独立した判断点として区別する。
   - 再試行可能性: 同じリクエストを再試行することに効果があるか
   - 再送安全性: 再送によって副作用を重複させるおそれはあるか
   - 結果の確定性: クライアントがリクエストの処理結果を確定できるか

   3 つすべてを、各エラー識別子の必須の属性とはしない。各識別子に必要な対処方針は specifications に定める。
4. 決定 4: クライアントの対処方法を、HTTP ステータスコードだけで判断しない。5xx を一律に再試行可能として扱わない。
   各 `code` の仕様が、対処に必要な条件を示す。
5. 決定 5: エラー識別子を得られない場合の扱いも、契約に定める。
   応答を受け取れない通信失敗は、結果が確定しない場合の扱いに含める。
6. 決定 6: 再送時の重複防止を API が保証する場合、その外部契約は各操作の契約として specifications に定める (DR-03 決定 6)。
   重複防止の内部の実現方法は、担当する兄弟 issue に委ねる。
   本 DR が扱うのは、クライアントがその保証をどう解釈し、エラーが起きたときにどう対処するかに限る。
7. 決定 7: `Retry-After` などの標準の HTTP ヘッダーで、動的な情報を提供することは妨げない。
8. 決定 8: 新しいエラー識別子の追加と、既存の API 操作の変更を区別して評価する。
   識別子の追加であることだけを理由に、後方互換と判断しない。
   新しいエラー識別子の追加を後方互換とするのは、既存の API 操作の次のいずれも変えない場合に限る。
   - 成功条件
   - 再送時の保証
   - クライアントに求める対処
9. 決定 9: 既存クライアントから観測できる振る舞い、または既存クライアントに求める対処が変わる変更は、破壊的変更として評価する。
   識別子の追加を伴うかどうかは問わない。
10. 決定 10: クライアントは、未知のエラー識別子を、次の順で扱う。
    - その識別子の分類が既知の契約に従って解釈できる場合に限り、分類に基づいて扱う
    - 分類が不明な場合、または解釈できない場合は、HTTP ステータスコードを参照する

    HTTP ステータスコードだけでは、再送安全性と処理結果の確定性を保証できない。
    そのため、再送安全性を確認できない冪等でない操作を、無条件に自動で再試行しない。
11. 決定 11: クライアントは、未知のエラー拡張メンバーを無視する。既知のメンバーの意味は変えない。

### Scope

- Applies to: 通知 REST API の契約が定義するすべてのエラーと、エラー識別子を得られない通信失敗に対するクライアントの対処。
  エラー識別子とエラー拡張メンバーの変更の互換性の評価を含む
- Consistency: DR-01 が決めた `type` と `code` の対応、および DR-03 決定 6 (再送時に観測できる振る舞いを契約に含める) と整合させる。
  本 DR はどちらも変更しない
- Not decided here:
  - 分類の具体的な名前と一覧 → specifications
  - エラー識別子の一覧と、各識別子の対処方針 → specifications (REQ-F-004、REQ-F-006)
  - 未知のエラー識別子から分類を判別する方法 → specifications (REQ-F-006 の命名規則)
  - エラー識別子を得られない場合の具体的な扱い → specifications
  - 各操作の再送時に観測できる具体的な振る舞い → specifications (DR-03 決定 6)
  - 重複防止の仕組みの実現方法 → 担当する兄弟 issue (バッチ登録の再送は #4)
  - 再試行を許す条件・再送安全性・待機の条件など、API 契約が保証する事項 → specifications
  - 指数バックオフ・ジッター・最大試行回数などの具体的な再試行のアルゴリズム → クライアントの実装
    (API 契約で保証する必要のある部分に限り specifications)。本 DR は特定のアルゴリズムを固定しない
  - `Retry-After` などの標準の HTTP ヘッダーを使うかどうかと、使う場合の意味 → specifications
  - エラー以外を含む、破壊的変更と非破壊的変更の判断基準の全体 → specifications (REQ-F-011)
  - REQ-F-006 と AC-012 の改訂 → requirements.md (4 本の DR の完成後にまとめて実施する。本 DR では変更しない)

### Alternatives Considered

- エラー識別子の追加をすべて後方互換とし、未知の識別子は HTTP ステータスコードだけで処理する。
  HTTP ステータスコードだけでは、クライアントが再試行・再認証・入力の修正のどれを選ぶかを保てない。
  また、以前は成功したリクエストが新しいエラーを返すような、既存の操作の意味を変える追加まで後方互換に含まれる。そのため不採用。
- エラー識別子を追加するたびに、契約バージョンの MAJOR を上げる。
  識別子を追加する自由がなくなり、兄弟 issue が必要なエラー識別子を追加できなくなる (REQ-F-006)。そのため不採用。
- エラーレスポンスに `retryable`・`action` などの拡張メンバーを加え、対処方法をレスポンスで伝える。
  対処方法は `code` ごとに specifications で契約として定める。
  レスポンスにも載せると、同じ情報を specifications とレスポンスの 2 か所で持つことになる。
  また、再試行可能性・再送安全性・結果の確定性は独立した判断点であり (決定 3)、単一のフラグでは表せない。そのため不採用。
  これは、対処方法を表す拡張メンバーを採らない判断に限る。
  RFC 9457 の拡張メンバー全般を禁止するものではない (拡張メンバーの追加は DR-01 が認め、未知のメンバーの扱いは決定 11 が定める)。
- ハードニングのレビューが出した、分類を 5 つに固定する案を採る。5 つの分類は、入力の修正 (4xx の検証エラー)、再認証 (401)、不存在 (404)、状態の競合 (409)、再試行 (5xx) とする。
  5xx を一律に再試行とすると、再試行可能性・再送安全性・結果の確定性を区別できない。
  分類が対処を兼ねるため、分類と対処を分離できない。そのため不採用。

### Rationale

分類や HTTP ステータスコードだけでは、クライアントの取るべき対処を特定できない。これが、分類と対処を分離する最大の理由となる。
同じ 5xx でも、再試行に効果があるか、再送で副作用が重複するか、処理結果を確定できるかは異なりうる。
3 つの判断点を区別すれば、クライアントは副作用を重複させずに対処を選べる。

対処方法を `code` ごとに specifications で定め、レスポンスに載せない理由は、対処方法が契約の一部であることにある。
クライアントは、契約を見て `code` ごとの対処を実装できる。
共通エラー形式は、DR-01 が決めた RFC 9457 の形のまま保てる。

エラー識別子を得られない場合の扱いを定める理由は、その場合には `code` ごとの対処を使えないことにある。
応答を受け取れない通信失敗では、クライアントは処理結果を確定できない。

識別子の追加を無条件に後方互換としない理由は、1.3 Terms の後方互換性の定義にある。
互換性を決めるのは変更の形 (識別子の追加かどうか) ではなく、既存クライアントへの影響となる。
既存の成功条件・再送時の保証・既存クライアントに求める対処のどれかが変わると、既存クライアントは変更なしに動作を続けられなくなる。
そのため、この変更は定義上、後方互換ではない。
一方で、この 3 つを変えない追加は、既存クライアントに影響しない。兄弟 issue は、この範囲で MAJOR を上げずに識別子を追加できる。

未知の識別子を、HTTP ステータスコードより先に分類で扱う理由は、HTTP ステータスコードだけでは対処の選択を保てないことにある。
分類に基づく扱いを、既知の契約に従って解釈できる場合に限る理由は、解釈できない分類から対処を推測すると誤った対処を選ぶおそれがあることにある。
HTTP ステータスコードは、再送安全性と処理結果の確定性を示さない。
再送安全性を確認できない冪等でない操作を自動で再試行しない理由は、再送で副作用が重複するおそれを避けることにある。
具体的な再試行のアルゴリズムをクライアントの実装に委ねる理由は、契約が保証すべきなのは再試行を許す条件であり、試行の間隔や回数の決め方ではないことにある。

未知の拡張メンバーを無視する理由は、拡張メンバーを追加できる余地を残すことにある (REQ-F-003、DR-01)。
既知のメンバーの意味を変えると、既存クライアントの解釈が変わる。そのため、意味は変えない。

### Consequences

- Positive:
  - クライアントは、`code` ごとに契約で定めた対処を選べる
  - 5xx を一律に再試行しないため、冪等でない操作で副作用を重複させるおそれが減る
  - 共通エラー形式は、DR-01 の RFC 9457 の形のまま保たれる
  - 兄弟 issue は、成功条件・再送時の保証・既存クライアントに求める対処を変えない範囲で、MAJOR を上げずに識別子を追加できる
- Negative:
  - specifications は、各エラー識別子の対処方針と、エラー識別子を得られない場合の扱いを定めなければならない
  - 識別子を追加するたびに、成功条件・再送時の保証・既存クライアントに求める対処を変えないかを評価する手間がかかる
  - レスポンスが対処方法を運ばないため、クライアントは `code` ごとの対処を契約から取り込んで持つ必要がある
  - REQ-F-006 と AC-012 は、識別子の追加を常に後方互換とし、HTTP ステータスコードへのフォールバックだけを示している。
    本 DR に合わせて、4 本の DR の完成後にまとめて行う requirements.md の改訂で改める必要がある。それまでは既存記述との不整合が残る
- Revisit Trigger:
  - 同じ `code` でもリクエストごとに対処が変わり、`code` ごとの定義と標準の HTTP ヘッダーでは対処を伝えられなくなったら、本 DR を見直す
  - 識別子の追加の多くが破壊的変更と評価され、兄弟 issue が必要なエラーを追加できなくなったら、本 DR を見直す

## DR-05: 契約確定前の兄弟 issue との整合確認は、保証ごとの照合結果を記録として Specifications に残す - 2026-11-14 07:43:22

**Phase**: review-harden
**Status**: Accepted

### Context

契約確定前の兄弟 issue との整合確認について、何をもって「確認した」とするかの基準と、確認の記録の置き場所が決まっていない。
DR-03 決定 5 は、契約を確定する前に兄弟 issue との整合を確認すると決めた。
DR-03 は、整合確認の範囲を次のように定めている。

- 兄弟 issue の実装の完了や内部設計の確定を要求しない
- API 契約の各保証について、兄弟 issue の責務、実現可能性、既知の制約に矛盾がないことを確認する

一方で、確認の具体的な方法は DR-03 では決めていない。

requirements.md v1.2.1 の REQ-F-009 は、DR-03 決定 5 を要件として定めている。
REQ-F-009 に紐づく AC-020 は、整合確認の結果として、矛盾がないと確認されていることを求める。
fix レビューは、AC-020 について次の 2 点が定まっていないと指摘した。

- 何をもって「確認されている」とするかの判定基準
- 確認の記録を置く場所

requirements.md の Open Questions には「兄弟 issue との整合を確認する具体的な方法をどうするか (契約の確定までに決める)」が残っている。
この項目の Owner は契約メンテナとしている。

兄弟 issue と API 契約の関わり方は、issue によって異なる。

- #4 (バッチ登録)、#5 (照会・キャンセル)、#6 (ローカルセキュリティ) は、DR-03 が外部から観測できる保証に関わる兄弟 issue として挙げた 3 つ
- #7 (永続化) は、requirements.md 1.2 Scope で、契約のデータ形状と状態の集合を通じて契約に間接的に依存するとされている

### Decision

1. 決定 1: 契約確定前の兄弟 issue との整合確認は、記録として残す。本 DR は DR-03 決定 5 を具体化するものであり、DR-03 を置き換えない。
2. 決定 2: 整合確認の記録は Specifications に置く。
3. 決定 3: 記録は、契約の各保証について、照合対象の兄弟 issue との照合結果を持つ。
   照合結果は、保証と照合対象の組ごとに、次の 3 つを区別する。
   - 整合
   - 矛盾あり
   - 未確認

   記録の存在だけでなく、保証ごとの照合結果と未解決の矛盾も、記録から検証できなければならない。
4. 決定 4: 基本の照合対象は、#4 (バッチ登録)、#5 (照会・キャンセル)、#6 (ローカルセキュリティ) の 3 つとする。
5. 決定 5: #7 (永続化) は、API 契約の保証が永続化の責務へ依存する場合だけ、その保証の照合対象に加える。
6. 決定 6: 契約を確定するときは、照合対象の保証について次の 2 点を条件とする。
   - 照合が完了している (照合結果に「未確認」が残っていない)
   - 未解決の矛盾が残っていない (「矛盾あり」の照合結果は、すべて解消されている)
7. 決定 7: 整合確認とその記録に、兄弟 issue の実装の完了や内部設計の確定を要求しない。

### Scope

- Applies to: 通知 REST API の契約を確定する前に行う、兄弟 issue との整合確認とその記録
- Consistency: DR-03 決定 5 と、DR-03 Scope が定めた整合確認の範囲 (責務・実現可能性・既知の制約) に従う。
  本 DR は DR-03 を置き換えない。DR-03 と同じく、兄弟 issue の実装の完了や内部設計の確定を要求しない
- Responsibility boundary with #8 (e2e テスト):
  - #8 は照合対象に加えない。#8 は API 契約を検証する側の責務を持つ
  - e2e テストで見つかった契約の矛盾は、契約の確定前に解消する
- Not decided here:
  - 記録の形式の詳細 (記録の構成、項目の書き方、照合結果の 3 つの区別の表し方など) → specifications
  - 照合の具体的な手順 (誰がどう照合するか) → requirements.md の Open Questions (Owner: 契約メンテナ)。契約の確定までに決める
  - REQ-F-009 の要件文と AC-020 の改訂 → requirements.md

### Alternatives Considered

- 判定基準を定めず、プルリクエストのレビューでの目視確認に任せる。
  記録が残らず、確認したかどうかを後から検証できないため不採用。
- 兄弟 issue ごとの承認を、契約確定の条件にする。
  兄弟 issue の設計の確定を事実上要求することになる。
  これは、確認に兄弟 issue の内部設計の確定を求めないとする REQ-F-009 に反するため不採用。
- 整合確認の記録を decision-records.md に置く。
  DR は設計判断とその理由を記録する文書であり、保証ごとの照合結果の一覧とは性質が異なる。
  また、DR の `Accepted` は設計方針の採用を表し、個別の仕様の確定を表さない (DR-03)。
  照合結果を DR に置くと、仕様の確定と DR の採用を混同しやすくなるため不採用。

### Rationale

記録を Specifications に置く最大の理由は、照合する保証そのものが Specifications で確定することにある。
DR-03 は、未確定の事項を Open Questions に、合意した設計判断を DR に、確定した API の動作仕様を Specifications に記録すると整理した。
保証と照合結果を同じ場所に置けば、確定する保証ごとに照合結果を対で追える。
記録が Deckrd のドキュメントの中にあれば、プルリクエストのレビューで記録の存否と内容を確認できる。

保証ごとの照合結果と未解決の矛盾まで検証できるようにする理由は、AC-020 の判定基準を定めることにある。
記録があるだけでは、どの保証をどの兄弟 issue と照らし合わせたかが分からない。
保証ごとの照合結果と未解決の矛盾が読み取れれば、矛盾が解消されたかを契約の確定時に判定できる。
「未確認」と「整合」を区別する理由は、照合していない保証を整合と取り違えないことにある。
この区別があれば、契約の確定時に照合が完了したかを判定できる。

基本の照合対象を #4、#5、#6 とする理由は、DR-03 がこの 3 つを外部から観測できる保証に関わる兄弟 issue として挙げていることにある。
永続化を担う #7 は、契約のデータ形状と状態の集合を通じて、間接的に契約へ依存する。
そのため、#7 を照合対象に加えるのは、保証が永続化の責務へ依存する場合に限る。
e2e テストを担う #8 は、API 契約を検証する側の責務を持ち、照合する側ではない。
そのため、#8 は照合対象に加えず、e2e テストで見つかった契約の矛盾を契約の確定前に解消することで扱う。

照合の具体的な手順を本 DR で決めない理由は、記録に求める条件と、照合を進める手順を分けて扱えることにある。
手順は requirements.md の Open Questions で契約メンテナが決める。

### Consequences

- Positive:
  - AC-020 の「確認されている」を、記録の存在と内容、照合の完了 (「未確認」が残っていない)、未解決の矛盾が残っていないことで判定できるようになる
  - Specifications の中で、確定した保証とその照合結果を対にして追える
  - 兄弟 issue の実装や内部設計の完了を待たずに、契約を確定できる
- Negative:
  - Specifications は、契約の各保証について照合結果の記録を持たなければならない
  - 保証ごとに、永続化の責務に依存するかを判断し、#7 を照合対象に加えるかを決める手間がかかる
  - REQ-F-009 と AC-020 は、記録とその所在を定めていない。本 DR に合わせて requirements.md を改訂する必要があり、それまでは既存記述との不整合が残る
  - 照合の具体的な手順は未定のまま残り、契約の確定までに決める必要がある
- Revisit Trigger:
  - 内部設計の確定を整合確認の前提とする必要が生じ、決定 7 の再検討が必要になったら、本 DR を見直す
  - #4、#5、#6、#7 以外の兄弟 issue の責務に依存する保証が API 契約に現れたら、照合対象の範囲を見直すために本 DR を見直す

## DR-06: バッチ登録の冪等性を、安全性・応答の一貫性・回復可能性に分けて外部契約にする - 2026-11-14 10:07:11

**Phase**: spec
**Status**: Accepted

### Context

バッチ登録の再送時の振る舞い (冪等性) について、外部契約の中身が決まっていない。
REQ-F-007、DR-03 決定 6、DR-04 決定 6 は、外部から観測できる再送時の振る舞いを契約に含めることを求めている。
同じ 3 つは、内部の実現方法を兄弟 issue に委ねるとしている。委ねる先は、バッチ登録を担う #4 と、永続化を担う #7 になる。

specifications の草案 (各ファイルの version 1.0.0) を設計する中で、次の 5 つの問題が見つかった。

- HTTP の 4xx から、キーを再利用してよいかを推論するのは安全でない。理由は次の 3 つである
  - エラー応答の優先順位 (DD-ER-05) では、`request.invalid` (400) がキーの評価より先に返る
  - 入力検証には、時刻に依存する判定がある (過去の `fireAt` の扱いは specifications-endpoints.md の Open Questions に残っている)
  - 応答を失った先行の送信が、後から処理される場合がある
- 同時に届いた別の本文のリクエストに 409 を返すと、処理中のリクエストが後で失敗したときに、その 409 が誤りになる
- 1 回の応答だけでは、論理操作が今後も登録されないことを保証できない
- 503 は、キーの競合からも他の障害からも返り得る。クライアントは両者を区別できない
- 登録と成功結果の記録を外部から見て同時に成立させても、停止後の回復が完了することまでは保証されない

草案の specifications は、これらの問題を含む次の規則を持っていた (一部の抜粋)。

- 結果が未確定のキーに別の本文が届いたら 409 `idempotency.key_conflict` を返す (R-ER-012、R-EP-072)
- API の 4xx を受け取ったキーは「登録なしが確定」とし、入力を修正した本文で再利用できる (R-EP-076)
- 「同じ本文」の判定基準 (バイト列の一致か、JSON としての意味的な等価か) を Open Questions に残している

ユーザーは、基本の方針として次を選んだ。

- クライアントが結果を確定できない場合でも、サーバー側で登録の重複を防ぐことを優先する
- 回復できない障害の後に、結果の確定しない状態が残ることは受け入れる

### Decision

安全性:

- 決定 1: Idempotency-Key は、本文と組になって、1 つの論理操作 (キー K と本文 B の組) を識別する。
  クライアントは、新しい論理操作には新しいキーを作らなければならない (MUST)。
  例外は、決定 9 が許す登録し直し (同じ登録の意図を、決定 9 の条件を満たして登録し直すこと) だけとする。
  この登録し直しに限り、同じキーを別の本文で使ってよい (新しいキーを推奨する。決定 9)。
  再送では、同じキーを使い、本文をまったく同じバイト列で送らなければならない (MUST)。
- 決定 2: 同じキーの同時の登録処理のうち、登録へ進めるのは同時に高々 1 つとする。
  どの登録処理が進むか、どの順序 (送信順・到着順・開始順・完了順) で進むかは保証しない。
  進めなかった登録処理は登録せず、他の登録処理の結果を変えない。
- 決定 3: 保持の保証が有効な間、1 つのキーで成立する登録は高々 1 つとする。保持の保証が有効な期間は次のとおりとする。
  - 成功の記録: サーバーで成功が確定した時点から最低 24 時間
  - 結果が確定していない登録処理: 結果が確定するまで
- 決定 4: 結果が確定していないキーは、安全性を失う形で解放しない。
  その登録処理がもう登録を成立させ得ないと確実になるまで、そのキーを未使用として扱わない。
  ここでいう登録処理は、論理操作 (キー K と本文 B の組で識別される操作) について、サーバーが実行する個々の処理を指す。
  期限切れにしてよいのは、結果が確定した記録だけとする。
  - 成功の記録: サーバーで成功が確定した時点から最低 24 時間の後
  - 登録なしの記録: いつでもよい

  保持の保証の終了、記録の実際の削除、再送を新規の登録として処理することの 3 つは、別の事柄として扱う。
  結果が確定していない記録を無期限に保持することは、実現方式として固定しない。
- 決定 5: キーの評価より前に拒否された送信は、キーと登録のどちらにも影響しない。対象は次の拒否とする。
  - 認証
  - ルーティング・メソッド・認可
  - メディアタイプと Content-Encoding・本文サイズ
  - キーのヘッダーの形式

  入力検証で拒否された送信は、何も登録せず、確定済みのキーの状態を変えない。

応答の一貫性:

- 決定 6: 成功が確定したキーに同じ本文で再送されたときは、元の 201 と、元のレスポンス本文の写しを返す。
  この再現は、認証、ルーティング・メソッド・認可、メディアタイプと Content-Encoding、本文サイズ、キーのヘッダーの形式の各検査を通過した送信に限る。
  そのうえで、入力内容の検証の結果は問わない。
  これを、エラー応答の優先順位 (specifications-errors.md 4.1、DD-ER-05) の唯一の例外とする。
  通知の最新の状態は GET で取得する。
- 決定 7: 処理中または回復待ちの登録処理と競合した送信には、本文が同じでも異なっても 503 `server.unavailable` を返す。
  入力検証の 400 は、本文が同じでも異なっても、常にこの 503 より優先する。
  サーバーは、競合による 503 を返した送信では登録しない。
  ただし、クライアントはこの 503 を他の 503 と区別できない。
- 決定 8: 409 `idempotency.key_conflict` を返すのは、そのキーで別の本文の成功がすでに確定している場合だけとする。
- 決定 9: 送信ごとの意味は次のとおりとする。
  - 契約に適合する 201 は、論理操作の成功が確定したことを示す
  - API が生成した、共通エラー形式の 4xx (`code` を持つ `application/problem+json`) だけが、その送信で登録されなかったことを示す
  - 503 を含むすべての 5xx、problem 形式でないエラー応答、応答なしは、結果が確定しないものとして扱う
  - 上のどれにも当てはまらない応答も、結果が確定しないものとして扱う

  「登録なしが確定」は、クライアントが次の C1〜C3 で判断する。
  C1〜C3 をすべて満たす場合に限り、クライアントは対象の論理操作 (キー K と本文 B の組) による登録が成立していないと判断できる。
  それ以外は結果が確定しない。
  - C1: クライアントが、透過的な自動再送 (HTTP ライブラリ、Service Worker、プロキシ) を無効にしている。
    そのうえで、論理操作のすべての送信とその完了の状態を自ら管理している
  - C2: すべての送信が応答を受け取っている。完了していない送信は無い。クライアントが中断した送信は、完了していない送信に数える
  - C3: すべての応答が、API が生成した 4xx である

  「登録なしが確定」は、K で別の本文の登録が成立していないことまでは意味しない。
  特に、409 `idempotency.key_conflict` は、K で別の本文の成功がすでに確定していることを意味する。
  また、「登録なしが確定」はクライアント側の判断であり、サーバー側の結果の確定 (決定 4 の登録なしの記録、決定 13 の登録なし) とは別の事柄である。

  クライアントの規則は次のとおりとする。
  - 同じ K と同じバイト列の再送は、最初の送信から 24 時間以内に限る
  - 最初の送信から 24 時間が経過しても、その経過だけでは結果が確定しない
  - 24 時間以内に開始した送信の応答を、24 時間を過ぎた後に受け取った場合も、決定 9 の冒頭に挙げた送信ごとの意味で判断する。
    その応答が契約に適合する 201 なら、論理操作の成功が確定する。24 時間の時点で確定していなかった結果も、後から受け取った応答によって確定し得る
  - 24 時間の期限は、再送を開始してよい期限である。24 時間を過ぎた後は、新しい再送を開始しない
  - 結果の確定前にクライアントが停止した場合、停止によって結果は確定しない
  - すでに確定した結果は、24 時間の経過や停止によって未確定に戻らない。確定した結果は、クライアントの判断としての次の 2 つを指す
    - 成功の確定: 契約に適合する 201 による。後から受け取った応答 (並行していた別の送信の 503 など) によっても、未確定に戻らない
    - 登録なしの確定: C1〜C3 による。この判断は、判断の対象とした送信 (C2・C3 の「すべての送信」) についての結論である。
      判断の後に同じ K・B で始めた新しい送信は、この結論に含まれない
  - 結果が確定しない間に、同じ内容を新しいキーで送ると、登録が重複し得る (SHOULD NOT)
  - 同じ登録の意図を、新しいキーや別の本文で登録し直すことは、「登録なしが確定」の後に限って許す (新しいキーを推奨)。
    登録し直しの可否は、新しい登録の送信を開始する時点で判断する。
    その時点までに開始した、先行の論理操作のすべての送信について C1〜C3 を満たす場合に限り、登録し直しの送信を開始してよい
  - 登録なしを判断した後に、先行の論理操作の送信を追加で開始した場合は、過去の判断だけを根拠に登録し直さない。
    追加した送信も含めて、上の条件を満たしてから登録し直す
  - 先行の論理操作の成功が確定している場合は、登録し直さず、既存の成功結果を扱う
  - 登録し直しの上の条件は、クライアントの行動の条件とする。条件の成立を確かめる方法 (クライアント内部の排他制御など) は定めない。
    サーバーは、キーの異なる論理操作の間の重複を防ぐことも、条件を満たさない登録し直しを拒否することも保証しない
  - 登録結果が確定しないまま、本文やキーを変えて登録し直すことは、安全と保証しない
  - 決定 3 の冪等性は、キーごとに成り立つ。同じ登録の意図でも、キーの異なる論理操作の間の重複は、決定 3 の保証の対象外である。
    新しいキーで登録し直した後に、クライアントが先行の論理操作の新しい送信を始めると、同じ登録の意図が 2 回登録され得る。本契約は、この重複を防がない
  - 同じキー・同じ本文の再送は、最初の送信から 24 時間以内に限る規則 (この一覧の最初の規則) に従う
  - 無関係な新しい通知の登録は、独立した論理操作として、決定 1 に従い新しいキーで送る。この登録は、ここに挙げた登録し直しの制限を受けない
- 決定 10: 「同じ本文」は、リクエスト本文のバイト列が同一であることとする。
  候補を絞り込むためにハッシュを使ってよい。ただし、ハッシュの一致だけで同じと判定してはならない (MUST NOT)。
- 決定 11: v1 が扱う Content-Encoding は identity だけとする。
  - Content-Encoding ヘッダーが無い場合は identity とみなす。クライアントに identity の明示を求めない
  - identity 以外の Content-Encoding は、415 `request.unsupported_media_type` で拒否する。
    この応答には `Accept-Encoding: identity` を付ける (RFC 9110)
  - Content-Type だけが原因の 415 には、`Accept-Encoding` を付けない

回復可能性:

- 決定 12: 登録と成功の記録は、外部から見て同時に成立する (R-EP-I-004)。
- 決定 13: 回復が完了した場合、停止前に処理中だった登録処理は、次のどちらか 1 つとして観測される。片方だけが存在する状態は観測されない。
  - 成功が確定: 登録と成功の記録がどちらも存在する
  - 登録なし: どちらも存在せず、停止前のその登録処理が後から登録を成立させることもない。
    その後に同じ K・B で新しい登録処理が始まり、登録が成立することは妨げない

  この扱いは決定 4 と整合する。
- 決定 14: 回復の完了、回復の期限、回復できない場合の扱いは保証しない。
  契約上の制約として、回復できないキーは安全に再利用できない場合がある。
  そのキーへの送信には、503 が返り続け得る。
  その論理操作の結果は、確定しないまま残ることがある。

共通:

- 決定 15: キーの空間は、API インスタンス全体で共有する。認証済みの主体ごとには分けない。
  ランダムなキーは、認証や認可の代わりにならない。
- 決定 16: 登録へ進む権利 (処理権) は、所有権ではない。更新操作は、別の契約で定める。
- 決定 17: ロックの方式、処理権を得る時点、永続化の方式、回復の方式は定めず、実装に委ねる。

### Scope

- Applies to: 通知 REST API のバッチ登録の、Idempotency-Key を使う再送時の外部から観測できる振る舞い。
  バッチ登録の Content-Encoding の扱いを含む
- Consistency: 本 DR は、DR-03 決定 6 と DR-04 決定 6 を具体化する。DR-04 決定 4・決定 5 と整合する。
  DR-01〜DR-05 のどれも置き換えない。エラー応答の優先順位 (DD-ER-05) には、決定 6 の例外を 1 つ加える
- Not decided here:
  - 回復の完了、回復の期限、回復できない場合の扱い → 未定。specifications の Open Questions で扱う。
    #4・#7 との実現可能性の照合は未確認のまま残る
  - 論理操作と通知を対応付ける手段 → 未定 (Revisit Trigger に挙げた事実が現れたら DR を追加する)
  - キャンセル同士の同時実行の詳細 → 未定 (キャンセルの契約として specifications で扱う)
  - 503 の種類を区別する手段 → 未定 (必要になった時点で DR を追加する)
  - 更新操作の契約 → 未定 (更新操作を追加するときに定める)
  - ロックの方式、処理権を得る時点、永続化の方式、回復の方式 → 兄弟 issue #4・#7 (DR-03 決定 2)
  - 各規則の具体的な文言、規則 ID、エラーカタログの記載 → specifications

### Alternatives Considered

- 最初の送信の 4xx を「登録なし」とみなし、本文を修正してキーを再利用する。
  応答を失った先行の送信が後から登録され得る。また、優先順位のため、4xx はキーの状態について何も示さない。そのため不採用。
- 処理中の登録処理と別の本文が競合したときに 409 を返す。処理中のリクエストが後で失敗すると、偽の競合になるため不採用。
- 処理中の競合による 503 を、入力検証より先に返す。
  400 が何も保証しない以上、先に返す利点が無い。DD-ER-05 の例外も広がるため不採用。
- 1 回の 400 で、論理操作の「登録なし」を確定する。
  先行の送信が、まだ処理権を得る段階に達していない場合があるため不採用。
- 応答を失った送信は後から処理されない、と仮定する (改訂前の草案にあった前提)。
  通信路と中継装置は、この仮定を保証しないため不採用。
- バージョンや更新時刻による楽観ロックを使う。
  登録前にはリソースが存在せず、クライアントがバージョンを持てないため不採用。
- 先着順 (FIFO) の順序や、待機を保証する。
  外部から観測と検証のどちらもできない。実装と応答時間を制約するため不採用。
- 回復が必ず完了することを無条件に保証する。実現の条件が決まっていないため不採用。
- 結果が確定していない記録の無期限の保持を、契約にする。保存と回復の方式を固定してしまうため不採用。
- JSON として正規化して比較する。
  Unicode や数値の正規化規則を契約に含める必要が生じるため不採用。
- ハッシュ (SHA-256) の一致だけで同じ本文と判定する。衝突が起きると、別の本文の結果を返してしまうため不採用。
- キーの空間を、認証済みの主体ごとに分ける。
  #6 (ローカルセキュリティ) は、主体の識別をまだ定めていない。資格情報を再発行すると、登録が重複し得るため不採用。

### Rationale

最大の理由は、クライアントが結果を確定できない場合でも、サーバーが登録を重複させないことを優先したことにある。
この方針のもとで、冪等性を次の 3 つの性質に分けて契約にした。

- 安全性 (決定 1〜5): 保持の保証が有効な間、キーごとの登録を高々 1 つに保つ
- 応答の一貫性 (決定 6〜11): 成功が確定した後は、同じ本文の再送に初回の応答を再現する。各応答が示す意味は、時刻や他の操作によって変わらない
- 回復可能性 (決定 12〜14): 回復が完了したときに観測できる状態を限定する

3 つに分ける理由は、性質ごとに保証できる範囲が異なることにある。
安全性は、回復が完了しなくても保てる。
回復の完了は、兄弟 issue での実現の条件が決まっていないため保証しない (決定 14)。

成功の再送で元の 201 を返す理由は、再送の結果を時刻に依存する入力検証から切り離すためである (決定 6)。
これにより、過去の `fireAt` の扱いを決める Open Questions の結論が、再送の結果を左右しない。

409 を、別の本文の成功が確定した場合だけに限る理由は、409 を常に確定した競合の意味に保つためである (決定 8)。
処理中の競合を 503 にすると、その応答は後の結果と食い違わない。

「登録なしが確定」に C1〜C3 を求める理由は、1 回の応答では論理操作の結果を確定できないことにある (決定 9)。
透過的な自動再送を有効にしていると、クライアントの知らない送信が後から処理され得る。

クライアントの再送の期限を最初の送信から 24 時間とする理由は、サーバーでの成功の確定が最初の送信より遅れて起きることにある。
この期限は、クライアントが再送を開始してよい期限を表す。
成功の記録の最低保持期間は、サーバーで成功が確定した時点から数える。
サーバーで成功が確定するのは、最初の送信より後になる。
そのため、再送がサーバーでキーを照合される時点が最初の送信から 24 時間以内であれば、成功の記録は保持の保証の中にある。
ただし、再送を期限内に開始しても、キーの照合が保持の保証の期間内に行われるとは保証しない。
再送の期限を守ることだけでは、重複登録を防げない場合が残る (Consequences の Negative に挙げた、重複登録が成立し得る場合)。
24 時間という値は、草案の specifications が定めた保持期間 (R-EP-073) に合わせている。

本文の同一性をバイト列の一致とする理由は 2 つある (決定 10)。
正規化規則を契約へ持ち込まずに済む。また、ハッシュの衝突による取り違えも起きない。
Content-Encoding を identity だけにする理由は、決定 10 の比較対象のバイト列を一意に定めるためである (決定 11)。

キーの空間を共有する理由は、#6 が主体の識別をまだ定めていないことにある (決定 15)。
主体ごとに分けると、資格情報の再発行で同じ論理操作が別の空間に入り、登録が重複し得る。

ロック・永続化・回復の方式を定めない理由は、DR-03 決定 2 に従い、内部の実現方法を兄弟 issue に委ねるためである (決定 17)。

### Consequences

- Positive:
  - 保持の保証が有効な間、登録は重複しない
  - 成功の再送の結果は、時刻に依存する入力検証の影響を受けない。過去の `fireAt` の扱いを決める Open Questions を制約しない
  - 409 `idempotency.key_conflict` は、常に確定した競合を意味する
  - ロック・永続化・回復の方式を、兄弟 issue が自由に選べる
- Negative:
  - エラー応答の優先順位 (specifications-errors.md 4.1) に、例外が 1 つ必要になる (DD-ER-05)
  - クライアントは、「登録なしが確定」へ達するため、送信を自ら管理し、透過的な自動再送を無効にしなければならない
  - 論理操作の結果が、確定しないまま残る場合がある。例は次のとおり (一部)
    - 送信の応答を失い、その後に同じ本文が入力検証に通らなくなった場合
    - キーが回復できない場合
  - 決定 3 の保証が及ばない場合として、重複登録が成立し得るのは、次の 3 つがそろった場合である
    - 成功の記録について、保持の保証が終了している
    - 実際に記録が削除され、そのキーが新規の登録として処理され得る
    - その後、通信経路に残っていた元の送信 (応答を失った先行の送信など) がサーバーに到着する

    保持の保証の終了だけで、重複登録が必ず起きるわけではない。
    クライアントの再送期限 (最初の送信から 24 時間以内) は送信開始の期限であり、サーバーへの到着期限を保証しない。
  - クライアントは、503 の種類を区別できない
  - 本 DR を記録した時点の状態として、specifications と requirements.md は本 DR に合わせた改訂を要する。改訂までは、既存の記述との不整合が残る。改訂の対象は次のとおり
    - specifications-errors.md: 4.1 (入力検証より前に成功を再送する規則と、リソース状態の段で処理中の競合に 503 を返す規則の追加)、R-ER-012 の 409 の条件、R-ER-006 と R-ER-025 の Content-Encoding と Accept-Encoding、R-ER-014、R-ER-042、エラーカタログの `idempotency.key_conflict` と `server.unavailable` の注記、DD-ER-05 の例外
    - specifications-endpoints.md: 3.8.1、R-EP-072、R-EP-075、R-EP-076、R-EP-077、R-EP-078、R-EP-081、R-EP-082、DD-EP-11、201 と本文の写しの再送を記録する設計判断の追加
    - specifications-governance.md: G-16 の改訂と、回復できない未確定のキーの照合行の追加 (#4・#7 との照合は、いずれも未確認)
    - requirements.md: REQ-F-001 と AC-025 (5xx を結果が確定しないものとして扱う。specifications-index.md 7.2 #13 に対応し、改訂することは決定済み)
- Revisit Trigger:
  - 回復できない事象が実際に起きたら、本 DR を見直す
  - 結果の確定前に停止した論理操作が運用上の問題になったら、本 DR を見直す (対応付けの手段を検討する)
  - #6 が複数の主体や所有権の分離を導入したら、本 DR を見直す
  - 更新操作を追加するときは、本 DR を見直す
  - 503 の種類を区別する必要が生じたら、本 DR を見直す

## DR-07: 一覧の並びと長さの上限は実装言語によらない方法で比べ、`state` クエリの値と上限の判定を一意にする - 2026-11-14 12:00:00

**Phase**: review-harden
**Status**: Accepted

### Context

一覧の並び、長さの上限、`state` クエリの値、上限どうしの関係について、比べ方と判定の方法が契約に定まっていない。
specifications-endpoints.md v2.0.1 には、次の 4 つの未定義がある。

- R-EP-C-009 は、一覧の並びを `fireAt` の昇順、同じ `fireAt` の通知は `id` の昇順と定める。値をどう比べるかは定めていない
- 3.5 の検証制約は、長さの上限を文字数で定める。対象は `title`・`body`・`url`・通知 ID・`Idempotency-Key` の 5 つ (全件) とする。文字の数え方は定めていない
- `state` クエリについて、R-EP-C-008 は複数回の指定を許し、R-EP-C-011 は 4 つの状態名以外の値を `request.invalid` で拒否する。空の値、区切り文字、同じ値の重複、大文字の扱いは定めていない
- 3.5 は、件数・長さ・本文サイズの上限を別々に定める。3 つの上限の関係は定めていない

`fireAt` は、UTC オフセットを含む RFC 3339 の日時である (R-EP-C-014)。
そのため、同じ時刻が異なるオフセットの文字列で送られ得る。
通知 ID に使える文字は、英数字・`-`・`_` に限られる (3.5)。

複数のエラー条件が同時に成立したときの外部応答は、specifications-errors.md 4.1 の優先順位に従う (R-EP-C-001)。
4.1 では、本文サイズの超過 (Step 6、413 `request.payload_too_large`) が、検証制約への違反 (Step 10、400 `request.invalid`) より先に来る。

これらは、`/deckrd review spec --phase harden` で、specifications-endpoints.md 7 章 Open Questions #20 の方針案として承認された。
規則にはまだ反映されていない。比べ方が定まらないままだと、一覧の順序と上限の判定が実装によって変わる。

### Decision

1. 決定 1: 一覧の並びは、`fireAt` を UTC に直した時刻の昇順とする。
   時刻が同じ通知は、`id` を Unicode のコードポイントの順で比べた昇順とする。
2. 決定 2: 3.5 の長さの上限は、Unicode のコードポイントの数で判定する。
3. 決定 3: `state` クエリの値は、3.6 の 4 つの状態名のどれかと、小文字で過不足なく一致しなければならない。
   次の値は `request.invalid` で拒否する。
   - 空の値
   - 区切り文字を含む値 (`scheduled,missed` など)
   - 大文字を含む値

   同じ値を重複して指定したときは、和集合として、1 回の指定と同じに扱う。
4. 決定 4: 件数・長さ・本文サイズの上限は、それぞれ独立に判定する。
   各要素が件数と長さの上限を満たしていても、本文サイズが上限を超えれば `request.payload_too_large` で拒否する。
   複数の違反が同時に成立したときの応答は、specifications-errors.md 4.1 の優先順位に従う (R-EP-C-001)。

### Scope

- Applies to: 一覧取得の並び、`state` クエリの値の検証、バッチ登録とパスの通知 ID に対する 3.5 の長さの上限と本文サイズの上限の判定
- Not decided here:
  - `fireAt` のオフセットの保持または正規化、秒未満の精度の受け付けと保持 → specifications-endpoints.md §Open Questions #9
  - `url` に許可する形式 → specifications-endpoints.md §Open Questions #8
  - 上限の既定値そのもの (件数、本文サイズ、各長さ) → specifications-endpoints.md §Open Questions #12
  - 未知のクエリの扱い → specifications-endpoints.md §Open Questions #19
  - `title`・`body` の空白だけの値と制御文字の扱い → specifications-endpoints.md §Open Questions #27
  - 各規則の具体的な文言と規則 ID → specifications-endpoints.md (`/deckrd spec` で反映する)

### Alternatives Considered

- `fireAt` を送られた文字列のまま比べる。オフセットが異なると、同じ時刻の通知の順序が送信時のオフセットで変わるため不採用。
- 文字数を UTF-16 のコードユニット、またはバイト数で数える。
  数がサーバーの実装言語によって変わり、絵文字などでクライアントとサーバーの判定が食い違うため不採用。
- `state` クエリの値に区切り文字を許す。
  複数指定の方法が 2 つになり、R-EP-C-008 の複数回の指定と重複するため不採用。
- 何もしない (比べ方と判定の方法を契約に定めない)。比較と上限の判定が実装によって変わるため不採用。

### Rationale

最大の理由は、比べ方と判定の方法を、クライアントとサーバーの間で揃えることにある。あわせて、実装言語への依存をなくす。

`fireAt` を UTC に直して比べれば、オフセットの書き方によらず、同じ時刻は同じ位置に並ぶ (決定 1)。
`id` の比較にコードポイントの順を選んでも、追加の規則は要らない。
通知 ID の文字は英数字・`-`・`_` に限られる (3.5)。そのため、コードポイントの順とバイト列の順は一致する。

コードポイントの数は、文字列の符号化の方式を問わず 1 つに定まる (決定 2)。
UTF-16 のコードユニットで数えると、絵文字などのサロゲートペアは 2 つに数えられる。
バイト数で数えると、同じ文字でも符号化によって数が変わる。

`state` クエリの値を 4 つの状態名との完全一致に限ると、受け付ける値の集合が 1 つに定まる (決定 3)。
複数の状態の指定は、R-EP-C-008 の複数回の指定だけで表せる。

上限の独立した判定の理由は、次のことをクライアントへ知らせる点にある (決定 4)。要素の検証を通っても、送信が受け付けられるとは限らない。
1 つのコードポイントは、UTF-8 で 1〜4 バイトになり、JSON のエスケープ表記では 6 バイト以上になる。
そのため、本文のバイト数はコードポイントの数からは決まらない。
3.5 の既定値の例は次のとおり。`title` (100) と `body` (1000) の各コードポイントを、サロゲートペアのエスケープ表記 (12 バイト) で送るとする。
この場合、`title` と `body` だけで 1 要素あたり 13200 バイト、100 件で 1320000 バイトになり、1 MiB (1048576 バイト) を超える。

### Consequences

- Positive:
  - 一覧の順序が、`fireAt` のオフセットの書き方と実装言語によらず一致する
  - 長さの上限の判定が、クライアントとサーバーで一致する
  - `state` クエリで受け付ける値と拒否する値が一意に定まる
  - クライアントは、要素の検証を通っても 413 `request.payload_too_large` になり得ることを、契約から知ることができる
- Negative:
  - 空の値、区切り文字を含む値、大文字を含む値を `state` クエリに送るクライアントは、`request.invalid` で拒否される
  - クライアントは、長さの上限をコードポイントの数で数えなければならない。実装言語の標準の文字列長が UTF-16 のコードユニット数である場合は、数え方を合わせる必要がある
  - クライアントは、要素ごとの長さの検証に加えて、本文サイズを確かめなければ送信が受け付けられるかを判断できない
  - 本 DR を記録した時点で、specifications-endpoints.md v2.0.1 は本 DR に合わせた改訂を要する。改訂までは既存の記述との不整合が残る。改訂の対象は次のとおり
    - R-EP-C-009 (並びの比べ方) と R-EP-C-011 (`state` クエリの値) の改訂
    - 長さの上限をコードポイントの数で判定する規則と、上限を独立に判定する規則の追加
- Revisit Trigger:
  - 通知 ID に使える文字が英数字・`-`・`_` 以外に広がったら、`id` の比べ方を見直すために本 DR を見直す
  - `state` クエリの値に、4 つの状態名以外の書き方 (区切り文字による複数指定など) を受け付ける必要が生じたら、本 DR を見直す
  - 長さの上限を、コードポイント以外の単位 (書記素クラスタなど) で数える必要が生じたら、本 DR を見直す

## DR-08: 発火時刻を過ぎた通知は、引き渡しの結果が決まるまで `scheduled` として観測される - 2026-11-14 12:00:00

**Phase**: review-harden
**Status**: Accepted

### Context

`fireAt` を過ぎてから `dispatched` か `missed` に決まるまでの間、通知がどの状態に見えるかが契約に定まっていない。
その間のキャンセルをどう扱うかも、明記されていない。

specifications-endpoints.md v2.0.1 は、状態を次のように定める。

- 状態の集合は `scheduled`・`dispatched`・`missed`・`cancelled` の 4 つとする (DD-EP-08、R-EP-C-021)
- `scheduled` は「登録済みで、発火時刻を待っている」状態とする (3.6)
- 3.6 の遷移表は、`scheduled` から発火時刻での引き渡しの成功で `dispatched` に、失敗で `missed` に遷移すると定める (R-EP-C-023)
- 遷移表には、`fireAt` を過ぎたが引き渡しの結果がまだ決まっていない間の行が無い

キャンセルについては、次の規則がある。

- キャンセルは `scheduled` の通知だけを受け付け、ほかの状態は `notification.not_cancellable` で拒否する (R-EP-C-024)
- キャンセルと引き渡しが競合したときは、キャンセルの成功か `notification.not_cancellable` による拒否のどちらか一方に確定する (R-EP-C-025)
- キャンセルが成功した通知は、以後 OS へ引き渡されない (R-EP-I-007)

状態の追加は、既存クライアントの解釈を変えるため破壊的変更になる (DD-EP-08)。
同じ理由で、4.3 は状態の追加を将来の拡張案に含めていない。

この見え方は、`/deckrd review spec --phase harden` で、specifications-endpoints.md 7 章 Open Questions #17 の方針案として承認された。
規則にはまだ反映されていない。

### Decision

1. 決定 1: `fireAt` を過ぎた通知は、`dispatched` または `missed` に遷移するまで `scheduled` として観測される。
2. 決定 2: その間のキャンセルは R-EP-C-025 に従う。
   キャンセルの成功か、`notification.not_cancellable` による拒否のどちらか一方に確定する。

### Scope

- Applies to: `fireAt` を過ぎてから、`dispatched` または `missed` に遷移するまでの間の、通知の観測される状態とキャンセルの結果
- Consistency: 状態の集合 (DD-EP-08) と、キャンセルと引き渡しの競合の規則 (R-EP-C-025、R-EP-I-007) は変えない
- Not decided here:
  - `missed` の判定の境界 (発火時刻からどれだけ遅れたら、引き渡せなかったとみなすか) → specifications-endpoints.md §Open Questions #10
  - 発火時刻の判定に使う時計、端末のスリープ、時計の変更、プロセスの停止中に `fireAt` を過ぎた通知の状態 → specifications-endpoints.md §Open Questions #18
  - 状態の変化が一覧取得・単体取得にすぐ反映されることを保証するか → specifications-endpoints.md §Open Questions #28
  - 兄弟 issue との照合 (7 章 #7 の (d-1)・(d-2)) → specifications-governance.md の照合の記録 (DR-05)。照合は未確認のまま残る
  - 規則の具体的な文言と規則 ID、3.6 の遷移表に加える行 → specifications-endpoints.md (`/deckrd spec` で反映する)

### Alternatives Considered

- 中間の状態 (`dispatching` など) を加える。
  状態の集合が変わり、状態の追加は既存クライアントにとって破壊的変更になるため不採用 (DD-EP-08)。
- `fireAt` を過ぎた通知へのキャンセルを、すべて拒否する。
  まだ OS へ引き渡されておらず、キャンセルできる通知まで拒否することになるため不採用。
- 何もしない (その間の見え方を契約に定めない)。その間に何が観測されるかを、クライアントが予想できないため不採用。

### Rationale

最大の理由は、v1 の状態の集合を変えない点にある。そのうえで、観測される状態も、その間は 1 つに限られる。
`scheduled` のまま見せれば、状態を追加する破壊的変更を避けられる (DD-EP-08)。

その間のキャンセルに新しい規則は要らない。
キャンセルと引き渡しの競合の結果は、R-EP-C-025 がすでに 2 つのうちの一方に確定させている。
キャンセルが成功した通知を以後引き渡さないことも、R-EP-I-007 が定めている。

### Consequences

- Positive:
  - `fireAt` を過ぎた後に観測される状態が `scheduled`・`dispatched`・`missed`・`cancelled` のどれかに限られ、状態の集合が変わらない
  - その間のキャンセルの結果は、R-EP-C-025 の 2 つのうちの一方に確定する
- Negative:
  - `scheduled` の通知が発火時刻を過ぎているかは、クライアントが `fireAt` から自ら判断しなければならない
  - 本 DR を記録した時点で、specifications-endpoints.md v2.0.1 は本 DR に合わせた改訂を要する。改訂までは既存の記述との不整合が残る。改訂の対象は次のとおり
    - `fireAt` を過ぎた通知の観測される状態を定める規則の追加
    - 3.6 の遷移表への、`fireAt` を過ぎて引き渡しの結果が決まっていない `scheduled` の行の追加
- Revisit Trigger:
  - `fireAt` を過ぎた後の状態を、クライアントが `fireAt` から判断するだけでは扱えなくなったら、本 DR を見直す
  - 状態の集合を変える API メジャーバージョンを導入するときは、本 DR を見直す

## DR-09: キャンセルの応答を 3 つに分類し、結果未確定のときにクライアントが結論を出すことを禁じる - 2026-11-14 12:00:00

**Phase**: review-harden
**Status**: Accepted

### Context

キャンセルの応答には、バッチ登録のような応答の分類が契約に定まっていない。
そのため、応答を失った後の再送が拒否されたとき、最初のキャンセルの結果をクライアントが誤って判断し得る。

バッチ登録の応答は、次の 3 つの区分に分類されている (3.9、R-EP-C-037、specifications-idempotency.md R-ID-C-301)。

- 成功: 契約に適合する 201
- 失敗: API が生成した、`code` を持つ共通エラー形式の 4xx
- 結果未確定: 5xx (503 を含む)、problem 形式でないエラー応答、上のどれにも当てはまらない応答、応答なし

problem 形式でない応答は、エラー識別子を得られない場合として扱い、その応答だけでは結果を確定できない (specifications-errors.md R-ER-C-042)。

キャンセルについては、次の 2 つの場合が同じ code の拒否になる。

- キャンセルが成功した後の再送は、`notification.not_cancellable` になる (R-EP-C-026)
- `dispatched`・`missed` の通知へのキャンセルも、`notification.not_cancellable` になる (R-EP-C-024)

このため、応答を失った後の再送が `notification.not_cancellable` で拒否されても、その拒否だけでは 2 つの場合を区別できない。

単体取得による確認の条件も、2 か所で書き方が異なる。

- R-EP-C-031: キャンセルのレスポンスを受け取れなかったときは、単体取得で状態を確認して判断する (SHOULD)
- 3.8 のキャンセルの行: レスポンスを受け取れずに再送して拒否された場合に、単体取得で状態を確認して判断する

成功レスポンスの結果が、その後の一覧取得・単体取得に反映されることを契約で保証するかは、決まっていない (specifications-endpoints.md 7 章 Open Questions #28)。
R-EP-C-031 の単体取得による確認は、この反映を前提にしている。

これらの不足は、`/deckrd review spec --phase harden` で見つかった。

### Decision

1. 決定 1: キャンセルの応答は、次の 3 つに分類する。分類はバッチ登録の応答の分類 (R-EP-C-037) に揃える。
   - 成功: 契約に適合する 200
   - 拒否: API が生成した、`code` を持つ problem 形式の 4xx
   - 結果未確定: 5xx、problem 形式でないエラー応答、契約に適合しない応答、応答なし
2. 決定 2: クライアントは、結果未確定の応答から、キャンセルの成功や失敗を判断してはならない (MUST NOT)。
3. 決定 3: クライアントは、結果未確定の後の再送が `notification.not_cancellable` で拒否されたことだけを根拠に、最初のキャンセルが失敗したと判断してはならない (MUST NOT)。
4. 決定 4: 単体取得による状態の確認は SHOULD のままとし、MUST に上げない。
   確認する条件は、「キャンセルの応答が結果未確定だった場合、またはその後の再送が `notification.not_cancellable` で拒否された場合」とする。

### Scope

- Applies to: キャンセルの応答の分類と、結果未確定の応答を受け取った後のクライアントの判断
- Consistency: バッチ登録の応答の分類 (R-EP-C-037、R-ID-C-301) と、分類とクライアントの対処を分ける方針 (DR-04) に揃える。どちらも変えない
- Not decided here:
  - 単体取得による確認を MUST に上げるか → specifications-endpoints.md §Open Questions #28 (成功の結果が後の取得に反映されるかの決定に依存する)
  - キャンセルの 5xx の後に、状態が `cancelled` か変化なしのどちらかであることを、既存の規則を超えて保証するか → 未定 (必要になった時点で DR を追加する)
  - 規則の具体的な文言と規則 ID、R-EP-C-031 の条件の書き直し → specifications-endpoints.md (`/deckrd spec` で反映する)

### Alternatives Considered

- 単体取得による確認も MUST に上げる。
  確認の信頼性は、成功の結果が後の単体取得に反映されるか (7 章 Open Questions #28) に依存する。
  この事項は未決定で、兄弟 issue との照合も済んでいない (DR-05)。
  MUST に上げると、本 DR を Proposed にしなければならないため不採用。
- 規則を加えず、レビューでの指摘にとどめる。再送の拒否を最初のキャンセルの失敗と読み違える余地が残るため不採用。

### Rationale

最大の理由は、操作を問わず同じ分類で応答を扱い、クライアントの対処の操作ごとの違いをなくすためである (DR-04)。
キャンセルの分類をバッチ登録の R-EP-C-037 に揃えれば、クライアントは同じ判断の手順を両方に使える。

結果未確定の後に結論を出すことを禁じる理由は、再送の拒否だけでは最初のキャンセルの結果を区別できないことにある。
成功したキャンセルの後の再送 (R-EP-C-026) と、発火済みの通知へのキャンセル (R-EP-C-024) は、同じ `notification.not_cancellable` になる。

単体取得による確認を SHOULD にとどめる理由は、確認の信頼性を契約がまだ保証していないことにある (7 章 Open Questions #28)。
確認する条件を 1 つに定めれば、R-EP-C-031 と 3.8 の書き方の違いがなくなる。

### Consequences

- Positive:
  - キャンセルとバッチ登録の応答を、同じ 3 つの区分で扱える
  - 再送の拒否を、最初のキャンセルの失敗と読み違えることを防げる
  - 単体取得で確認する条件が 1 つに定まる
- Negative:
  - 7 章 Open Questions #28 が決まるまで、単体取得による確認の信頼性は保証されない
  - 結果未確定の後、クライアントがキャンセルの結果を確定できない場合が残る
  - 本 DR を記録した時点で、specifications-endpoints.md v2.0.1 は本 DR に合わせた改訂を要する。改訂までは既存の記述との不整合が残る。改訂の対象は次のとおり
    - キャンセルの応答の分類と、結果未確定のときの判断の禁止を定める規則の追加
    - R-EP-C-031 の単体取得による確認の条件の書き直し
- Revisit Trigger:
  - 7 章 Open Questions #28 が決まり、成功の結果が後の取得に反映されることが保証されたら、単体取得による確認を MUST に上げるかを決めるために本 DR を見直す
  - キャンセルに `Idempotency-Key` などの再送を識別する手段を加えるときは、本 DR を見直す

## DR-10: エラー応答の本文で、認証状態と実装の内部情報を開示しない - 2026-11-14 20:26:31

**Phase**: spec
**Status**: Accepted

### Context

エラー応答の本文で何を開示してはならないかについて、契約の規定が足りない。
specifications-errors.md v2.0.0 のハードニングのレビューで、次の 2 つの欠落が見つかった。

1 つ目の欠落は、認証失敗の本文での認証状態の開示に関わる。

- DD-ER-07 は、認証の失敗を、資格情報なし・形式不正・失効で区別せず、すべて `auth.unauthenticated` とする
- DD-ER-07 の理由は、区別してもクライアントの対処は増えず、認証状態の情報を開示するだけになる、というものである
- 一方で、未認証の応答で開示を禁じる規則 (R-ER-C-017、R-ER-C-056) が対象にするのは、パスの存在・メソッドの可否・リソースの状態だけである
- そのため、`code` 以外のメンバー (`title`・`detail`・拡張メンバー) で資格情報の状態を区別することは、禁じられていない
- `code` を 1 つにまとめても、本文で区別できれば DD-ER-07 の目的は達成できない

2 つ目の欠落は、エラー応答での実装の内部情報の開示に関わる。

- エラー応答に載せてはならない内部情報の規定が、契約にない
- RFC 9457 のセキュリティ上の考慮事項は、`detail` などに実装の内部情報が混入する危険を示している
- `server.internal` (500) と `server.unavailable` (503) の応答が、特に該当する

### Decision

1. 決定 1: 401 `auth.unauthenticated` の応答本文は、資格情報の欠落・形式の不正・失効のどれに当たるかを区別できる内容を含まない。
   対象は、`title`・`detail`・拡張メンバーのすべてとする。
2. 決定 2: API が生成するエラー応答は、どのメンバーにも実装の内部情報を含まない。
   内部情報の例は、スタックトレース、内部のファイルパス、データストアのクエリや識別子、使用しているライブラリの名称やバージョンである (一部の例示)。
3. 決定 3: `WWW-Authenticate` ヘッダーの内容は、決定 1 の対象にしない。
   チャレンジの内容は、認証方式の確定まで確定しないため (R-ER-C-053)。

決定 1 と決定 2 は、specifications-errors.md に契約の規則 (R-ER-C-060、R-ER-C-061) として追加する。
どちらの決定も、応答の内容に対する制約であり、開示を防ぐ実現方法は定めない。

### Scope

- Applies to:
  - 決定 1: 401 `auth.unauthenticated` の応答本文
  - 決定 2: API が生成するすべてのエラー応答の、すべてのメンバー
- Not decided here:
  - 規則の文言と、禁じる内部情報の具体的な書き方 → specifications-errors.md (R-ER-C-060、R-ER-C-061)
  - `WWW-Authenticate` のチャレンジの内容と、そこで資格情報の状態を区別するかどうか → specifications-errors.md (R-ER-C-053。#6 との照合後に確定する。R-ER-C-057)
  - 開示を防ぐ実現方法 (診断用の詳細をどこに記録するかを含む) → 実装 (DR-03 決定 2)
  - API が生成しない応答 (プロトコルレベルのエラー、プロキシなどが生成する応答) の内容 → 本 DR の対象外 (R-ER-C-016)

### Alternatives Considered

- DD-ER-07 だけで足りるとして、規則を追加しない。
  `code` が同じでも本文で資格情報の状態を区別でき、DD-ER-07 の目的を達成できないため不採用。
- `detail` を、すべての `code` で固定の文言にする。
  診断に使える情報まで失う。たとえば `request.invalid` の違反の内容は、`detail` の文面だけで伝える (R-ER-X-001)。そのため不採用。
- 開示の制限を実装の判断に委ね、契約には置かない。
  応答の内容はクライアントから観測できる。外部から観測できる振る舞いは契約に含めるため (DR-03 決定 1)、不採用。

### Rationale

開示の制限を契約の規則にする最大の理由は、DD-ER-07 の意図を `code` だけでなく応答本文まで一貫させることにある。
`code` を 1 つにまとめても、本文の他のメンバーで区別できれば、認証状態の情報は開示される。
決定 1 は、DD-ER-07 の意図を本文に延ばす最小の追加であり、新しい条件を加えない。

内部情報の禁止を契約に置く理由は、エラー応答の内容がクライアントから観測できることにある。
DR-03 決定 1 は、外部から観測できる振る舞いを契約に含めると決めている。
一方で DR-03 決定 2 に従い、開示を防ぐ実現方法は定めない。
開示の制限は観測できる応答の内容に対する制約であり、内部の実現方法を拘束しない。

`WWW-Authenticate` を対象から外す理由は、チャレンジの内容が認証方式の確定まで確定しないことにある (R-ER-C-053)。
内容が未確定のまま規則を置くと、方式を確定するときに規則と食い違うおそれがある。

### Consequences

- Positive:
  - 認証状態と実装の内部情報が応答に含まれないことを、契約への適合として検証できる
  - 401 の応答は、`code` と本文のどちらからも資格情報の状態を区別できなくなり、DD-ER-07 の目的が本文まで及ぶ
- Negative:
  - 実装者は、診断用の詳細を、サーバー側のログなど応答の外に置く必要がある
  - `WWW-Authenticate` の内容は、認証方式の確定まで、決定 1 の対象外のまま残る
- Revisit Trigger:
  - 認証方式が確定し、`WWW-Authenticate` のチャレンジの内容が決まったら、資格情報の状態の区別を決定 1 の対象に含めるかを見直すために本 DR を見直す
  - クライアントが資格情報の状態ごとに異なる対処を必要とするようになったら、DD-ER-07 とあわせて本 DR を見直す

## DR-11: `dispatched` の条件は OS の通知 API の呼び出しの正常終了とアプリケーション単位の通知可否の確認とし、OS の受理・表示と `missed` の遅れの上限は保証しない - 2026-11-15 12:29:36

**Phase**: spec
**Status**: Superseded by DR-12

### Context

通知が `dispatched` に遷移する外部の条件が、契約に定まっていない。
`missed` と判定する基準も、契約に定まっていない。
同じ事象でも、実装や OS によって `dispatched` と `missed` の観測が分かれ得る。

specifications-endpoints.md v2.2.2 は、状態を次のように定める。

- 状態の集合は `scheduled`・`dispatched`・`missed`・`cancelled` の 4 つとする (DD-EP-08、R-EP-C-021)
- `dispatched`・`missed`・`cancelled` は終端状態であり、別の状態へ遷移しない (R-EP-C-021)
- `dispatched` は、発火時刻に OS へ通知を引き渡したことだけを意味する。画面への表示と利用者の確認は、意味に含めない (DD-EP-08、R-EP-C-022)
- `missed` は、発火時刻に OS へ通知を引き渡せなかった状態とする (3.6)
- 3.6 の遷移表は、引き渡しに成功すると `dispatched` に遷移すると定める。引き渡しに失敗すると `missed` に遷移すると定める (R-EP-C-023)
- `fireAt` を過ぎた通知は、`dispatched` または `missed` に遷移するまで `scheduled` として観測される (R-EP-C-042、DR-08)

「引き渡し」の成功を何で判断するかは、決まっていない。
specifications-endpoints.md 7 章 Open Questions #10 は、`dispatched` の条件の候補として、意味の異なる次の 4 つを挙げている (全件)。

1. OS の通知 API の呼び出しが、例外やエラーを返さない
2. OS が通知の要求を受理する
3. OS が通知を表示する
4. 利用者が通知を確認する

このうち 3 と 4 は、DD-EP-08 と R-EP-C-022 によって `dispatched` の意味から外れている。
同じ #10 は、`missed` と判定する遅れの境界を契約で保証するかも問うている。
DR-08 は、この境界を #10 に委ねている。

契約は、Windows と Android を対象の OS にしている。
両 OS の通知 API の公式ドキュメント (Microsoft Learn と Android Developers) を、2026-11-15 に確認した。
本 DR に関わる事実は次のとおりとする (確認結果の一部)。
出典の URL は `### Related` に挙げる。

- 呼び出しの戻り値: Windows の `Show` と Android の `notify` は、どちらも戻り値を返さない
- 正常終了の意味: どちらの OS の文書も、呼び出しの正常な戻りが OS の受理や表示を保証するとは書いていない
- 通知が無効なときの呼び出し: どちらの OS も、呼び出しが同期的に例外やエラーを返すとは書いていない
- Windows の非同期の失敗: UWP では、表示の失敗が `Show` の後に `Failed` イベントで知らされる。最も多い原因は、設定によるブロックである。Windows App SDK には、これに当たるイベントが無い
- OS の受理の観測: Windows には、受理を知らせるイベントが無い。Android の `getActiveNotifications()` は投稿済みの通知を列挙するが、一覧に現れる時期は書かれていない
- アプリケーション単位の通知可否: Windows は `Setting` で、アプリケーション・ユーザー・グループポリシー・マニフェストによるブロックを確かめられる。Android は `areNotificationsEnabled()` で、アプリケーション単位の可否を確かめられる
- それ以外の通知可否: Android のチャネルの無効・一時停止・おやすみモードは、別の API で確かめる。Windows にはこれらに当たる確認の手段が無い。Windows の集中モードは、`Setting` に反映されるかが書かれていない
- 確認と呼び出しの間の変化: どちらの OS も、可否を確かめてから呼び出すまでの間に状態が変わったときの扱いを書いていない

状態の意味と `missed` の検出と保持は、specifications-governance.md G-04 の保証にあたる。
この保証の兄弟 issue との照合 (照合 (d-1)) は、未確認のまま残っている (DR-05)。

### Decision

1. 決定 1: `dispatched` の条件を、次の 4 つの観点で定める。
   - (a) 呼び出しの正常終了: 発火時刻に OS の通知 API を呼び出し、その呼び出しが例外やエラーを返さずに戻ることを、必要条件とする。
     呼び出しの正常終了は、OS の受理と同じ意味として扱わない。
   - (b) OS 側の通知可否: 呼び出しの直前に、OS のアプリケーション単位の通知可否の確認が「有効」を返したことを、必要条件とする。
     条件にする通知可否は、Windows と Android の両方で確かめられるアプリケーション単位の可否に限る。
   - (c) OS の受理: 保証しない。
   - (d) 表示と利用者の確認: 保証しない (DD-EP-08、R-EP-C-022)。

   (a) と (b) をともに満たした通知は `dispatched` に遷移する。
2. 決定 2: 発火時刻の引き渡しの試みの結果を、次の 5 つの場合に分ける。
   - A 呼び出しの正常終了: (a) と (b) を満たしていれば `dispatched` に遷移し、`missed` にはならない
   - B 呼び出しの失敗: 呼び出しが同期的に例外やエラーを返した場合は、`missed` に遷移する
   - C 通知の無効: 呼び出しの直前の通知可否の確認が「無効」を返した場合は、`missed` に遷移する。このとき、OS の通知 API を呼び出す必要は無い
   - D 呼び出しの不実施: プロセスの停止やスリープなどで発火時刻に呼び出しが行われなかった場合の状態は、本 DR では決めない。specifications-endpoints.md §Open Questions #18 で決める
   - E 呼び出しの結果の確認不能: 本 DR では決めない (Open Questions 3)

   場合 A〜C は、決定 1 の条件に従う。
3. 決定 3: 発火時刻からの遅れの上限は、`missed` の判定の境界として契約で保証しない。
4. 決定 4: 契約にする条件は、Windows と Android の両方で共通に観測できるものだけとする。
   OS ごとの判定の方法 (呼び出しの成否と、通知可否を確かめる手段) は契約に定めない。

呼び出しが例外やエラーを返さないことは、通知が無効な場合を検出する手段として扱わない。
理由は、通知が無効な場合の同期的なエラーを、両 OS とも書いていないことにある。

### Scope

- Applies to: 発火時刻に行う OS への引き渡しの試みの結果として、通知が `dispatched` または `missed` に遷移する外部の条件
- Consistency: 状態の集合と `dispatched` の意味 (DD-EP-08、R-EP-C-021、R-EP-C-022) と、`fireAt` を過ぎた通知の観測される状態 (DR-08) は変えない
- Not decided here:
  - 発火時刻に呼び出しが行われなかった通知の状態 (決定 2 の場合 D) と、発火時刻の判定に使う時計 → specifications-endpoints.md §Open Questions #18
  - 呼び出しの結果を確かめられなかった通知の状態 (決定 2 の場合 E) → 未定 (本 DR の Open Questions 3)
  - 通知可否の確認と呼び出しの間に状態が変わった場合の扱い → 未定 (本 DR の Open Questions 1)
  - Windows (UWP) の非同期の失敗を契約で扱うか → 未定 (本 DR の Open Questions 2)
  - Windows App SDK の `AppNotificationSetting` が `Unsupported` を返したときの扱い → 未定 (本 DR の Open Questions 5)
  - OS ごとの判定の方法 (どの API で呼び出しの成否と通知可否を確かめるか) → implementation (DR-03 決定 2)
  - 規則の具体的な文言と規則 ID、3.6 の `dispatched`・`missed` の意味の書き直し → specifications-endpoints.md (`/deckrd spec` で反映する)
  - 状態の変化が一覧取得・単体取得に反映される時期 → specifications-endpoints.md §Open Questions #28
  - 兄弟 issue との照合 (照合 (d-1)) → specifications-governance.md の照合の記録 (DR-05)

### Alternatives Considered

- `dispatched` の条件を、呼び出しの正常終了だけにする (通知が無効でも `dispatched` とする)。
  通知が無効なら、Keneek は OS へ通知を引き渡したと主張できない。
  OS に届いていないと分かっている事実を、状態が主張してしまうため不採用。
- `dispatched` の条件を、OS が通知の要求を受理したこととする。
  Windows には受理を知らせるイベントが無い。
  Android の `getActiveNotifications()` も、一覧に現れる時期が書かれていない。
  両 OS で受理を観測する手段が無いため不採用。
- 通知可否の条件に、Android のチャネルの無効・一時停止・おやすみモードや Windows の集中モードを含める。
  Windows と Android の両方で確かめられる手段が無いため不採用 (決定 4)。
- `missed` と判定する遅れの上限を契約で定める。
  Windows と Android の両方で成り立つ 1 つの値を選ぶ根拠が無いため不採用。
- OS ごとに `dispatched` の条件を契約に書く。
  同じ事象の状態が端末によって異なり、契約が端末に依存するため不採用。

### Rationale

決定 1 の最大の理由は、(a) と (b) だけが、両 OS の公式ドキュメントで共通して確かめられる条件であることにある。
(a) を OS の受理と区別する理由は、両 OS とも、正常終了が受理や表示を保証すると書いていないことにある。
(b) を加える理由は、通知が無効なときに呼び出しがエラーを返すとは、どちらの OS にも書かれていないことにある。
(a) だけでは、OS に届かないと分かっている通知を `dispatched` と見せてしまう。
(b) をアプリケーション単位の可否に限る理由は、それより細かい可否を確かめる手段を Windows が持たないことにある。
表示と利用者の確認を保証しないことは、DD-EP-08 と R-EP-C-022 ですでに決まっている。

決定 2 で場合を分ける目的は、各場合で `dispatched` と `missed` のどちらへ決まるかを読み取れることにある。
場合 D と場合 E は、既存の契約で状態が決まらない。
R-EP-C-042 は、遷移するまで `scheduled` として観測されることだけを定め、どちらに遷移するかは定めていない。

決定 3 の理由は、両 OS で共通に成り立つ遅れの値の根拠が無いことにある。

決定 4 の理由は、次の点にある。OS ごとに条件を変えると、同じ事象の状態が端末によって異なり、契約が端末に依存する。
判定の方法は内部の実現方法にあたるため、DR-03 決定 2 に従い implementation に委ねる。

### Consequences

- Positive:
  - 同じ引き渡しの試みは、OS によらず同じ条件で `dispatched` か `missed` に決まる (場合 A〜C)
  - アプリケーション単位で通知が無効だと分かっている通知が、`dispatched` として観測されない
  - OS ごとの判定の方法を、契約を変えずに implementation で選べる
- Negative:
  - `dispatched` は、OS の受理と表示のどちらも保証しない
  - Android のチャネルの無効・一時停止・おやすみモードや Windows の集中モードで表示されない通知も、`dispatched` になり得る
  - 通知可否の確認と呼び出しの間に通知が無効になった場合、表示されない通知が `dispatched` になり得る
  - Windows (UWP) で `dispatched` の後に `Failed` イベントが発生しても、`dispatched` は終端状態のため状態は変わらない (R-EP-C-021)
  - `missed` の判定に遅れの上限が無いため、クライアントは発火時刻からどれだけ遅れたら `missed` になるかを契約から知ることができない
  - 場合 D と場合 E の状態は、本 DR では決まらない
  - 本 DR を記録した時点で、specifications-endpoints.md v2.2.2 は本 DR に合わせた改訂を要する。改訂の対象は次のとおり
    - 3.6 の `dispatched`・`missed` の意味
    - R-EP-C-022 と、7 章 Open Questions #10
- Revisit Trigger:
  - Windows または Android の公式ドキュメントが、呼び出しの正常終了の意味、または通知が無効なときの呼び出しの振る舞いを定めたら、本 DR を見直す
  - 両 OS で OS の受理を観測できる手段が公式に示されたら、本 DR を見直す
  - Windows でアプリケーション単位より細かい通知可否を確かめる手段が公式に示されたら、本 DR を見直す
  - 照合 (d-1) で、issue #5 または issue #7 の責務と矛盾が見つかったら、本 DR を見直す
  - Windows と Android 以外の OS を契約の対象に加えるときは、本 DR を見直す

### Open Questions

1. 通知可否を確かめてから呼び出すまでの間に状態が変わった場合を、契約でどう扱うか。両 OS とも、この間の扱いを公式ドキュメントに書いていない。
2. Windows (UWP) の `Failed` イベントのように、呼び出しの後から非同期で知らされる失敗を、契約で扱うか。`dispatched` は終端状態であり (R-EP-C-021)、後から状態を変えられない。
3. 呼び出しの結果を確かめられなかった通知 (決定 2 の場合 E。呼び出しから結果の記録までの間に停止した場合など) を、どちらの状態にするか。R-EP-C-042 は、遷移するまで `scheduled` として観測されることだけを定めている。
4. 照合 (d-1) (specifications-governance.md G-04、issue #5・issue #7) が未確認のまま残っている (DR-05)。
5. Windows App SDK の `AppNotificationSetting` が `Unsupported` を返したときを、どう扱うか。決定 1 の (b) は「有効」と「無効」だけを扱っている。本 DR を置き換える Accepted の DR の前に決める。

上の事項が決まった後、本 DR を置き換える Accepted の DR を追加する。

## DR-12: `dispatched` は事前の通知可否が「有効」で呼び出しが正常終了した通知と判定し、`missed` は成功を確認できないまま引き渡し処理を終了した状態とする - 2026-11-15 13:57:58

**Phase**: spec
**Status**: Accepted
**Supersedes**: DR-11（全体）

### Context

DR-11 (Proposed) は、`dispatched` と `missed` の外部の条件を決めた。
しかし、Open Questions が残っているため、DR-11 は Accepted にできない。
Open Questions を決めると、`missed` の意味は改訂前の定義のままでは合わなくなる。

DR-11 の決定 (全件) と Open Questions (全件) を、本 DR では次のように扱う。

specifications-endpoints.md v2.2.2 は、状態を次のように定める (本 DR に関わる部分)。

- 状態の集合は `scheduled`・`dispatched`・`missed`・`cancelled` の 4 つとする (DD-EP-08、R-EP-C-021)
- `dispatched`・`missed`・`cancelled` は終端状態であり、別の状態へ遷移しない (R-EP-C-021)
- `dispatched` は、発火時刻に OS へ通知を引き渡したことだけを意味する (R-EP-C-022)
- 画面への表示と利用者の確認は、`dispatched` の意味に含めない (DD-EP-08、R-EP-C-022)
- `missed` は、発火時刻に OS へ通知を引き渡せなかった状態とする (3.6)
- 3.6 の遷移表は、発火時刻での引き渡しに成功すると `dispatched` に遷移すると定める (R-EP-C-023)
- 同じ遷移表は、発火時刻での引き渡しに失敗すると `missed` に遷移すると定める (R-EP-C-023)
- `fireAt` を過ぎた通知は、`dispatched` または `missed` に遷移するまで `scheduled` として観測される (R-EP-C-042、DR-08)
- 7 章 Open Questions #10 は、`dispatched` の外部の条件と、`missed` と判定する遅れの境界を問うている

universal-dictionary.md v1.1.2 は、次のように定義する。

- UD-NST-003 `dispatched`: 発火時刻に Keneek が OS へ通知を引き渡したことを表す
- UD-NST-004 `missed`: 発火時刻に OS へ通知を引き渡せなかったことを表す

両 OS の通知 API の公式ドキュメント (Microsoft Learn と Android Developers) を、2026-11-15 に確認した。
本 DR に関わる事実は次のとおりとする (確認結果の一部)。
出典の URL は `### Related` に挙げる。

- Windows の `Show` と Android の `notify` は、どちらも戻り値を返さない
- 呼び出しの正常な戻りが OS の受理や表示を保証するとは、どちらの OS の文書も書いていない
- 通知が無効なときに呼び出しが同期的に例外やエラーを返すとは、どちらの OS も書いていない
- 通知可否の確認と呼び出しを不可分に行う API は、どちらの OS にも無い
- 通知可否の確認の結果は、確認した時点の値である
- 確認してから呼び出すまでの間に状態が変わったときの扱いは、どちらの OS も書いていない
- Windows UWP の `ToastNotification.Failed` は、通知を出すときに生じたエラーを知らせる
- `Failed` が `Show` に対していつ発生するかは書かれていない
- `Failed` がすべての失敗で発生するかは書かれていない
- `Failed` を購読できるのは、動作中のアプリケーションに限られる
- Windows App SDK の `AppNotificationManager` には、`Failed` に当たるイベントが無い
- Android では、`notify` の後に投稿の失敗を通常のアプリケーションへ知らせるコールバックは、確認した範囲では書かれていない
- Windows App SDK の `AppNotificationSetting` は、有効と 4 種類の無効のほかに `Unsupported` を返し得る
- `Unsupported` の意味と、返る条件は書かれていない
- Android の `areNotificationsEnabled()` には、判定できない場合の記載が無い
- Windows App SDK のクイックスタートは、管理者権限で動くアプリケーションでは `Show` が黙って失敗し、通知は表示されないと書いている

OS への通知の引き渡しと、通知の状態の記録は、別々の処理として行われる。
そのため、引き渡し処理を始めた後、終端状態が確定する前にプロセスが停止し得る。
停止は、OS の通知 API を呼び出した後にも、呼び出す前にも起こり得る。
呼び出した後に停止した場合、通知が OS に届いた可能性がある。
その場合でも、状態は確定していない。
DR-11 の場合 E は、呼び出した後の停止だけを指している。
呼び出す前の停止をどの場合に含めるかは、DR-11 では決まっていない。

再開後に停止した通知を扱うには、その通知の引き渡し処理を始めていたかを識別できなければならない。
識別できなければ、引き渡し処理を始めていた通知を、始めていない通知 (場合 D) と取り違える。
場合 D の扱いは、specifications-endpoints.md §Open Questions #18 でまだ決まっていない。
§Open Questions #18 が場合 D を遅れて引き渡すと決めた場合、取り違えた通知は再び引き渡され、通知が重複し得る。
引き渡し処理の開始の記録が、再開の後で復元できる状態となるまで、通知可否の確認と OS の通知 API の呼び出しを始めなければ、この取り違えを防げる。
この記録は、永続化 (issue #7) の責務に関わる。

状態の意味と `missed` の検出と保持は、specifications-governance.md G-04 の保証にあたる。
G-04 の照合対象には、照会・キャンセル (issue #5) と永続化 (issue #7) が含まれる。
どちらの照合結果も「未確認」である (DR-05)。

### Decision

1. 決定 1: 次の 2 つをともに確認した通知は、`dispatched` と判定する。
   終端状態の確定は決定 6 による。
   - (i) この引き渡しの試みに対応するアプリケーション単位の通知可否の確認を、OS の通知 API の呼び出しより前に行い、その結果が「有効」だったこと
   - (ii) OS の通知 API の呼び出しが、例外やエラーを返さずに正常終了したこと

   次の 4 つは保証しない。
   - OS の受理
   - 表示の成功
   - 利用者の確認
   - 呼び出した時点でも通知可否が「有効」だったこと

   確認から呼び出しまでの時間の上限は定めない。
   確認の後の設定の変更によって、呼び出しが同期的に例外やエラーを返した場合は、決定 5 の場合 B に従う。
2. 決定 2: 呼び出しの後から非同期に知らされる失敗 (Windows UWP の `ToastNotification.Failed` など) によって、`dispatched` を `missed` へ変えない。
   `dispatched` の判定は、決定 1 の 2 つの条件だけで行う。
   判定は、失敗のイベントの到着の順序に左右されない。
   失敗のイベントが状態の記録より先に届いた場合も、同じとする。
   失敗のイベントの監視は、API 契約の義務にしない。
   監視するかどうかと監視の方法は、implementation に委ねる。
3. 決定 3: `missed` は、OS への通知要求について、成功を確認できないまま引き渡し処理を終了した状態を表す。
   `missed` は、OS へ通知が届かなかったことを意味しない。
4. 決定 4: アプリケーション単位の通知可否の確認結果を、「有効」「無効」「判定不能」の 3 つに分ける。
   判定不能は、確認の結果から有効か無効かを決められない場合 (Windows App SDK の `AppNotificationSetting` の `Unsupported` など) を指す。
5. 決定 5: 引き渡しの試みを次の 6 つの場合に分け、それぞれの終端状態と、確定の根拠が揃う時点を次の表のとおりとする。

   | 場合                   | 内容                                                         | 確定の根拠が揃う時点                                                    | 状態               |
   | ---------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------- | ------------------ |
   | A 呼び出しの正常終了   | 決定 1 の (i) と (ii) を満たす                               | 呼び出しの正常終了を確認した時点 (事前の確認の結果は「有効」)           | `dispatched`       |
   | B 呼び出しの失敗       | 「有効」の確認の後の呼び出しが、同期的に例外やエラーを返した | 呼び出しの失敗を確認した時点                                            | `missed`           |
   | C 通知の無効           | 事前の通知可否の確認が「無効」だった                         | 「無効」の確認に基づいて、呼び出さないと確定した時点                    | `missed`           |
   | F 通知可否の判定不能   | 事前の通知可否の確認が「判定不能」だった                     | 「判定不能」の確認に基づいて、呼び出さないと確定した時点                | `missed`           |
   | E 確定前の停止         | 引き渡し処理の開始の後、終端状態の確定の前に停止した         | 再開後、その通知の OS の通知 API の呼び出しを再実行しないと確定した時点 | `missed`           |
   | D 引き渡し処理の未開始 | 引き渡し処理を開始していない (プロセスの停止やスリープなど)  | 本 DR では決めない (specifications-endpoints.md §Open Questions #18)    | 本 DR では決めない |

   表の時点で根拠が揃った後、終端状態は決定 6 の定義を満たしたときに確定する。
   場合 E は、OS の通知 API を呼び出したかどうかによらない。
   場合 E には、場合 C または場合 F の判定の後、終端状態が確定する前に停止した通知も含む。
   終端状態がすでに確定した通知は、回復の後もその終端状態を保ち、場合 E として扱い直さない。
   場合 E の通知は、再開後に OS の通知 API を呼び出し直さない。
   場合 E で終端状態を確定できなかったことは、OS への引き渡しが失敗した証拠として扱わない。
   引き渡し処理の終了までの時間の上限 (発火時刻からの遅れの上限を含む) は、契約で保証しない。

   再開後の場合 D と場合 E の区別は、有効な開始の記録があるかどうかで行う。
   区別は、永続化の完了の通知には依らない。
   - 有効な開始の記録がある通知は、場合 E とする
   - 有効な開始の記録が無い通知は、場合 D とする
   - 開始の記録は、通知可否の確認より前の時点で復元できる状態となる
   - そのため、場合 C または場合 F の判定の後で停止した通知も、再開後に場合 E として扱える
   - 記録の破損などで区別できなくなった場合は、永続化 (issue #7) の回復の方法で解決する

   次の性質を、外部の契約の不変条件として保証する。
   - 保証する性質: 再開後、引き渡し処理を開始していた通知 (場合 E) を、開始していない通知 (場合 D) と取り違えない
   - 満たすべき条件: その引き渡し処理の開始の記録が、再開の後で復元できる状態となるまで、通知可否の確認と OS の通知 API の呼び出しを始めないこと
   - 記録の方法は契約に定めず、永続化 (issue #7) の implementation に委ねる (DR-03 決定 2)
6. 決定 6: 結果の確認と、終端状態の確定を区別する。
   - 結果の確認は、引き渡しの試みで、呼び出しの結果や通知可否の確認の結果を得ることを指す
   - 終端状態の確定は、その結果に基づいて通知の状態が `dispatched` か `missed` に決まり、再開後にその状態を一意に復元できるようになったことを指す
   - 再開後に一意に復元できることを、確定の保証条件とする
   - この条件を満たした状態は、停止の後の回復でも保たれる

   引き渡し処理を開始した後、終端状態を確定する前にプロセスが停止した場合は、再開後に場合 E として扱う。
   結果を確認したかどうかは、この扱いに影響しない。
   結果を確認した後の停止 (場合 A・B・C・F の結果を得た後の停止) も、場合 E に含む。
   その通知は、呼び出し直さず `missed` に確定する。
   終端状態が確定するまで、通知は `scheduled` として観測される (R-EP-C-042、DR-08)。
   確定した状態が一覧取得・単体取得に反映される時期は、本 DR では保証しない。
   本 DR は、書き込みの後の読み取りの一貫性 (read-after-write) を新たに保証しない。
7. 決定 7: 契約にする条件は、Windows と Android の両方で観測できるものだけとする。
   OS ごとの判定の方法 (呼び出しの成否、通知可否、停止の検出を確かめる手段) は契約に定めず、implementation に委ねる (DR-03 決定 2)。

### Scope

- Applies to: 発火時刻の引き渡しの試みの結果として、通知を `dispatched` または `missed` と判定する外部の条件、確定の根拠が揃う時点、終端状態の確定の定義、`dispatched` と `missed` の意味
- Consistency: 次のものは変えない
  - 状態の集合 (DD-EP-08、R-EP-C-021)
  - 画面への表示と利用者の確認を `dispatched` の意味に含めないこと (DD-EP-08、R-EP-C-022)
  - 終端状態が別の状態へ遷移しないこと (R-EP-C-021)
  - `fireAt` を過ぎた通知が、遷移するまで `scheduled` として観測されること (R-EP-C-042、DR-08)
  - DR-08 は置き換えない
- Not decided here:
  - 引き渡し処理を開始していない通知の状態 (決定 5 の場合 D) と、発火時刻の判定に使う時計 → specifications-endpoints.md §Open Questions #18
  - 確定した状態が一覧取得・単体取得に反映される時期 → specifications-endpoints.md §Open Questions #28
  - OS ごとの判定の方法 (どの API で呼び出しの成否と通知可否を確かめるか、非同期の失敗のイベントを監視するか) → implementation (DR-03 決定 2)
  - 引き渡し処理の開始の記録と終端状態を、再開後に復元できる形で残す方法 → 永続化 (issue #7) の implementation
  - 記録の破損などで、再開後に場合 D と場合 E を区別できなくなった場合の扱い → 永続化 (issue #7) の回復の方法 (実現性は specifications-governance.md G-04 の照合で確かめる。DR-05)
  - 次の 2 つの条件を実現できるか → specifications-governance.md G-04 の照合で、実現性の照合の事項として確かめる (DR-05)
    - 開始の記録の条件 (決定 5): 開始の記録が、再開の後で復元できる状態となるまで、通知可否の確認と OS の通知 API の呼び出しを始めないこと
    - 一意の復元の条件 (決定 6): 確定した終端状態を、再開後に一意に復元できること
  - 照合 (d-1) (specifications-governance.md G-04、issue #5・issue #7) → specifications-governance.md の照合の記録 (DR-05)
  - 規則の具体的な文言と規則 ID → specifications-endpoints.md (本 DR とは別の変更)
  - R-EP-C-022 と 3.6 の `dispatched`・`missed` の意味と遷移表の書き直し、UD-NST-003・UD-NST-004 の定義の改訂 → specifications-endpoints.md と universal-dictionary.md (本 DR とは別の変更として、同じ変更単位で整合させる)
- Relation to DR-05: 本 DR では次の 3 つを区別する
  - 照合待ちの規則の有効性: 照合待ちの規則も有効であり、拘束力を持つ。この扱いは specifications-endpoints.md 4 章の冒頭が定めており、DR-05 が定めたものではない
  - 本 DR の採用: 照合 (d-1) の完了は、本 DR を Accepted とする条件ではない
  - API 契約全体の確定: DR-05 決定 6 のとおり、照合結果に「未確認」が残っておらず、未解決の矛盾も無いことを条件とする
  - 本 DR は、API 契約全体の確定の条件を免除しない

### Alternatives Considered

判定不能 (決定 4・決定 5 の場合 F) の扱い:

- 案 A: 通知 API の呼び出しを試み、その結果に従う。
  判定不能のときだけ決定 1 (i) の必要条件を外すことになる。
  管理者権限のアプリケーションのように黙って失敗する場合でも `dispatched` になり得るため不採用。
- 案 C: 判定できるまで `scheduled` のままにする。
  判定不能が続くと状態が決まらない。
  遅れの上限も保証しないため、クライアントが結果を知る手段が無い。
  §Open Questions #18・#28 の判断にも依存するため不採用。

場合 E の扱い:

- E2: `dispatched` にする。
  呼び出しの正常終了を確かめておらず、根拠なしに引き渡しを主張するため不採用。
- E3: 再開後に呼び出し直す。
  停止の前に呼び出していて通知が OS に届いていた場合に、利用者に同じ通知が 2 回出るため不採用。
- E4: `scheduled` のままにする。
  状態が決まらないまま残り、遅れの上限も無いため不採用 (判定不能の案 C と同じ理由)。

確認と呼び出しの間の変化 (DR-11 Open Questions 1) の扱い:

- 案 B: 呼び出しの後にも通知可否を確かめる (再確認)。
  呼び出しと再確認の間に同じ競合が残り、競合を解消できない。
  再確認が「無効」を返しても、呼び出した時点で無効だったとは言えず、表示された通知を `missed` にし得る。
  再確認が判定不能を返した場合の扱いも新たに要るため不採用。
- 案 C: 呼び出した時点の通知可否を保証できなければ `missed` にする。
  呼び出した時点の可否を保証する手段は、どちらの OS にも無い。
  文字どおりに適用すると、すべての通知を `missed` にするか、実質的に決定 1 と同じ運用になる。
  外部の契約として成り立たないため不採用。

呼び出しの後から知らされる失敗 (DR-11 Open Questions 2) の扱い:

- 案 B: 後から失敗が知らされたら、`dispatched` から `missed` に遷移させる。
  終端状態の不変性 (R-EP-C-021) を破り、`dispatched` を暫定の状態にする。
  失敗のイベントは Windows UWP にしか無く、イベントがある OS だけで状態の意味が変わるため不採用。
- 案 C: 失敗を後から知らされる可能性が消えるまで、`scheduled` のままにする。
  失敗の可能性の無くなる時期は公式に書かれておらず、`scheduled` から抜ける条件を決められない。
  期限を設けると、根拠の無い値を契約へ入れることとなるため不採用。

DR-11 から引き継ぐ不採用の案:

- `dispatched` の条件を、呼び出しの正常終了だけにする (通知が無効でも `dispatched` とする)。
  OS に届いていないと分かっている事実を、状態が主張してしまうため不採用。
- `dispatched` の条件を、OS が通知の要求を受理したこととする。
  Windows には受理を知らせるイベントが無い。
  Android の `getActiveNotifications()` も、一覧に現れる時期が書かれていない。
  両 OS で受理を観測する手段が無いため不採用。
- 通知可否の条件に、Android のチャネルの無効・一時停止・おやすみモードや Windows の集中モードを含める。
  Windows と Android の両方で確かめられる手段が無いため不採用 (決定 7)。
- `missed` と判定する遅れの上限を契約で定める。
  Windows と Android の両方で成り立つ 1 つの値を選ぶ根拠が無いため不採用。
- OS ごとに `dispatched` の条件を契約に書く。
  同じ事象の状態が端末によって異なり、契約が端末に依存するため不採用。

### Rationale

最大の理由は、Keneek の観測した事実だけを状態が示すことにある。
DD-EP-08 は、Keneek が観測できない事実を状態が主張しないことを、状態の集合の根拠にしている。

決定 1 の条件を (i) と (ii) に限る理由は、両 OS の公式ドキュメントで保証されているのが、確認した時点の値と呼び出しの正常終了だけであることにある。
`dispatched` は、この 2 つの事実だけを示す。
そのため、確認の後に設定が無効になって表示されなくても、`dispatched` の示す事実は偽にならない。
(i) は、確認がその試みに対応することと、呼び出しより前に行われたことだけを条件にする。
`dispatched` と判定した後の終端状態の確定は、決定 6 の定義に従う。
確認から呼び出しまでの時間に上限を付けない理由は、両 OS で共通に成り立つ値の根拠が無いことにある。

決定 2 の理由は、終端状態の不変性 (R-EP-C-021) と DR-08・R-EP-C-042 を、変えないで済むことにある。
後から知らされる失敗は Windows UWP にしか無い。
その発生時期と確実性は、公式の文書に書かれていない。
そのため、両 OS で共通の契約にできない (決定 7)。

決定 3 の理由は、場合 E に改訂前の `missed` の意味 (引き渡せなかった) を当てると、観測できない事実を状態が主張することにある。
場合 E は、呼び出しの後で停止し、OS へ届いた可能性のある通知を含む。
「成功を確認できないまま終了した」と定めれば、届いた可能性を否定せずに、場合 B・C・E・F を 1 つの状態で表せる。
`dispatched` は成功を確認して終了した場合を表す。
`missed` は成功を確認できずに終了した場合を表す。
2 つの意味は重ならない。

決定 4 と場合 F の理由は、判定不能が「有効と確認できなかった」場合であり、決定 1 (i) を満たさないことにある。
場合 C (無効) と同じ `missed` を選べば、(i) を一貫した必要条件で扱える。
判定不能が続く環境でも、通知が `scheduled` のまま残らない。
`Unsupported` のときに `Show` で表示できたと言える根拠は、公式ドキュメントに無い。

場合 E を `missed` とし呼び出し直さない理由は、通知の重複を避けることを優先したことにある。
終端状態を確定できなかったことは、引き渡しの失敗の証拠ではない。
決定 3 の `missed` の意味は、届かなかったことを主張しないため、場合 E に当てはまる。
場合 E を、呼び出したかどうかによらず定める理由は、場合 D と場合 E の境界を「有効な開始の記録の有無」の 1 点へ置くことにある。
再開後に必要な識別は、開始の記録があるかどうかだけになる。
呼び出したかどうかを区別する必要は無い。
呼び出す前に停止した通知も呼び出し直さないため、その通知は失われ得る。
重複を避けることを優先し、この損失を受け入れる。

場合 D と場合 E を取り違えないことを不変条件にする理由は、取り違えると場合 E の決定が守れないことにある。
呼び出した通知を場合 D と取り違えると、#18 の決定によっては再び引き渡され、通知が重複する。
開始の記録が復元できる状態になるまで確認と呼び出しを始めなければ、確認や呼び出しの済んだ通知は必ず有効な開始の記録を持つ。
そのため、呼び出した通知が場合 D と取り違えられることは無い。
記録を呼び出しより前ではなく確認より前へ置く理由は、場合 C・F の判定の後、確定の前で停止した通知も、場合 E として回復できることにある。
記録の方法を契約に定めない理由は、DR-03 決定 2 が内部の実現方法を兄弟 issue に委ねていることにある。
契約は、保証する性質と、その性質に必要な条件だけを定める。

決定 6 の理由は、結果を確認した時点で終端状態が確定したとみなすと、停止の後に観測される状態が決まらないことにある。
確定する前の停止をすべて場合 E に含めれば、再開後の外部の状態が 1 つに決まる。
再開後に状態を一意に復元できることを確定の保証条件にする理由は、終端状態の不変性 (R-EP-C-021) が再開をまたいで成り立つための必要条件であることにある。
確定した状態を再開後に一意に復元できないと、通知は `scheduled` に戻って観測されるか、別の終端状態として観測され得る。
この条件だけで R-EP-C-021 のすべてを実現するわけではない。
後から知らされる失敗で状態を変えないことは、決定 2 で別に定めている。
確定の定義に取得での観測を含めない理由は、取得への反映の時期が §Open Questions #28 で未決定であることにある。
取得での観測を確定の条件にすると、#28 で決めるべき反映の時期を本 DR が先に決めてしまう。

決定 7 の理由は、契約が端末へ依存するのを避けることにある。
OS ごとに条件を変えると、同じ事象の状態が端末によって異なる。
判定の方法は内部の実現方法にあたるため、DR-03 決定 2 に従い implementation に委ねる。

場合 D (§Open Questions #18) が未決定でも本 DR を採用できる理由は、場合 A・B・C・E・F の決定が場合 D の扱いへ依存しないことにある。
場合 D の通知は、#18 が決まるまで R-EP-C-042 により `scheduled` として観測される。
この扱いは既存の契約と矛盾しない。

### Consequences

- Positive:
  - 同じ引き渡しの試みは、OS によらず同じ条件で `dispatched` か `missed` と判定される (場合 A・B・C・E・F)
  - アプリケーション単位で通知が無効、または判定不能と分かっている通知が、`dispatched` として観測されない
  - `dispatched` と `missed` は、後から知らされる失敗やイベントの到着の順序によって変わらない
  - 場合 E の通知は呼び出し直さないため、利用者に同じ通知が 2 回出ない
  - 場合 D と場合 E の境界が有効な開始の記録の有無の 1 点になり、再開後に呼び出したかどうかを区別しなくてよい
  - 判定の方法、非同期の失敗のイベントの扱い、開始の記録の方法を、契約を変えずに implementation で選べる
- Negative:
  - `dispatched` は、OS の受理、表示の成功、利用者の確認、呼び出した時点の通知可否のどれも保証しない
  - 確認の後に通知が無効になった場合も、表示されない通知が `dispatched` のまま残る
  - Windows UWP で後から失敗が知らされた場合も、表示されない通知が `dispatched` のまま残る
  - Android のチャネルの無効・一時停止・おやすみモードや Windows の集中モードで表示されない通知も、`dispatched` になり得る
  - `missed` から「OS に確実に届かなかった」と読み取れなくなる
  - 場合 E では、OS に届いて表示された通知も `missed` になり得る
    - 正常終了を確認した後、確定する前に停止した通知も、これに含む (決定 6)
  - 場合 F では、呼び出せば表示できた可能性のある通知も `missed` に確定する
  - 開始の記録の後、呼び出しの前に停止した通知も、場合 E として呼び出し直さない
    - その通知は、利用者に届かないまま失われ得る
    - 重複を避けるため、この損失を受け入れる
  - 引き渡し処理の終了までの時間に上限が無いため、クライアントは、発火時刻からどれだけ遅れたら `missed` になるかを契約から知ることができない
  - 確定した状態が取得に反映される時期は、§Open Questions #28 で決まるまで保証されない
    - クライアントは、取得の結果から確定の時点を知ることができない
  - 場合 D の状態は、本 DR では決まらない
  - 決定 5 の開始の記録の条件と、決定 6 の一意の復元の条件は、永続化 (issue #7) の実現に制約を加える
    - 開始の記録が、再開の後で復元できる状態となるまで、通知可否の確認と OS の通知 API の呼び出しを始められない
    - 確定した終端状態を、再開後に一意に復元できなければならない
  - 2 つの条件が実現できるかは、G-04 の照合で確かめるまで未確認である
  - 記録の破損などで場合 D と場合 E を区別できなくなった場合の扱いは、永続化 (issue #7) の回復の方法が決まるまで定まらない
    - 不変条件が守られないと、呼び出した通知が場合 D と取り違えられ得る
    - #18 が場合 D を遅れて引き渡すと決めた場合、取り違えた通知は再び引き渡され、通知が重複し得る
  - 本 DR を仕様に反映すると G-04 の保証の内容が変わるため、G-04 の照合結果は「未確認」に戻る (specifications-governance.md DD-GV-13)
  - DR-05 決定 6 により、G-04 の照合が済むまで、API 契約全体は確定しない
  - R-EP-C-022 の規則の意味が変わるため、言い回しの明確化だけでは足りない (理由を次に挙げる)
    - R-EP-C-022 の「発火時刻に OS へ通知を引き渡した」は、OS へ通知が渡ったことを主張すると読める

## DR-13: 引き渡し処理の開始が確定した後は、終端状態が確定するまでキャンセルを拒否する - 2026-11-15 15:08:18

**Phase**: spec
**Status**: Partially superseded by DR-17（決定 12）

### Context

引き渡し処理の開始の後、終端状態の確定の前に届いたキャンセルを、成功させるか拒否させるかが契約に定まっていない。
DR-12 (Accepted) を specifications へ反映する前に、この扱いを決める必要がある。

specifications-endpoints.md v2.2.2 は、キャンセルを次のように定める (本 DR に関わる部分)。

- `scheduled` は「登録済みで、OS への引き渡しの結果がまだ決まっていない」状態とする (3.6)
- 3.6 の遷移表の `scheduled` へのキャンセルの行は、「成功。状態は `cancelled`」とする
- 同じ遷移表の、`fireAt` を過ぎたが引き渡しの結果が決まっていない `scheduled` の行は、その間のキャンセルは R-EP-C-025 に従うとする (R-EP-C-042)
- キャンセルは `scheduled` の通知だけを受け付け、`cancelled`・`dispatched`・`missed` の通知は `notification.not_cancellable` で拒否する (R-EP-C-024)
- キャンセルと引き渡しが競合したときは、成功か拒否のどちらか一方に確定する (R-EP-C-025)。どちらになるかの決め方は書かれていない
- 3.7 は、競合して拒否された通知は「`dispatched` または `missed` になる」と書く
- キャンセルが成功した通知は、以後 OS へ引き渡されない (3.7、R-EP-I-007)
- キャンセルが成功した後の再送は、`notification.not_cancellable` になる (R-EP-C-026)
- `fireAt` を過ぎた通知の、確定までの間のキャンセルは R-EP-C-025 に従う (R-EP-C-042、DR-08 決定 2)

DR-12 は、引き渡し処理について次のことを決めた。

- 引き渡し処理の開始は、有効な開始の記録が、再開の後で復元できる状態となったことを指す。その時点まで、通知可否の確認と OS の通知 API の呼び出しを始めない (DR-12 決定 5)
- 開始の後の通知の終端状態は、確定する場合、場合 A・B・C・E・F に従って `dispatched` か `missed` になる (DR-12 決定 5)。DR-12 は、確定までの時間 (引き渡し処理の終了までの時間) の上限も、確定すること自体も保証しない
- 終端状態の確定は、状態が決まり、再開の後に一意に復元できるようになったことを指す。確定するまで、通知は `scheduled` として観測される (DR-12 決定 6)

このため、開始の後でも、通知は確定まで `scheduled` として観測され得る。
本 DR の前は、R-EP-C-025 が成功と拒否のどちらに確定するかを定める規則が無い。
そのため、開始の後のキャンセルも成功し得る。
その場合、DR-12 決定 5 の表で `dispatched` か `missed` と判定される通知が、`cancelled` にもなり得る。
キャンセルの確定と開始の確定の両方が、再開の後に復元され得るかも決まっていない。

関連する未決定の事項として、次の 2 つがある。

- DR-09 の Scope は、「キャンセルの 5xx の後に、状態が `cancelled` か変化なしのどちらかであることを、既存の規則を超えて保証するか」を保留している
- specifications-endpoints.md §Open Questions #24 は、R-EP-I-007 の保証が永続化 (issue #7) に依存するかを問うている

### Decision

1. 決定 1: `scheduled` は、終端状態がまだ確定していないことだけを示す。
   - `scheduled` は、キャンセルできることを示さない
   - `scheduled` は、引き渡し処理を開始したかどうかを示さない
   - `scheduled` であることは、キャンセルの成功の必要条件であり、十分条件ではない
2. 決定 2: キャンセルを成功させ得るのは、引き渡し処理の開始の確定より前に限る。
   この条件は、状態に関してキャンセルを受け付けるための必要条件であり、成功を無条件に保証しない。
   キャンセルの成功の応答 (200) は、次をすべて満たした場合に限る。
   - specifications-errors.md 4.1 の他の段 (認証・認可・経路・通知 ID など) で拒否されない
   - サーバーの処理が失敗しない (5xx でない)
   - キャンセルの確定が、開始の確定より先に成立する

   リクエストが届いた時点で開始が確定していなくても、処理の間に開始が先に確定すれば、そのキャンセルは拒否になる。
3. 決定 3: 開始が確定し、終端状態がまだ確定していない通知へのキャンセルは、409 `notification.not_cancellable` で拒否する。
   その間、一覧取得と単体取得では、その通知の状態として `scheduled` が観測され得る。
4. 決定 4: 同じ通知について、キャンセルの確定と引き渡し処理の開始の確定は両立しない。
   - 競合の途中でプロセスが停止しても、再開の後に両方が復元されることは無い
   - 記録の破損などで、どちらが確定していたかを判定できなくなった場合は、永続化 (issue #7) の回復の方法に委ねる。DR-12 で場合 D・場合 E の区別を失った場合と同じに扱う
5. 決定 5: `cancelled` も、DR-12 決定 6 と同じ意味で確定する。
   確定した `cancelled` は、停止の後の再開でも一意に復元できる終端状態とする。
6. 決定 6: キャンセルの成功の応答 (200) は、`cancelled` の確定の後にだけ返す。
   確定した `cancelled` が一覧取得・単体取得に反映される時期は、本 DR では決めない。
7. 決定 7: `cancelled` になった通知については、引き渡し処理を開始せず、OS の通知 API を呼び出さない。
   その通知について、OS の通知 API は一度も呼び出されていない。
   3.7 と R-EP-I-007 の「以後 OS へ引き渡されない」の意味を、この性質として確定する。
8. 決定 8: 開始が確定した通知は、`cancelled` に遷移しない。
   この性質は、キャンセルの拒否の応答があったかどうかに関係なく成り立つ、通知の性質とする。
   その通知の終端状態は、DR-12 決定 5 の場合 A・B・C・E・F に従い、`dispatched` か `missed` にだけ確定し得る。
9. 決定 9: キャンセルできない期間 (開始の確定から終端状態の確定まで) の時間の上限は保証しない。
10. 決定 10: プロセスの停止の後に再開したとき、各通知の回復時の判定区分を次の 4 つに分け、それぞれの扱いを定める。
    - (a) キャンセルが確定していた通知は、`cancelled` とする
    - (b) 開始が確定し、終端状態が確定していなかった通知は、DR-12 決定 5 の場合 E として `missed` とする
    - (c) 開始が確定し、終端状態も確定していた通知は、その終端状態とする
    - (d) キャンセルと開始のどちらも確定していなかった通知は、DR-12 決定 5 の場合 D とする。状態は specifications-endpoints.md §Open Questions #18 で決める。決まるまでは `scheduled` として観測され、決定 2 の条件でキャンセルを受け付ける

    (b) の場合 E による `missed` への回復は、停止の後の再開のときに限る。
    通常の稼働の間、開始が確定し、終端状態の確定していない通知は、`scheduled` のままとする (DR-12 決定 6)。
11. 決定 11: 確定しなかったキャンセルと、結果を確認できなかったキャンセルの後の状態を、次のとおりとする。
    - 内部でキャンセルが確定しなかった場合、そのキャンセルは状態に影響を残さない。状態は、そのキャンセルが無かった場合の状態と同じになる。引き渡し処理が進めば、`dispatched` と `missed` のどちらにもなり得る
    - クライアントがキャンセルの結果を確認できなかった場合 (5xx・応答なしなどの結果未確定)、状態は次のどちらかである
      - `cancelled` (内部でキャンセルが確定していた場合)
      - そのキャンセルが無かった場合の状態
    - 結果を確認できなかった場合も、クライアントは結論を出さない (DR-09 決定 2・決定 3)
12. 決定 12: `notification.not_cancellable` による拒否が示すことを、次のとおりに限る。
    - 示すこと: そのキャンセルの要求が拒否された事実と、その要求が通知の状態を変えなかったこと
    - 示さないこと: 通知の具体的な現在の状態と、将来の終端状態
    - 拒否の理由は次の 3 つであり、拒否の応答はこれらを区別しない
      - `cancelled` (キャンセルの成功の後の再送を含む。R-EP-C-026)
      - `dispatched`・`missed`
      - 開始が確定した `scheduled`
    - 拒否応答から、終端状態が確定していることは導けない。開始が確定した `scheduled` の通知は、DR-12 に従って確定するまで `scheduled` のまま残り得る。確定までの時間と、確定すること自体は保証しない
13. 決定 13: 通知の状態遷移と、キャンセルの要求の結果 (成功・拒否) を区別する。
    - 状態遷移は、通知の状態の変化だけを指す
    - キャンセルの拒否は、要求の結果であり、状態遷移ではない。拒否で状態は変わらない
    - キャンセルの成功は、要求の結果である。成功に対応する状態遷移は、キャンセルの確定による `scheduled` から `cancelled` への遷移である

### Scope

- Applies to: 引き渡し処理の開始の確定の後、終端状態の確定の前のキャンセルの扱い、キャンセルの成功と拒否の条件と意味、キャンセルの確定と開始の確定の関係、停止の後の再開での状態の決まり方
- Consistency: 次のものは変えない
  - 状態の集合 (DD-EP-08、R-EP-C-021)
  - 終端状態が別の状態へ遷移しないこと (R-EP-C-021)
  - キャンセルの応答の分類と、結果未確定のときにクライアントが結論を出さないこと (R-EP-C-043、R-EP-C-044、DR-09 決定 1〜3)
  - キャンセルの成功の後の再送が `notification.not_cancellable` になること (R-EP-C-026)
- Relation to DR-08: 補完であり、置き換えない
  - DR-08 決定 1 (確定するまで `scheduled` として観測される) は、決定 3・決定 12 の開始が確定した `scheduled` にもそのまま当てはまる
  - DR-08 決定 2 (成功か拒否の一方に確定する) は変えない。本 DR は、R-EP-C-025 がどちらに確定するかの決め方を定める
- Relation to DR-09: 補完であり、置き換えない
  - DR-09 決定 1〜4 は変えない
  - DR-09 の Scope の保留事項 (キャンセルの 5xx の後に、状態が `cancelled` か変化なしのどちらかであることを保証するか) は、決定 11 の範囲でだけ解決する
  - 本 DR が保証するのは、「`cancelled` か、そのキャンセルが無かった場合の状態のどちらか」である
  - 「変化なし」(状態が変わらないこと) は保証しない。引き渡し処理は、キャンセルとは独立に進むためである
- Relation to DR-12: 補完であり、置き換えない
  - DR-12 決定 1〜7 の文は変えない
  - 決定 5 は、DR-12 決定 6 の確定の定義を `cancelled` にも当てるだけである

  - specifications-governance.md G-05・G-06 の照合対象に issue #7 を加えること → specifications-governance.md (本 DR とは別の変更)

### Alternatives Considered

3 つの案の違いは次のとおりとする。

| 案                      | キャンセルを成功させ得る範囲   | DR-12 との関係                                     | 200 の意味                                       |
| ----------------------- | ------------------------------ | -------------------------------------------------- | ------------------------------------------------ |
| 案 A (採用)             | 引き渡し処理の開始の確定より前 | DR-12 の決定を変えない                             | OS の通知 API を一度も呼び出さないことが確定した |
| 案 B (先に確定した方)   | 終端状態の確定より前           | 決定 5 と衝突し、一部の Supersede が要る           | 通知を止めたことを意味しない                     |
| 案 C (呼び出しの前だけ) | OS の通知 API の呼び出しより前 | 場合 C の扱いで決定 5 と衝突するか、境界が食い違う | OS の通知 API を一度も呼び出さない               |

- 案 B: キャンセルと引き渡しの終端状態の確定を競合させ、先に確定した方を優先する。
  キャンセルできる範囲は最も広く、実現も単純である。
  しかし、場合 A と判定された通知が `cancelled` に確定し得る。
  これは、DR-12 決定 5 (場合ごとに終端状態が決まる) と衝突し、DR-12 の一部の Supersede が要る。
  200 は「通知を止めた」ことを意味しなくなる。表示済みの通知も `cancelled` になり得る。
  再開の後に場合 E として回復を待つ通知も、キャンセルできてしまう。
  以上の理由で不採用。
- 案 C: OS の通知 API の呼び出しの前だけ、キャンセルを成功させ得る。
  まだ OS へ引き渡していない通知はキャンセルできるべきという DR-08 の理由と、最もよく合う。
  しかし、通知可否の確認が「無効」だった後 (場合 C) のキャンセルを成功させると、DR-12 決定 5 と衝突する。
  拒否すると、「有効」の確認の後、呼び出しの前のキャンセルが成功することと食い違う。
  排他の基準が、呼び出しの開始と、確定の根拠が揃うことの 2 つになる。
  再開の後は呼び出したかどうかが分からないため、結局は案 A と同じ境界になる。
  以上の理由で不採用 (次点)。
- DR-08 で退けた「`fireAt` を過ぎた通知へのキャンセルを、すべて拒否する」案とは異なる。
  案 A は、開始が確定する前の通知を、`fireAt` を過ぎていてもキャンセルできる。
  場合 D の通知も、決定 2 の条件でキャンセルを受け付ける。
  DR-08 が退けた理由 (まだ OS へ引き渡されていない通知まで拒否する) は、案 A では開始の確定の後の通知にだけ当てはまる。その影響は Consequences の Negative に挙げる。

### Rationale

最大の理由は、(a) キャンセルの成功の意味が確実となることと、(b) 停止と再開の後の回復の扱いが一意となることにある。

- (a) 200 を受け取った通知は、引き渡し処理を開始しておらず、OS の通知 API を一度も呼び出していない (決定 6・決定 7)
- (b) キャンセルの確定と開始の確定は排他であり、再開の後、各通知の回復時の判定区分が 1 つに決まる (決定 4・決定 5・決定 10)。場合 D の通知の状態は、specifications-endpoints.md §Open Questions #18 に委ねたままとする

(a) は、DR-12 決定 5 に支えられる。
DR-12 決定 5 は、開始の確定まで通知可否の確認と OS の通知 API の呼び出しを始めないと定めている。
そのため、開始より先にキャンセルが確定した通知は、OS の通知 API を一度も呼び出していない。
`cancelled` の意味は、比較した 3 つの案の中で最も強くなる。

(b) は、境界を 1 点に置くことで成り立つ。
キャンセルの可否の境界は、DR-12 の場合 D と場合 E の境界と同じ 1 点 (有効な開始の記録の有無) になる。
再開の後に必要な識別は、DR-12 がすでに求めている開始の記録の有無だけで済む。
呼び出したかどうかを区別する必要は無い。

開始が確定した通知は `cancelled` にならない (決定 8)。
そのため、DR-12 決定 5 の場合の表は、開始が確定した通知を例外なく覆う。
決定 4 により、`cancelled` の通知は有効な開始の記録を持たない。
そのため、`cancelled` の通知が再開の後に場合 E として扱われることは無い。

副次的な利点として、案 A は、比較した案 A・B・C のうち、DR-08・DR-09・DR-12 のどの決定も変えずに済む唯一の案でもある。
本 DR は 3 つの DR を補完するだけで、Supersede を要しない。

本 DR は、キャンセルできない期間という、契約に無かった新しい制約を加える。
本 DR の前は、その期間のキャンセルも R-EP-C-025 のもとで成功し得た。
本 DR は、次の取引を明示して選ぶ。

- 受け入れるもの
  - キャンセルできない期間に、時間の上限が無いこと (決定 9)
  - OS の通知 API をまだ呼び出していない通知も、開始が確定していれば拒否されること
- 得るもの: 上の (a) と (b)
- 受け入れられると判断する理由
  - DR-12 は、終端状態の確定までの時間に、もともと上限を設けていない
  - 影響を受けるのは、開始が確定した通知だけである。場合 D の通知は、引き続きキャンセルできる

決定 11 で「変化なし」を保証しない理由は、引き渡し処理がキャンセルとは独立して進むことにある。
確定しなかったキャンセルの後も、通知は `dispatched` か `missed` に確定し得る。
「`cancelled` か、そのキャンセルが無かった場合の状態のどちらか」であれば、決定 4 の排他から導ける。

### Consequences

- Positive:
  - キャンセルの成功か拒否かが、開始の確定とキャンセルの確定の順序で一意に決まる (R-EP-C-025 の決め方が定まる)
  - 開始が確定した通知の終端状態は、DR-12 決定 5 の場合の表だけで決まる
  - 200 を受け取った通知は、OS の通知 API を一度も呼び出していない
  - 停止の後の再開でも、キャンセルの確定と開始の確定が両方復元されることは無い
  - キャンセルが結果未確定になった後の状態が、`cancelled` か、そのキャンセルが無かった場合の状態のどちらかに限られる
- Negative:
  - キャンセルできない期間は、終端状態の確定まで無期限に続き得る (決定 9)
  - キャンセルできない期間の通知には、次のものが含まれる
    - OS の通知 API をまだ呼び出していない通知 (通知可否の確認の前、確認と呼び出しの間)
    - 再開の後に、場合 E として回復を待つ通知
  - 上の通知を拒否することは、DR-08 の Rationale と部分的に衝突する
    - DR-08 は、まだ OS へ引き渡されていない通知までキャンセルを拒否する案を退けた
    - DR-08 の Rationale の「その間のキャンセルに新しい規則は要らない」という前提も成り立たなくなる
    - DR-08 決定 1・決定 2 とは直接矛盾しない。結果は成功か拒否のどちらかのままで、DR-08 決定 2 が参照する R-EP-C-025 の中身が本 DR で定まる
  - クライアントは、取得の結果から開始が確定したかを判断できない
  - 取得で `scheduled` が観測され、キャンセルが 409 になる組み合わせには、次の 3 つの原因があり、クライアントは区別できない
    - (i) 開始が確定し、終端状態がまだ確定していない
    - (ii) 終端状態は確定したが、取得にまだ反映されていない (§Open Questions #28)
    - (iii) 以前のキャンセルが成功したが、取得にまだ反映されていない (§Open Questions #28、R-EP-C-026)
  - `notification.not_cancellable` の理由が 3 つになり、§Open Questions #34 の情報の不足が大きくなる
  - 本 DR は、キャンセルの成功と拒否の条件、および状態遷移の規則を変える。この変更は、specifications-governance.md 3.4〜3.6 の規則に従って、互換性の分類と版の更新の評価を受ける (分類の判断基準は 3.5)
  - 決定 4 の排他と決定 5 の一意の復元は、永続化 (issue #7) と照会・キャンセル (issue #5) の実現に制約を加える
  - 2 つの条件を実現できるかは、G-05・G-06 の照合で確かめるまで未確認である
  - 本 DR を記録した時点で、次の文書は本 DR に合わせた改訂を要する。改訂までは既存の記述との不整合が残る。改訂は本 DR とは別の変更とする

    - specifications-endpoints.md v2.2.2 の 3.7 (成功と拒否の意味。「拒否された通知は `dispatched` または `missed` になる」は意味が変わる)

## DR-14: 停止中・スリープ中に発火時刻を過ぎ、引き渡し処理を開始していない通知は再開後に遅れて引き渡し、発火時刻の判定はサーバーの時計で行う - 2026-11-15 16:52:49

**Phase**: spec
**Status**: Accepted

### Context

プロセスの停止中や端末のスリープ中に `fireAt` を過ぎ、引き渡し処理を開始していない通知の状態が、契約に定まっていない。
発火時刻の判定に使う時計も、契約に定まっていない。
specifications-endpoints.md §Open Questions #18 は、この 2 つを問うている。

specifications-endpoints.md v3.0.0 は、この通知を次のように扱う (本 DR に関わる部分)。

- 3.6.1 は、引き渡しの試みを場合 A〜F に分ける (DR-12 決定 5)。場合 D (引き渡し処理の未開始) だけ、確定の根拠と状態を 7 章 #18 に委ねている
- 引き渡し処理の開始 (UD-NST-005) は、有効な開始の記録が、再開の後で復元できる状態となったことを指す。その時点まで、通知可否の確認と OS の通知 API の呼び出しを始めない (R-EP-I-009)
- 再開の後の場合 D と場合 E の区別は、有効な開始の記録の有無で行う (R-EP-I-009)
- 場合 E の通知は、再開の後に OS の通知 API を呼び出し直さず、`missed` に確定する (R-EP-I-008)
- R-EP-I-010 は、再開の後の各通知を判定区分 (a)〜(d) に分ける。(d) の場合 D の状態は 7 章 #18 で決めるとし、決まるまでは `scheduled` として観測され、キャンセルを受け付けるとする
- R-EP-C-046 は `missed` の意味を定め、末尾で「場合 D の通知の状態は 7 章 #18 で決める」とする
- 終端状態が確定するまで、通知は `scheduled` として観測される (R-EP-C-042)
- キャンセルの確定と引き渡し処理の開始の確定は両立しない (R-EP-C-025、R-EP-I-007、DR-13 決定 4)
- 5 章の「引き渡し処理を開始する前にプロセスが停止した」の行は、状態を未定義としている

既存の規則が排他や区別を保証する範囲は、次の 2 つに限られる。

- R-EP-C-025 と R-EP-I-007 の排他: キャンセルの確定と、引き渡し処理の開始の確定の間だけ
- R-EP-I-009 の区別: 場合 E を場合 D と取り違えないことと、開始の記録が復元できる状態となるまで通知可否の確認と呼び出しを始めないことだけ

同じ通知について引き渡しの試みが並行したとき、開始の確定が 1 回だけになること (開始の確定の一意性) を定めた規則は無い。
UD-NST-005 も、開始を「有効な開始の記録が復元できる状態となったこと」とだけ定義している。

DR-12 と DR-13 は、場合 D の扱いが決まったときに見直す条件を残している。

- DR-12 の Revisit Trigger: §Open Questions #18 が場合 D の扱いを決め、場合 E の扱いと両立しなくなったら見直す
- DR-12 の Consequences: #18 が場合 D を遅れて引き渡すと決めた場合、場合 D と場合 E を取り違えた通知は再び引き渡され、通知が重複し得る
- DR-13 の Revisit Trigger: §Open Questions #18 が場合 D の扱いを決め、DR-13 決定 2 の受け付ける条件や決定 10 の (d) と両立しなくなったら見直す

時計については、次の事実がある。

- Keneek は、デバイス上の PWA からの通知スケジュールを管理・発火するローカル通知サービスである (requirements.md 2. Context)
- クライアントの時計とサーバーの時計は一致しない (specifications-idempotency.md 2.2)

永続化 (issue #7) の下書きは、起動時に保存した通知を復元して再スケジュールし、停止中に時刻を過ぎた通知の方針を issue #7 で決めるとしている (specifications-governance.md の G-04 の照合の記録)。
G-04 と issue #5・issue #7 の照合結果は、どちらも「未確認」である (DR-05)。

改善計画 (specifications-improvement-plan.md の IMP-02) は、外部から観測できる結果だけを契約にし、時計の読み方は implementation に回す方向を推奨している。

### Decision

1. 決定 1: プロセスの停止中や端末のスリープ中に `fireAt` を過ぎ、引き渡し処理を開始していない通知 (3.6.1 の場合 D) は、再開の後に引き渡しの対象とする。
   その通知は、発火時刻より遅れて引き渡す。
2. 決定 2: 遅れた引き渡しの結果は、DR-12 決定 5 の場合 A・B・C・F に従う。
   `dispatched` と `missed` の判定は、DR-12 の判定のとおりとする。
3. 決定 3: DR-12 決定 3 の `missed` の意味 (OS への通知要求について、成功を確認できないまま引き渡し処理を終了した状態) は変えない。
4. 決定 4: 再開から引き渡しまでの遅延の上限は保証しない。
5. 決定 5: 停止やスリープの期間の長さだけを理由に、通知を破棄しない。
6. 決定 6: 通知の有効期限と猶予時間は、本 DR では規定しない。別の設計判断とする。
7. 決定 7: `fireAt` を過ぎたかどうかは、サーバーの時計で判定する。
   - サーバーの時計で `fireAt` より前に、引き渡し処理を開始しない
   - 時計の正しさは環境の責務とし、契約では保証しない
   - 時計の変更 (前進・逆行) の影響も環境の責務とし、契約では保証しない

- Consistency: 本 DR は、DR-12 と DR-13 が §Open Questions #18 に委ねた場合 D の扱いを決める。DR-08・DR-12・DR-13 のどれも置き換えない。次のものは変えない

  古い通知の引き渡しは防げる。
  しかし、猶予の値を契約で決める必要がある。
  また、引き渡し処理を開始していない `missed` が生まれる。
  そのため、DR-12 決定 3 の `missed` の定義 (成功を確認できないまま引き渡し処理を終了した) を広げる必要がある。
  有効期限と猶予は別の設計判断に回すため不採用。
- 常に `missed` にする。
  結果は分かりやすい。
  しかし、短いスリープでも通知が落ちる。
  また、DR-12 決定 3 の `missed` の定義を広げる必要があるため不採用。
- 時計の変更 (逆行・前進のときの再判定) まで契約に含める。

  しかし、OS ごとの差を契約が抱える。
  外部から観測できる結果だけを契約にする方針 (IMP-02 の推奨) に反するため不採用。

### Rationale

最大の理由は、短い停止やスリープで通知を落とさずに、DR-12 の `missed` の意味を保てることにある。
場合 D の通知は引き渡し処理を開始していない。
そのため、引き渡し処理を終了したことを前提とする `missed` には当たらない。
遅れて引き渡せば、結果は既存の場合 A・B・C・F で決まり、`missed` の定義を広げずに済む (決定 2・決定 3)。

本 DR では、「開始の記録を作ること」と「開始を一意に確定すること」を区別する。

- 開始の記録を作ること: R-EP-I-009 が求める。開始の記録が復元できる状態となる前に、通知可否の確認と呼び出しを始めない
- 開始を一意に確定すること: 同じ通知について、開始の確定が 1 回だけであること。既存の規則では確認できない

遅れた引き渡しで通知が重複しないことは、次の 2 つの前提が成り立つ場合に限って、既存の規則から導ける。

- 前提 1: 同じ通知について、引き渡し処理の開始の確定が 1 回だけである (開始の確定の一意性)
- 前提 2: 開始の記録が再開の後に正しく復元され、場合 D と場合 E を区別できる

2 つの前提のもとで、次のことが言える。

- 場合 D の通知は、有効な開始の記録を持たない。R-EP-I-009 により、その通知について OS の通知 API はまだ呼び出されていない
- 遅れた引き渡しも、まず有効な開始の記録を作ってから、通知可否の確認と呼び出しに進む (R-EP-I-009)
- 遅れた引き渡しの途中で再び停止した通知は、有効な開始の記録を持つため場合 E となり、呼び出し直さない (R-EP-I-008)
- よって、1 つの通知について、OS の通知 API の呼び出しは高々 1 回となる

前提 1 は、既存の規則では確認できない。
R-EP-C-025 と R-EP-I-007 の排他は、キャンセルの確定と開始の確定の間だけを対象にする。
R-EP-I-009 は、場合 D と場合 E の区別と、記録と呼び出しの順序だけを定める。
そのため、前提 1 は G-04 の照合 (issue #7) で確かめる事項とし、本 DR では排他の方式を定めない。
前提 2 が崩れる場合 (記録の破損など) の扱いは、永続化 (issue #7) の回復の方法と G-04 の照合に委ねる (DR-12 決定 5)。

この結論は、DR-12 と DR-13 の場合 E の扱いと両立する。
本 DR は、場合 E を呼び出し直さないことも、場合 D と場合 E を開始の記録の有無で区別することも変えない。
場合 D の通知は、引き渡し処理の開始が確定するまで `scheduled` のままキャンセルを受け付ける。
開始の確定の後は、DR-13 決定 3 により拒否される。
これは、DR-13 決定 2 の受け付ける条件と、決定 10 の (d) とも両立する。

遅延の上限を保証しない理由は、DR-12 決定 5 が、発火時刻からの遅れを含む引き渡し処理の終了までの時間の上限を、すでに保証していないことにある (決定 4)。
停止の期間の長さだけで破棄しない理由は、破棄の境界を決めることが、有効期限・猶予の値を決めることと等しいことにある (決定 5)。
その値は、本 DR で扱わない別の設計判断とする (決定 6)。

サーバーの時計で判定する理由は、引き渡しを行うのが、デバイス上で動くサーバー (Keneek) であることにある (決定 7)。
クライアントの時計とサーバーの時計は一致しない (specifications-idempotency.md 2.2)。
決定 7 が外部の結果として示すのは、サーバーの時計で `fireAt` より前に引き渡し処理を開始しないことに限られる。
サーバーの時計が実際の時刻と一致することは示さない。
時計の正しさと時計の変更の影響を環境の責務とする理由は、時計の変更の扱いを契約に含めると OS ごとの差を契約が抱えることにある。
外部から観測できる結果だけを契約にする方針 (IMP-02 の推奨) にも合う。

### Consequences

- Positive:
  - 停止やスリープの後も、引き渡し処理を開始していない通知は、期間の長さだけを理由に破棄されず、引き渡しの対象として残る
  - 引き渡しの対象となった通知は、既存の規則に従って終端状態が決まる
    - 引き渡し処理の開始より先にキャンセルが確定した通知は `cancelled` になり、OS の通知 API を呼び出さない (R-EP-C-024、R-EP-C-025、R-EP-I-007)
    - 開始が確定した通知の結果は、場合 A・B・C・F に従う。途中で再び停止すれば場合 E となる
  - DR-12 の `missed` の意味が変わらず、`missed` は引き渡し処理を終了した通知だけを表し続ける
  - 開始の確定が通知ごとに一意であり、記録が正しく復元される場合、1 つの通知について OS の通知 API の呼び出しは高々 1 回となる
  - R-EP-I-010 の判定区分 (d) の状態が決まり、再開の後の各通知の扱いがすべて定まる
  - サーバーの時計で `fireAt` より前に引き渡し処理を開始しないことが、契約から読み取れる
- Negative:
  - 引き渡しの対象とすることは、OS の通知 API の呼び出しを保証しない。キャンセル、通知可否の確認の結果 (場合 C・F)、再度の停止 (場合 E) によって、呼び出されないことがある
  - 長い停止の後にも、古い通知が引き渡され得る。有効期限と猶予を決めるまで、これを防ぐ手段は契約に無い
  - 再開から引き渡しまでの遅延に上限が無い。クライアントは、通知がいつ引き渡されるかを契約から知ることができない

## DR-15: 成功レスポンスへのメンバーの追加は後方互換とし、クライアントは成功レスポンスの未知のメンバーを無視しなければならない - 2026-11-15 17:57:49

**Phase**: spec
**Status**: Accepted

### Context

成功レスポンスに未知のメンバーが含まれ得るかが、契約に定まっていない。
そのため、成功レスポンスにメンバーを加える変更が後方互換かどうかを判断できない。
specifications-endpoints.md §Open Questions #23 は、この点を問い、新しい DR として決めるとしている。

specifications-endpoints.md v3.1.0 は、リクエストとレスポンスを次のように扱う (本 DR に関わる部分)。

- 登録リクエストは、本文のオブジェクトと各要素のどちらも、未知のメンバーを拒否する (DD-EP-03、3.5 の検証制約)
- `notifications.schema.json` は、登録リクエストの本文、登録済み通知、応答本文の 3 つを区別して定義する (R-EP-C-045)
- 応答本文は、一覧取得とバッチ登録の成功レスポンスの本文であり、登録済み通知の配列を `notifications` メンバーに持つ (DD-EP-02)
- 単体取得とキャンセルの成功レスポンスは、登録済み通知そのものを返す (DD-EP-02)
- R-EP-C-045 と 3.5 は、応答本文が未知のメンバーを含み得るかを定めず、#23 に委ねている
- 4.3 は、レスポンスへのメンバーの追加が後方互換になるかは #23 で未決定であると記している

エラーレスポンスには、拡張についての既存の規則がある (specifications-errors.md v3.0.0 4.8)。

- クライアントは、未知のエラー拡張メンバーを無視する (R-ER-C-049、DR-04 決定 11)
- 既知のメンバーの意味は変えない。拡張メンバーの追加は、既知のメンバーの意味を変えない限り後方互換な変更である (R-ER-C-050)

specifications-governance.md v2.1.0 の 3.5 の判断基準表には、成功レスポンスへのメンバーの追加を扱う行が無い。
同じ表には、次の行と規則がある。

- 「既存フィールドの削除、型・形式・意味の変更」を破壊的とする行
- 「成功条件の変更、または成功・失敗のレスポンス形状の変更」を破壊的とする行 (DR-02)
- 判断に迷う変更は破壊的変更として評価する、という規則

メンバーの追加が「レスポンス形状の変更」にあたるかは、この表からは決まらない。
そのため、成功レスポンスへのメンバーの追加は、判断に迷う変更として破壊的と評価され得る (推測)。

後方互換性は、既存クライアントが変更なしに動作し続けられることと定義されている (UD-VER-001)。
その対象には、レスポンスとクライアントに求める対処が含まれる。

成功レスポンスへのメンバーの追加を前提にする未決定の事項がある。
§Open Questions #35 は、`dispatched`・`missed` に遷移した時刻を登録済み通知のメンバーとして公開するかを問う。
公開する場合は #23 の決定を前提にするとしている。

### Decision

1. 決定 1: 成功レスポンス (登録済み通知と応答本文) へのメンバーの追加は、後方互換 (非破壊的) な変更とする。
   非破壊的とするのは、追加が次のいずれも変えない場合に限る。
   - 既存メンバーの型
   - 既存メンバーの意味
   - 既存メンバーの必須性
   - 既存クライアントに求める動作
2. 決定 2: クライアントは、成功レスポンスに含まれる未知のメンバーを無視しなければならない (MUST)。
3. 決定 3: 既知のメンバーの変更は、メンバーの追加と区別して評価する。
   次の変更は破壊的とする。
   - 既存メンバーの削除
   - 既存メンバーの型の非互換な変更
   - 既存メンバーの意味の変更
   - 既存クライアントに新たな処理を求める変更

   既存メンバーの必須性の変更は、メンバーの追加として評価しない。
   必須性の変更を一律に破壊的とはしない。既存クライアントから観測できる振る舞いと、既存クライアントに求める対処への影響で評価する (DR-04 決定 8・9)。
4. 決定 4: エラーレスポンスの拡張は、既存の規則 (R-ER-C-049・R-ER-C-050、DR-04 決定 11) に従う。
   本 DR は、エラーレスポンスの拡張の規則を変更せず、重ねて定義しない。
5. 決定 5: 本 DR の判断方針は、specifications-governance.md 3.5 の既存の判断基準と矛盾せず、重複しない形で、判断基準に反映する。
   3.5 の既存の行「成功条件の変更、または成功・失敗のレスポンス形状の変更」(破壊的、DR-02) は、適用範囲を明確にする。
   明確にした後の適用範囲は、決定 1 の条件を満たすメンバーの追加を含まない。
   新しい行を加えるだけにせず、その行と既存の行との関係を判断基準表の上で明示する。

### Scope

- Applies to: 通知 REST API の成功レスポンスのうち、登録済み通知と応答本文へのメンバーの追加、その後方互換性の判断、
  および未知のメンバーを受け取るクライアントの扱い。応答本文に含まれる登録済み通知も対象とする
- Consistency:
  - 互換性を変更の形ではなく既存クライアントへの影響で決める方針 (DR-04 決定 8・9、UD-VER-001) と整合させる。本 DR は DR-04 を変更しない
  - 成功レスポンスとエラーレスポンスの判定は、どちらもメンバーの追加を後方互換とし、既知のメンバーの意味の変更を認めない点で一致する。
    エラーレスポンスで既存クライアントに求める対処が変わる変更は、DR-04 決定 9 により破壊的と評価される
  - DR-02 が決めたバッチ登録のレスポンスの形状 (成功と失敗の 2 つだけ、部分成功の形状を持たない) は変えない
  - 登録リクエストが未知のメンバーを拒否すること (DD-EP-03) は変えない
- Not decided here (決定 1〜5 の内容は本 DR で決まっている。残すのは仕様書での記述の位置・文言・表し方だけとする):
  - 決定 2 のクライアントの規範を仕様書のどの規則に置くかと、その文言 → specifications-endpoints.md (R-EP-C-045、3.5、4.3)
  - 決定 1・3・5 を反映する判断基準表の行と文言 → specifications-governance.md 3.5
  - スキーマでの、応答本文と登録済み通知の未知のメンバーの表し方 → specifications-endpoints.md 3.5
- Out of scope:
  - エラーレスポンスの拡張の規則 → specifications-errors.md 4.8 (R-ER-C-049・R-ER-C-050、DR-04 決定 11)
  - `dispatched`・`missed` に遷移した時刻を公開するか → specifications-endpoints.md §Open Questions #35 (未定。本 DR は、公開すると決めた場合のメンバーの追加の扱いだけを与える)

### Alternatives Considered

- 成功レスポンスへのメンバーの追加を破壊的変更とする。レスポンスのメンバーを閉じた集合にし、追加のたびに契約バージョンの MAJOR を上げる。
  クライアントはレスポンスを厳密に検証できる。
  しかし、#35 の時刻のようなメンバーを加えるたびに、新しい API メジャーバージョンの導入と既存クライアントへの影響の管理が要る (REQ-F-011)。
  また、拡張メンバーの追加を後方互換とするエラーレスポンス (R-ER-C-050) と扱いが食い違う。そのため不採用。
- クライアントが未知のメンバーを無視することを SHOULD とする。
  未知のメンバーを拒否するクライアントは、メンバーの追加で動作できなくなり得る。
  そのクライアントにとって追加は後方互換にならず、決定 1 が成り立たない。そのため不採用。
- クライアントに未知のメンバーの扱いを求めない。
  未知のメンバーを拒否するクライアントを契約が排除できず、SHOULD とする案と同じく、追加が後方互換であることを保証できない。そのため不採用。
- エラーレスポンスも含め、すべてのレスポンスの拡張の規則を 1 つに揃えて定め直す。
  エラーレスポンスの拡張は、既存の決定 (DR-04 決定 11) と規則 (R-ER-C-049・R-ER-C-050) で決まっている。
  定め直すと、同じ規範を 2 か所で持つことになる。そのため不採用。

### Rationale

成功レスポンスへのメンバーの追加を後方互換とする最大の理由は、エラーレスポンスの拡張メンバーの扱い (R-ER-C-050) と揃えることにある。
エラーレスポンスと成功レスポンスで追加の扱いが同じなら、クライアントはレスポンスの種類によらず、未知のメンバーを同じ方法で扱える。

追加を後方互換と言えるのは、クライアントが未知のメンバーを無視する場合に限られる。
後方互換性は、既存クライアントが変更なしに動作し続けられることと定義されている (UD-VER-001)。
クライアントが未知のメンバーを無視すれば、既存クライアントはメンバーの追加の後も変更なしに動作を続けられる。
そのため、無視をクライアントの MUST とする。

追加を非破壊的とする条件は、既存メンバーの型・意味・必須性と、既存クライアントへ求める動作に置く。この条件を置く理由は、DR-04 決定 8・9 と同じく、互換性を既存クライアントへの影響で決めることにある。
メンバーの追加という形をとっても、既存メンバーの解釈や既存クライアントの動作が変わる変更は、既存クライアントを変更なしに動作させ続けられない。
必須性の変更を一律に破壊的としない理由も同じで、既存クライアントへの影響は変更ごとに異なるため、影響で評価する。

3.5 の既存の行の適用範囲を明確にする理由は、その行と判断に迷う変更の規則が残ったままだと、決定 1 の条件を満たす追加まで破壊的と評価され得ることにある。
新しい行を加えるだけでは、既存の行とどちらが優先するかが表から読めない。

成功レスポンスへのメンバーの追加を後方互換にすると、#35 の時刻のようなメンバーを、MAJOR を上げずに後から加えられる。

### Consequences

- Positive:
  - #35 の時刻のようなメンバーを、MAJOR を上げずに成功レスポンスへ加えられる
  - 成功レスポンスとエラーレスポンスで、メンバーの追加と未知のメンバーの扱いが揃う
  - メンバーの追加と既知のメンバーの変更を区別するため、追加の形をとった破壊的変更を見落としにくくなる
- Negative:
  - クライアントは、未知のメンバーが含まれることを理由にレスポンスを拒否できない。
    既知のメンバーの型・必須性などは、引き続き厳密に検証できる
  - メンバーを追加するたびに、既存メンバーの型・意味・必須性と既存クライアントに求める動作を変えないかを評価する手間がかかる
  - specifications-governance.md 3.5 の既存の行の適用範囲を明確にするまで、決定 1 と 3.5 の行は食い違って読める。
    本 DR を仕様の正とするには、3.5 の整理を本 DR の追加と同じ変更で揃える必要がある
- Revisit Trigger:
  - 既存クライアントが処理しなければ正しく動作できないメンバーの追加が多くなり、追加の多くが破壊的と評価されるようになったら、本 DR を見直す
  - エラーレスポンスの拡張の扱い (DR-04 決定 11、R-ER-C-050) が変わったら、本 DR を見直す

## DR-16: 成功応答の後に開始された取得に結果の反映を保証し、確定した終端状態は最終的に反映して `scheduled` に戻さない - 2026-11-16 07:47:27

**Phase**: spec
**Status**: Accepted

### Context

201 と 200 の成功応答の後に、一覧取得・単体取得へその結果が反映されるかが、契約に定まっていない。
specifications-endpoints.md の 7 章 Open Questions #28 は、この点を未決定として残している。
論点は 3 つある。

- (a) バッチ登録の 201 の後に、登録した通知が取得に現れるか
- (b) キャンセルの 200 の後に、取得で `cancelled` と `cancelledAt` が観測されるか
- (c) `dispatched`・`missed` への遷移が、取得にいつ反映されるか

(c) については、specifications-endpoints.md の 3.6 が、終端状態の確定の前は `scheduled` として観測されると定めている (R-EP-C-042)。
同じ節は、確定した状態が一覧取得・単体取得に反映される時期を定めていない。

反映の保証がないことは、次の規則に影響している。

- R-EP-C-031 の単体取得による状態の確認は、確認の信頼性が #28 の決定に依存するため、SHOULD にとどまる (DR-09 決定 4)
- R-EP-C-044 は、結果未確定のキャンセルの後に、クライアントが結論を出すことを禁じている。判断の手段は単体取得による確認である
- specifications-errors.md の R-ER-C-041 も、キャンセルの結果を単体取得で確認してから判断することを求めている

保証がないまま実装すると、確認の取得が古い状態を返し、クライアントが誤って判断し得る。

一覧取得の 1 回の応答が、単一の時点の状態を表すかも、定まっていない。
取得の途中で状態が変わったときに、同じ通知が異なる状態で現れることや、`state` で絞り込んだ結果から抜け落ちることを許すかが、7 章 #36 の問いとして残っている。
7 章 #36 は #28 と合わせて決めるとされている。

関係する保証の照合は、まだ終わっていない。
specifications-governance.md の 3.3.3 で、G-04 と G-08 の照合結果は「未確認」と記録されている。
G-05 と issue #5 の組は「矛盾あり」で、解消されていない。
issue #5 は照会とキャンセルを担い、issue #7 は永続化を担う。
この 2 つで反映を実現できるかは、DR-05 の整合確認として確かめる必要がある。

### Decision

1. 決定 1: バッチ登録が 201 を返した後に開始された、同じサーバーへの一覧取得・単体取得に、その登録が反映されることを保証する。
2. 決定 2: キャンセルが 200 を返した後に開始された、同じサーバーへの一覧取得・単体取得に、キャンセルによる `cancelled` と `cancelledAt` が反映されることを保証する。
3. 決定 3: `dispatched` または `missed` の終端状態が確定した通知について、サーバーは、確定した状態を後続の単体取得・一覧取得に最終的に反映しなければならない (MUST)。
   - 終端状態の確定から取得結果への反映までの時間の上限は、保証しない。
   - 一度取得で観測可能になった終端状態を、後続の単体取得・一覧取得で `scheduled` に戻してはならない (MUST NOT)。
   - この保証は、サーバーの再起動の後も維持する。
   - 内部で終端状態を確定する条件は、DR-12 から変更しない。
4. 決定 4: 一覧取得の 1 回の応答は、リクエストの開始から応答の確定までの範囲にある、単一の論理的な観測時点の状態を表す。
   - その応答の中で、通知の包含判定、状態、`state` フィルター、状態に依存するメンバーが、その時点について互いに整合する。
   - 決定 3 の遅延反映は許容する。この決定は、最新の内部確定状態の即時反映を意味しない。
   - 単一の時点を実現する方式は、指定しない。

### Scope

- Applies to: 通知 REST API の契約が定義する、バッチ登録の 201、キャンセルの 200、終端状態 (`dispatched`・`missed`) の確定の後の、一覧取得と単体取得の結果。決定 1 と決定 2 は、成功応答の後に開始された、同じサーバーへの取得に適用する
- Not decided here:
  - 上の保証を仕様書のどの規則にどう書くか。R-EP-C-031、3.8、4.1 の注記、7 章 #28・#36 の解決を含む → specifications-endpoints.md (spec 側の作業)
  - R-EP-C-031 の単体取得による確認を SHOULD から MUST に上げるか → 未定。DR-09 決定 4 との整合確認が済んだ時点で決める。本 DR は MUST 化を決めず、DR-09 を置き換えない
  - 保証の行を加えること → specifications-governance.md の 3.3.3
  - 結果未確定の間に、その操作の通知が取得に現れるか → specifications-endpoints.md の 7 章 #14。本 DR の保証の対象外とする
  - 反映と単一の論理的な観測時点を実現する方法 → issue #5 (照会・キャンセル) と issue #7 (永続化)
  - issue #5・issue #7 との照合 → specifications-governance.md の 3.3.3 (G-04・G-05・G-08)。DR-05 の整合確認に従う。照合は未了である

### Alternatives Considered

- 反映を保証しない。取得の結果は、クライアントが次の操作を選ぶための参考情報にとどめる。
  保証がないと、確認の取得が古い状態を返し、クライアントが誤って判断し得るため不採用。
- 決定 3 の反映までの時間に上限を設ける。
  上限の値を決める根拠が、DR-12 などの既存の記述に無い。
  DR-12 は、発火時刻からの遅れの上限も保証していない。
  実現できるかの照合も、issue #5・issue #7 とは済んでいないため不採用。
- 決定 4 の単一の論理的な観測時点を保証しない。
  1 回の一覧取得の内部で、同じ通知が異なる状態として現れる、または `state` で絞り込んだ結果から抜け落ちることを許すことになる。
  この状況はクライアントの誤判断につながるため不採用。

### Rationale

保証を置く最大の理由は、確認の取得が古い状態を返して、クライアントが誤って判断するのを防ぐことにある。
R-EP-C-031 の単体取得による確認は、結果未確定の後にクライアントが判断する手段となる。
取得が成功応答の結果を反映しなければ、この手段は成り立たない。

利用者は Progressive Web App (PWA) であり、確認の取得は PWA が行う。
この前提は、specifications-endpoints.md の 2.2 に定めがある。
issue #5・issue #7 で保証を実現できるかは、確かめていない (未確認)。

この保証があれば、R-EP-C-031 を SHOULD から MUST に上げる道が開ける。
ただし、MUST に上げるには DR-09 決定 4 との整合確認が要る。
そのため、本 DR では決めない。

決定 3 で、確定した終端状態を最終的に反映する義務を置く理由は、反映が永久に起きない状態を契約から外すことにある。
反映までの時間の上限は、DR-12 が遅れの上限を保証していないことに合わせて、保証しない。
一度観測可能になった `dispatched` や `missed` が `scheduled` に戻ると、クライアントは確定した状態を信頼できない。
再起動の後も保証を維持するのは、再起動で戻る状態を許すと、同じ誤判断を生むことが理由になる。

決定 4 は、1 回の一覧取得の中に、同じ通知が異なる状態として現れる状況を、契約から外す。
この状況も、クライアントの誤判断につながる。
範囲を、リクエストの開始から応答の確定までに限るのは、保証を 1 回の応答の内部に限り、最新状態の即時反映と切り分けることにある。

結果未確定のキャンセルは、取得だけで常に結果を確定できるわけではない。
状態は `cancelled` か、そのキャンセルが無かった場合の状態のどちらかであり、状態が変わらないことは保証されない。
決定 3 の遅延反映により、確定した終端状態が取得にまだ反映されていない期間も残る。

### Consequences

- Positive:
  - 成功応答の後に開始された確認の取得が、成功応答の結果を反映する
  - R-EP-C-031 を MUST に上げる検討が、DR-09 決定 4 との整合確認の後にできる
  - 一度観測可能になった終端状態が取得で戻らないため、クライアントは確定した状態を信頼できる
  - 一覧取得の 1 回の応答が単一の論理的な観測時点を表すため、1 回の応答の内部で状態が食い違わない
- Negative:
  - サーバーは、成功応答の結果を後続の取得に反映する責務を負う。実現できるかは、issue #5・issue #7 との照合で確かめる必要がある
  - 終端状態が取得に反映されるまでの時間は保証されない。クライアントは、その間に `scheduled` を観測し得る
  - 結果未確定のキャンセルの後、単体取得だけでは結果を確定できない場合が残る
  - specifications の反映が済むまで、R-EP-C-031 や 4.1 の注記は、保証が無いことを前提とした書き方のまま残る
- Revisit Trigger:
  - issue #5・issue #7 との照合で、決定 1〜4 の保証を実現できないと分かったら、本 DR を見直す
  - 終端状態の反映の遅れが原因で、クライアントの判断に問題が実際に起きたら、時間の上限の保証について本 DR を見直す

## DR-17: `notification.not_cancellable` の拒否応答に、判定した時点の通知の状態を `currentState` として載せる - 2026-11-16 17:40:42

**Phase**: spec
**Status**: Accepted
**Supersedes**: DR-13（決定 12: 「示さないこと」のうち通知の具体的な現在の状態を示さない部分、拒否の理由を応答で区別しない部分、拒否応答から終端状態の確定を導けないとする部分）
本 DR は Proposed の間、DR-13 の既存決定を変更しない。Accepted になった時点で、決定 6 に定めた範囲を部分的に置き換える。

### Context

`notification.not_cancellable` の拒否応答は、拒否の理由となる通知の状態を区別しない。
区別できない状態は、次の 3 分類である (DR-13 決定 12、R-EP-C-024、R-EP-C-026)。

- `cancelled` (キャンセルが成功した後の再送を含む)
- `dispatched`・`missed`
- 引き渡し処理の開始が確定した `scheduled`

DR-13 は、3 つ目の分類 (開始が確定した `scheduled`) を同じ code の拒否に加えた。
その結果、区別できない分類は 1 つ増えた。
DR-13 は、Revisit Trigger に「`notification.not_cancellable` の理由を応答で区別すると決めたら見直す」を置いている。
この論点は、specifications-endpoints.md §Open Questions #34 に未決定として残っている。

区別できないことの影響は、応答を失った後の再送で現れる。
再送が `notification.not_cancellable` で拒否されても、その拒否だけでは結果を判断できない (DR-09 決定 3、R-EP-C-044)。
クライアントは、単体取得で状態を確認する (R-EP-C-031、SHOULD)。

エラー応答の拡張には、既存の規則がある。

- クライアントは、未知のエラー拡張メンバーを無視する (R-ER-C-049、DR-04 決定 11)
- 拡張メンバーの追加は、既知のメンバーの意味を変えない限り後方互換な変更である (R-ER-C-050)

成功レスポンスへのメンバーの追加を扱う DR-15 は、成功レスポンスに限る。
エラー応答の拡張は、DR-15 の対象ではなく、R-ER-C-050 の対象である (DR-15 決定 4)。

通知の状態は、`scheduled`・`dispatched`・`missed`・`cancelled` のいずれか 1 つである (R-EP-C-021)。

### Decision

1. 決定 1: `notification.not_cancellable` の既存の code と拒否の条件は変えない。新しいエラー code は追加しない。
2. 決定 2: `notification.not_cancellable` の応答は、RFC 9457 の拡張メンバー `currentState` を必須で持つ。
   `currentState` は、キャンセルの可否を判定した時点の通知の状態を示す。
3. 決定 3: `currentState` は JSON string とする。値は既存の通知の状態の定義と一致させる。
   値は `scheduled`・`dispatched`・`missed`・`cancelled` のいずれかとし、別の語彙を作らない。
   - `currentState` の値だけでは、引き渡し処理の開始が確定したかどうかは判断できない
   - ただし、`notification.not_cancellable` の拒否条件と組み合わせると、`currentState: scheduled` は開始が確定した状態を示す
   - この解釈は既存の拒否条件 (R-EP-C-024) から導かれる。`scheduled` 自体の意味 (DR-13 決定 1) は変えない
4. 決定 4: `currentState` は、判定した時点の状態である。
   応答を受け取る時点まで、状態が変わらないことは保証しない。
5. 決定 5: `currentState` を必須とする範囲は、`notification.not_cancellable` に限る。他のエラーには広げない。
6. 決定 6: DR-13 決定 12 を、部分的に置き換える。置き換える範囲は次の 3 つである。
   - 「示さないこと」のうち、通知の具体的な現在の状態を示さない部分
   - 拒否の理由 (`cancelled`、`dispatched`・`missed`、開始が確定した `scheduled` の 3 分類) を、応答で区別しない部分
   - 拒否応答から、終端状態が確定していることは導けないとする部分。`currentState` が `cancelled`・`dispatched`・`missed` のとき、判定した時点で終端状態にあることは導ける

   決定 12 のその他の部分は変えない。
   - 示すこと: そのキャンセルの要求が拒否された事実と、その要求が通知の状態を変えなかったこと
   - 将来の終端状態を示さないこと
   - `currentState` が `scheduled` の通知は、次の 3 つを保証しないこと
     - 将来の終端状態
     - 終端状態の確定までの時間
     - 終端状態が確定すること自体
   - 上の `scheduled` の通知とは、開始が確定した `scheduled` である。DR-12 に従って確定するまで、`scheduled` のまま残り得る

   本 DR は Proposed の間、DR-13 の既存決定を変更しない。Accepted になった時点で、上の範囲の置き換えが発効する。
7. 決定 7: `currentState` は、観測された通知の状態である。状態遷移の原因や、操作の主体を識別する情報ではない。
   このため、DR-09 決定 3 と R-EP-C-044 は変更しない。

### Scope

- Applies to: `notification.not_cancellable` で拒否するキャンセルの応答に載せる、通知の状態の示し方
- Consistency: 次のものは変えない。
  - 拒否の条件と code (R-EP-C-024、R-EP-C-026、DR-13 決定 3・決定 8)
  - キャンセルを冪等な成功にしない方針 (DD-EP-04)
  - 結果未確定のときにクライアントが結論を出さないこと (DR-09 決定 2・決定 3、R-EP-C-044)
  - 単体取得による確認が SHOULD であること (DR-09 決定 4、R-EP-C-031)
  - 成功レスポンスへのメンバーの追加の規則 (DR-15)。本 DR は成功レスポンスにメンバーを加えない
  - 対処方法を表す拡張メンバーを加えない方針 (DR-04 決定 2)。`currentState` は通知の状態であり、対処方法ではない
  - 取得への反映の保証 (DR-16)
- Relation to DR-13: 決定 6 の範囲で部分的に置き換える。Proposed の間は DR-13 の決定を変えず、Accepted になった時点で発効する。決定 12 以外の DR-13 の決定 (決定 1 の状態の定義を含む) は変えない
- Relation to DR-16: 本 DR は取得 API に新たな同期保証を加えない。`currentState` は判定した時点に観測された状態であり、取得 API の結果との一致は、各 API の観測時点と DR-16 の反映保証に従う
- Relation to DR-04: 新しいエラー識別子を追加しないため、識別子の追加の評価 (DR-04 決定 8) は要らない。
  拡張メンバーの追加の互換性は、R-ER-C-050 と DR-04 決定 8・決定 9 の条件で評価する。
  条件は、成功条件、再送時の保証、クライアントに求める対処を変えないことである
- Not decided here:
  - `currentState` のスキーマの具体的な記述 → specifications-errors.md (`/deckrd spec` で反映する)。型は JSON string、許容値は決定 3 の 4 値と本 DR で定める。JSON オブジェクトのメンバーの順序は規定しない
  - 仕様反映時の確認: `currentState: scheduled` の拒否が、R-EP-C-024 の開始が確定した通知に限られること
  - 規則の具体的な文言と規則 ID、DR-13 決定 12 を反映した仕様書の記述の書き直し → specifications-endpoints.md と specifications-errors.md (別の変更)
  - 本 DR の変更の互換性の分類と版の更新 → specifications-governance.md の既存の規則による評価
  - `notification.not_cancellable` 以外のエラーに状態を載せるか → 未定 (必要になった時点で DR を追加する)
  - 複数のタブや端末からのキャンセルで、操作の主体を区別するか → specifications-endpoints.md §Open Questions #21
  - 単体取得による確認の MUST 化 → 本 DR の対象外とする。SHOULD を維持し、MUST 化の判断は DR-09 決定 4 と DR-16 Scope に従って別途行う

### Alternatives Considered

比較した案は、次の 4 つ。

| 案  | 内容                                                         | 判定   |
| --- | ------------------------------------------------------------ | ------ |
| (1) | 現状を維持する                                               | 不採用 |
| (2) | 拒否の応答に現在の状態を載せる                               | 採用   |
| (3) | `cancelled` のときだけ別の code にする                       | 不採用 |
| (4) | `cancelled` へのキャンセルを 200 の冪等な成功にする (ALT-02) | 不採用 |

- (1) 現状を維持する。「状態を区別したい」という要望を満たさないため不採用。
- (3) `cancelled` のときだけ別の code にする。新しい code の追加になり、DR-04 (識別子の追加を無条件に後方互換としない) の判断が要るため不採用。
- (4) `cancelled` へのキャンセルを 200 の冪等な成功にする。「今回成功したのか以前に成功したのか」を区別できなくなるため不採用。

### Rationale

採用する理由は、既存の code と拒否の条件を変えずに、状態を区別できることにある。
新しい code を足さないため、識別子の追加の評価 (DR-04 決定 8) は要らない。

状態を載せる形に拡張メンバーを使う理由は、エラー応答の拡張に既存の規則があることにある。
クライアントは未知の拡張メンバーを無視する (R-ER-C-049)。
拡張メンバーの追加は、既知のメンバー (`status`・`type`・`code`・`title`・`detail`・`instance`) の意味を変えない限り、後方互換な変更である (R-ER-C-050)。
本 DR は、既知のメンバーの意味、拒否の条件、再送時の保証、クライアントに求める対処を変えない。

`currentState` を必須にする理由は、任意にすると、状態を区別できない応答が残り、「状態を区別したい」という要望を満たせないことにある。
必須の範囲を絞る理由は、本 DR の問題がこの code の拒否だけにあることにある。

値を既存の状態の定義と一致させる理由は、通知の状態の語彙を 2 つ持たないことにある (R-EP-C-021)。

判定した時点の状態とする理由は、応答を受け取る時点まで状態が変わらないことを、契約が保証できないことにある。

`currentState` と単体取得・一覧取得の結果は、次の 2 つの理由で食い違い得る。2 つは別の問題。

- 観測時点の違い: `currentState` は判定した時点の状態であり、取得は別の時点の状態を返す。本 DR の決定 4 が扱う
- 反映の遅れ: 確定した終端状態の取得への反映は最終的であり、時間の上限はない (DR-16 決定 3)。本 DR は扱わず、DR-16 に従う

本 DR は取得 API に新たな同期保証を加えない。
なお、キャンセルが 200 を返した後に開始された取得では `cancelled` が保証される (DR-16 決定 2)。

`currentState` の値だけでは、開始の確定は分からない。
`notification.not_cancellable` の拒否は、R-EP-C-024 により、`scheduled` の通知については開始が確定した場合に限られる。
そのため、この code の拒否と `currentState: scheduled` の組み合わせは、開始が確定したことを示す。
`scheduled` の意味は変わらない (DR-13 決定 1)。

DR-09 決定 3 と R-EP-C-044 を変えない理由は、`currentState` が観測された通知の状態であることにある。
`currentState` は、状態遷移の原因や操作の主体を識別する情報ではない。
そのため、`currentState` があっても、再送の拒否から最初のキャンセルの結果は判断できない。

### Consequences

- Positive:
  - 3 分類に属する 4 つの通知状態 (`scheduled`・`dispatched`・`missed`・`cancelled`) を、拒否応答の `currentState` によって識別できる
  - 新しいエラー code を追加しない
  - 拒否の条件、DD-EP-04、R-EP-C-024、R-EP-C-026 を変えない
- Negative:
  - `currentState` は判定した時点の状態であり、応答を受け取る時点の状態とは限らない
  - `currentState` は、観測時点の違いと、DR-16 が許す取得への反映の遅れ (決定 3) により、単体取得・一覧取得の結果と食い違い得る。本 DR は取得 API に新たな同期保証を加えない
  - `currentState` の値からは、状態遷移の原因や操作の主体は分からない。複数のタブや端末からのキャンセルを区別することは、本 DR では解決しない
  - 既存のクライアントが受け取る `notification.not_cancellable` の応答のメンバーが増える
  - 本 DR を Accepted にすると、DR-13 決定 12 の記述と、仕様書の次の記述が食い違う。Accepted にする変更と同時に、仕様書を改訂する必要がある
    - specifications-endpoints.md の拒否が示すことの記述 (拒否の理由を応答で区別しない旨を含む) と §Open Questions #34
    - specifications-errors.md の `notification.not_cancellable` の記述
- Revisit Trigger:

  - 複数のタブや端末からのキャンセル (§Open Questions #21) で、操作の主体の識別が必要になったら、本 DR を見直す

  - 判定した時点と応答を受け取る時点の状態の食い違いが原因で、クライアントの判断に問題が実際に起きたら、本 DR を見直す

## DR-18: 同一通知について引き渡し処理の開始の確定を高々 1 回とすることを、外部から観測できる保証として API 契約に含める - 2026-11-16 18:19:59

**Phase**: spec
**Status**: Proposed

### Context

同一通知について、引き渡し処理の開始の確定を高々 1 回にすることを定めた規則は、契約に無い (specifications-endpoints.md §Open Questions #41)。
引き渡し処理の開始 (UD-NST-005) は、有効な開始の記録が、再開の後で復元できる状態となったことを指す。

既存の規則が保証する範囲は、次の 2 つに限られる。

- キャンセルの確定と開始の確定の排他 (R-EP-C-025、R-EP-I-007)
- 再開の後の場合 D と場合 E の区別 (R-EP-I-009)。場合 D は引き渡し処理の未開始、場合 E は開始の後で終端状態の確定の前に停止した場合を指す (DR-12 決定 5)

同じ通知について引き渡しの試みが並行したとき、開始の確定が 2 回になることを防ぐ規則は無い (specifications-endpoints.md 3.6.1 の末尾)。

開始が複数回確定することを許すと、同一通知について OS の通知 API が複数回呼び出される可能性を排除できない。
その結果は、利用者に重複した通知として観測され得る。

この一意性は、他の決定の前提にもなっている。
DR-14 は、遅れた引き渡しで通知が重複しないことを、次の場合に限って導いている (DR-14 Rationale の前提 1)。
その場合とは、同じ通知について開始の確定が 1 回だけの場合を指す。
DR-12 の Consequences も、場合 D と場合 E を取り違えると通知が重複し得ると述べている。

DR-14 は、この保証の採否を決めずに未定として残した (DR-14 Scope の Not decided here)。
v1 の契約を確定した後に保証を加えると、実装が満たすべき排他の要件が後から増える。
そのため、契約の確定前に採否を決める。

実現できるかの照合は、完了していない。
specifications-governance.md 3.3.3 の G-04 は、issue #5 と issue #7 のどちらの組も「未確認」である (DR-05、DD-GV-13)。
issue #7 (永続化) の下書きは、次のように書いている。

- SQLite のトランザクションで、登録・状態変更・キャンセルを原子的に保存する
- Risk として、起動時の再スケジュールは、復元と新規登録の調整がないと重複し得る

一方で、下書きには次の 3 点が書かれていない。

- 開始の記録という概念
- 開始の確定の排他
- 「still active」の通知が、開始の確定した通知を含むかどうか

そのため、下書きと本保証の間に矛盾は確定できない。
同時に、実現できると確かめる根拠も無い。

issue #5 (照会・キャンセル) の下書きも、発火の処理と開始の確定の並行の扱いを書いていない。
G-04 と issue #5 の組も、未確認のままとなっている。

### Decision

1. 決定 1: 同一通知について、引き渡し処理の開始の確定 (UD-NST-005) を高々 1 回とすることを、外部から観測できる保証として API 契約に含める (DR-03 決定 1)。
   - この保証は、有効な開始の記録 (UD-NST-005) に対する性質とする
   - 保証の範囲は、並行する引き渡しの試みと、停止・再起動をまたぐ場合の両方とする。どちらでも、同一通知の開始の確定は高々 1 回とする
   - 本 DR は、DR-13 のキャンセルの確定と開始の確定の排他 (R-EP-C-025、R-EP-I-007) を変えない。DR-14 が未規定とした、開始の確定どうしの一意性を補う
   - 場合 D と場合 E の区別 (R-EP-I-009) は変えない
   - 記録の破損などで開始の確定の有無を判定できない場合の回復は、既存の DR と同じく保証の対象外とし、本 DR で新たに保証しない
2. 決定 2: 決定 1 の保証は、OS への通知の引き渡しや表示の exactly-once 保証とは区別する。
   - 保証するのは、開始の確定が高々 1 回であることだけである
   - OS の通知 API の呼び出しの成否、OS の受理、画面への表示、利用者の確認は、保証の対象外とする (DR-12 決定 3、endpoints 3.6 の `dispatched` の意味)
3. 決定 3: 排他の方式と永続化の方式は、契約に定めない。implementation と issue #7 に委ねる (DR-03 決定 2)。
   契約は外部から観測できる保証だけを定義し、issue #7 の実装の責務とは分けて扱う。

### Scope

- Applies to: 同一通知の、引き渡し処理の開始の確定の回数
- Consistency: 次のものは変えない。
  - キャンセルの確定と開始の確定の排他 (DR-13 決定 4、R-EP-C-025、R-EP-I-007)
  - 場合 D と場合 E の区別と、場合 E の通知を呼び出し直さないこと (DR-12 決定 5、R-EP-I-008、R-EP-I-009)
  - 確定した終端状態の一意の復元 (R-EP-I-010)
  - 場合 D の遅れた引き渡し (DR-14 決定 1・決定 2・決定 5)
  - `dispatched` と `missed` の意味 (DR-12 決定 1・決定 3)
- Status: 本 DR は Proposed とする。Accepted への変更は、別途判断する (issue #7 との照合の結果を待つ)
- Not decided here:
  - 排他の方式 (ロック、トランザクション、一意制約など) → implementation と issue #7 (DR-03 決定 2)
  - 開始の記録の方法、復元の方法 → 永続化 (issue #7)
  - 記録の破損などで、開始の確定の有無を判定できなくなった場合の扱い → 永続化 (issue #7) の回復の方法 (R-EP-I-007、R-EP-I-009 と同じ)
  - 保証の文言と規則 ID (3.6.1 と R-EP-I-007〜R-EP-I-010 への反映、7 章 #41 の解決) → specifications-endpoints.md (本 DR とは別の変更)
  - G-04 の保証の内容の改訂と、issue #5・issue #7 との照合 → specifications-governance.md (本 DR とは別の変更)
  - 通知の有効期限と猶予時間 → 未定 (DR-14 決定 6 のとおり、別の設計判断とする)
  - Accepted への変更 → 別途判断 (issue #7 との照合の結果を待つ)

### Alternatives Considered

| 案  | 内容                                                          | 判定   |
| --- | ------------------------------------------------------------- | ------ |
| (1) | 開始の確定の一意性を保証する (契約に含める)                   | 採用   |
| (2) | 保証せず、前提として明記し、重複の可能性を残す                | 不採用 |
| (3) | OS への通知の引き渡し・表示まで含めた exactly-once を保証する | 不採用 |

- (2) 保証せず、前提として明記し、重複の可能性を残す。
  契約の範囲は小さく保てる。
  しかし、次の 3 つの理由で不採用とする。
  - DR-14 の「遅れた引き渡しで通知が重複しない」という導出が成り立たなくなる
  - クライアントは、重複通知を契約上の許容範囲として受け入れる必要が出る
  - v1 の確定後に保証を加えると、実装の排他の要件が後から増える
- (3) OS への通知の引き渡し・表示まで含めた exactly-once を保証する。
  利用者への重複を、より強く防げる。
  しかし、次の 3 つの理由で不採用とする。
  - OS の受理・表示・利用者の確認は、`dispatched` の意味に含めていない (endpoints 3.6、DR-12 決定 3)
  - OS ごとの差を契約が抱えることになる (DR-12 決定 7)
  - 呼び出しの成否を確認できない場面 (場合 E) では成り立たない

### Rationale

最大の理由は、DR-14 が導いた「遅れた引き渡しで通知が重複しない」ことの前提 1 を、契約の保証として確実に定められる点にある。
DR-14 の導出は、前提 1 と前提 2 が成り立つ場合に限られる。
前提 2 は、開始の記録が再開の後に正しく復元され、場合 D と場合 E を区別できることを指す。
本 DR の保証は、そのうち前提 1 を契約として定める。

保証を外部から観測できる性質だけとする理由は、契約が外部から観測できる保証だけを定義し、実現を兄弟 issue へ委ねる方針にある (DR-03 決定 1・決定 2)。
排他の方式を契約に含めると、実装の差し替えのたびに契約が変わる。

OS への通知の引き渡し・表示の保証と区別する理由は、`dispatched` の意味が OS の受理・表示・利用者の確認を含まないことにある (DR-12 決定 3)。
本決定では、サーバーが管理する開始確定の一意性を保証対象とする。
OS への通知の引き渡し・表示は別の事象であり、開始確定の一意性だけでは、それらの exactly-once を保証できない。
呼び出しの成否を確認できない場面 (場合 E) では、呼び出しの回数を契約が約束できない。
OS ごとの差も、契約が抱えることになる (DR-12 決定 7)。

契約の確定前に採否を決める理由は、確定後に保証を加えると、実装が満たす排他の要件が後から増えることにある。
開始確定の一意性を契約上の保証として提案することで、issue #7 の永続化設計に必要な制約を明確にする。
契約の確定前には、issue #7・#5 との責務、実現可能性、既知の制約を照合する。

既存の規則とは両立する。
一意性は、R-EP-C-025・R-EP-I-007 (キャンセルとの排他)、R-EP-I-008・R-EP-I-009 (場合 E と場合 D の区別)、R-EP-I-010 (一意の復元)、DR-14 決定 1・決定 2・決定 5 が前提とする「有効な開始の記録」に対する性質として定義できる。
照合では、これらの規則との矛盾は見つからなかった (2026-11-16 実施)。

Proposed に留める理由は、実現可能性を確かめていないことにある (DR-05 決定 3・決定 6)。
issue #7 の下書きは、トランザクションによる原子的な保存を書く。
しかし、開始の記録、開始の確定の排他、再スケジュールの対象から場合 E の通知を外すことは書いていない。
実現できると確かめる根拠が無いため、G-04 の issue #7 との照合結果は、未確認のままとする (DD-GV-13)。
実現可能性の確認は、Accepted にする前の条件とする。

### Consequences

- Positive:
  - 同一通知について、開始の確定が高々 1 回であることを、クライアントが契約から読み取れる
  - DR-14 の遅れた引き渡しで通知が重複しないという導出の前提 1 が、契約で定まる
  - v1 の確定前に保証を決めるため、実装の排他の要件が後から増えない
  - OS への引き渡し・表示の保証と区別するため、契約が OS ごとの差を抱えない
- Negative:
  - 保証するのは開始の確定が高々 1 回であることだけであり、利用者に通知が重複して見えないことは保証しない。OS の通知 API の呼び出しの成否、OS の受理、画面への表示、利用者の確認も保証しない
  - issue #7 は、開始の確定を排他にする設計を求められる。実現できるかは確かめていない
  - 記録の破損などで開始の確定の有無を判定できない場合の重複は、本 DR では防げない。その扱いは永続化 (issue #7) の回復の方法に委ねる
  - 本 DR を Accepted とする前に、issue #7 と issue #5 の照合の結果を、G-04 へ記録する必要がある
  - 保証の文言を specifications-endpoints.md に反映するまで、3.6.1 の末尾と 7 章 #41 の記述は、本 DR と食い違う。反映は本 DR とは別の変更とする
- Revisit Trigger:
  - issue #7 または issue #5 の照合で、開始の確定の一意性を実現できないと分かったら、本 DR を見直す
  - issue #7 の DR が、開始の記録を残さない設計を選んだら、本 DR を見直す
  - issue #7 の DR が、場合 E の通知を再スケジュールの対象に含める設計を選んだら、本 DR を見直す

### Open Questions

- 開始の確定の一意性を、issue #7 の永続化で実現できるか。次の 3 点を、issue #7 の DR で確かめる必要がある。
  - 開始の記録を残すこと
  - 場合 E の通知を、再スケジュールの対象から外すこと
  - 開始の確定を排他にすること
