> **Normative Statement**
> 本ドキュメントは拘束力のある要件を定義する。
> 実装は本ドキュメントに適合しなければならない (MUST)。
> RFC 2119 キーワードは本ドキュメントにのみ適用する。

## 1. Overview

### 1.1 Purpose

PWA と Keneek の間には、合意された REST API 契約が存在しない。そのため、サーバー、PWA、テストが共通で参照できる基準がない。
本モジュールは、通知 REST API の契約をドキュメントとして定義し、関係者が共通の基準に基づいて実装・検証できるようにする (GitHub issue #3、親 EPIC #2)。

### 1.2 Scope

- OpenAPI: 通知のバッチ登録、一覧取得、単体取得、キャンセルの各エンドポイントと、そのリクエストおよびレスポンス
- JSON Schema: `notifications` 配列のリクエスト形式
- エラー仕様: 共通エラー形式、エラー識別子とその分類・拡張規則、各エラーケースから HTTP ステータスコードへの対応、エラー識別子ごとのクライアントの対処方針
- 通知データ形状と状態の集合の定義
- 外部から観測できる振る舞いの保証 (再送時の振る舞い、キャンセルの結果の意味など)
- 通知 API は認証済みクライアントのみが利用できるという契約上の宣言と、認証の外部仕様
- API 契約のバージョン管理 (Keneek アプリのリリースバージョンとは独立)
- 契約のローカル検証

**Out of Scope**:

- 内部の実現方法の定義 (兄弟 issue の責務)
  - #4 (バッチ登録): 登録処理の原子性 (all-or-nothing) の実現方法、冪等性・重複排除の実現方法、バリデーションの判定アルゴリズム
  - #5 (照会・キャンセル): 照会・キャンセルの判定アルゴリズム、状態遷移の内部の実現方法
  - #6 (ローカルセキュリティ): loopback、CORS、Origin チェック、ペアリング、認証メカニズムの内部実装
  - #7 (永続化): SQLite 永続化
  - #8 (e2e テスト): e2e テスト
- ペアリングエンドポイントの定義 (#6 が定義する)
- 認証メカニズムの内部実装 (資格情報の発行、保存、検証) の定義
- 具体的な再試行のアルゴリズム (指数バックオフ、ジッター、最大試行回数など)。契約で保証する必要がある部分を除き、クライアント実装の責務とする
- 契約検証の CI 統合

## 2. Context

- Target Environment: ドキュメント成果物 (OpenAPI、JSON Schema、エラー仕様)。現時点でアプリケーションソース、
  OpenAPI/JSON Schema ファイル、HTTP サーバーコードは存在しない。
  Keneek (Flutter 製ローカル通知サービス) は、デバイス上の PWA からの通知スケジュールを管理・発火する。オフラインでも動作する
- Related Components: PWA クライアント、#4 (バッチ登録) の実装、#5 (照会・キャンセル) の実装、#6 (ローカルセキュリティ) の実装。

- Assumptions:
  - 契約の利用者は PWA クライアントのみであり、通信は JSON over HTTP のみとする。別のクライアントやメディアタイプが加わる場合は、本ドキュメントを改訂する
  - 契約検証の実行環境として、プロジェクトの既存ツールチェーン (Node.js と pnpm) が開発環境に導入されている
  - 既存の REQ/SPEC ID は存在しないため、ID の衝突はない

## 4. Functional Requirements

EARS Type は feature / event-driven / ubiquitous / unwanted behavior のいずれか、またはその組み合わせで示す。
unwanted behavior の要件は `NOT DO` で、契約に定義してはならない事項を示す。

### REQ-F-001: Notification Endpoints Definition

- EARS Type: feature

```text
GIVEN 通知 REST API の契約が OpenAPI ドキュメントとして提供される
  WHERE 通知 API が PWA と Keneek の間のインターフェースである
THEN 本契約は、通知のバッチ登録、一覧取得、単体取得、キャンセルの各エンドポイントと、
     それぞれのリクエストおよびレスポンスを OpenAPI で定義すること (SHALL)。
     各操作のインターフェースは、少なくとも次を満たすこと (SHALL)。
     - バッチ登録: リクエストは `notifications` 配列を受け取る。レスポンスは all-or-nothing を前提とした形状とし、
       成功時は入力の各要素に 1 対 1 で、入力と同じ順序で対応する通知ごとの結果 (通知 ID と状態を含む) を返す。
       失敗時は共通エラー形式の単一のエラーを返し、一部の要素だけが成功したことを表す形状を持たない。
       登録操作の原子性として、次を満たす。
       - 成功時のレスポンスを返した場合は、そのリクエストに含まれる通知がすべて登録されている
       - API が共通エラー形式 (`code` を持つ) の 4xx の失敗レスポンスを返した場合は、そのリクエストによる新規登録が 1 件も残っていない
       - 5xx の失敗レスポンスを返した場合も、そのリクエストに含まれる通知は、すべて登録されているか、
         1 件も登録されていないかのどちらかであり、一部の要素だけが登録された状態を残さない。
         ただし、どちらであるかはクライアントにとって確定しない
       5xx と応答を受け取れない場合 (応答の喪失、タイムアウト) は、4xx の失敗レスポンスと区別し、
       結果が確定しない場合として扱う
     - 一覧取得: 通知の配列を返す。各要素は REQ-F-005 のデータ形状に従う
     - 単体取得: 通知 ID で 1 件の通知を指定し、その通知を返す。存在しない場合はエラーを返す
     - キャンセル: 通知 ID で 1 件の通知を指定する。成功時はキャンセル後の通知を返し、
       キャンセルできない状態の通知を指定した場合はエラーを返す
```

**Rationale**: サーバー、PWA、テストが共有して実装できる基準を提供するため。
バッチ登録のレスポンスを all-or-nothing の形状にするのは、クライアントがバッチ全体の成功と失敗を一意に解釈できるようにするためである (DR-02)。
部分成功を表すレスポンス形状を持たないこと (形状) と、登録操作の原子性は別の保証として扱う。
原子性は、そのリクエストの通知が全件登録されるか、1 件も登録されないかのどちらかであることを保証する。
API が返す共通エラー形式の `4xx` の失敗レスポンスでは、そのリクエストによる新規登録が残らない。
`5xx` の失敗レスポンスでも原子性は保たれるが、登録の結果は確定しない。
形状だけでは、一部を登録した後に単一のエラーを返す実装を排除できないため、原子性も外部から観測できる保証として契約に含める (DR-03)。
原子性の実現方法は #4 (バッチ登録) が定義し、保証する (DR-02)。
原子性が対象とするのは、そのリクエストによる新規登録だけであり、既存の通知には及ばない。
応答を受け取れない場合はクライアントが結果を確定できないため、4xx の失敗レスポンスとは扱いを分ける。その場合の対処は REQ-F-004 の対処方針と、REQ-F-007 の再送時の振る舞いで定める。
原子性 (全件の登録または 0 件) と、クライアントが登録の結果を確定できることは、別の事柄として扱う。
5xx でも原子性は保たれるが、5xx を結果が確定しない場合に含めるのは、5xx だけでは登録済みか登録なしかを区別できないためである (DR-06 決定 9・決定 12)。
結果が確定しない場合の確定の手段は、REQ-F-007 の再送時の振る舞いで定める。
再送時の振る舞い (冪等性・重複排除) は、レスポンスの形状とは別の保証として REQ-F-007 に従って定義する。
一覧取得の絞り込み・並び順・ページング、パスと HTTP メソッドなどの詳細は Specifications で決定する。

**Acceptance Criteria**:

| AC ID  | Scenario                                                                                        |
| ------ | ----------------------------------------------------------------------------------------------- |
| AC-001 | 4 種類の操作が OpenAPI に定義されている                                                         |
| AC-010 | バッチ登録のレスポンスが all-or-nothing を前提とした形状である                                  |
| AC-025 | バッチ登録の原子性が、成功時・4xx 失敗時・結果未確定時 (5xx・応答なし) を区別して保証されている |
| AC-011 | 一覧取得・単体取得・キャンセルの最小インターフェースがある                                      |

### REQ-F-002: Notifications Array Request Schema

- EARS Type: feature

```text
GIVEN バッチ登録リクエストが `notifications` 配列を含む
  WHERE 契約が JSON Schema Draft 2020-12 で記述される
THEN 本契約は、`notifications` 配列のリクエスト形式を、
     OpenAPI とは独立に検証できる JSON Schema として定義すること (SHALL)。
```

**Rationale**: JSON Schema を単独で検証できるようにすることで、契約検証とテストでの再利用を容易にするため。配列の構造と検証制約 (1.3 Terms の定義による) の詳細は Specifications で決定する。

**Acceptance Criteria**:

| AC ID  | Scenario                                              |
| ------ | ----------------------------------------------------- |
| AC-002 | `notifications` 配列の JSON Schema を単独で検証できる |

### REQ-F-003: Common Error Response Format

- EARS Type: event-driven

```text
GIVEN 通知 API のいずれかのエンドポイントが契約に定義されている
  WHEN API がエラーレスポンスを返す
THEN 本契約は、すべてのエラーレスポンスに共通する単一の形式を定義すること (SHALL)。
     共通エラー形式は RFC 9457 (Problem Details for HTTP APIs) に従い、
     メディアタイプ `application/problem+json` で表すこと (SHALL)。
     共通エラー形式は、`status`・`type`・`code` を必須メンバーとして持ち (SHALL)、
     拡張メンバーの追加を許容すること (SHALL)。
     `status` の値は HTTP レスポンスのステータスコードと一致させること (SHALL)。
     `type` は Problem Type の URI とし、`code` はエラー識別子とすること (SHALL)。
     `type` と `code` は 1 対 1 で対応させ、その対応を Specifications の 1 か所で管理すること (SHALL)。
     `type` の URI に、参照先を解決できることは要求しない。
```

**Rationale**: クライアントがエラーケースごとに異なる形式を扱わずに済ませるため。
RFC 9457 を採用し、URI の命名方式と Keneek のエラー識別子を `type` と `code` に分ける理由は DR-01 に記録する。
`type` の URI を解決可能にしないのは、契約をネットワーク接続なしで検証するためである (REQ-F-012)。

**Acceptance Criteria**:

| AC ID  | Scenario                                                             |
| ------ | -------------------------------------------------------------------- |
| AC-003 | エラーレスポンスが共通形式で定義されている                           |
| AC-018 | RFC 9457 の評価結果と共通エラー形式の決定理由が記録されている        |
| AC-021 | 共通エラー形式の必須メンバーと `type`・`code` の対応が定義されている |

### REQ-F-004: Error-to-HTTP-Status Mapping

- EARS Type: event-driven

```text
GIVEN 共通エラー形式が定義されている
  WHEN 契約がエラーケースを定義する
THEN 本契約は、各エラーケースに対応するエラー識別子と HTTP ステータスコードを定義すること (SHALL)。
     契約が定義するエラーケースは、少なくとも次を含むこと (SHALL)。
     - リクエストが検証制約に違反する
     - リクエストが未認証である
     - 認証済みのリクエストが、対象の操作または通知について認可されていない
     - 指定した通知が存在しない
     - 通知の状態がキャンセルを受け付けない (発火済み、キャンセル済みなど)
     - サーバー内部でエラーが発生した
     各エラー識別子は、ちょうど 1 つのエラー分類に属すること (SHALL)。
     本契約は、エラー識別子ごとのクライアントの対処方針を定義すること (SHALL)。
     対処方針は、再試行可能性・再送安全性・結果の確定性を区別して扱い、HTTP ステータスコードだけに依存しないこと (SHALL)。
     本契約は、応答を受け取れない通信失敗など、エラー識別子を得られない場合の対処も定義すること (SHALL)。
     対処方針をエラーレスポンスの拡張メンバー (`retryable`・`action` など) で表さないこと (SHALL NOT)。
```

**Rationale**: クライアントがエラー識別子からエラーの種別と取るべき対処を判断できるようにするため。
分類や HTTP ステータスコードだけでは対処が一意に決まらない (5xx を一律に再試行可能とはできない) ため、分類と対処方針を分離する (DR-04)。
3 つの判断点すべてを各エラー識別子の必須属性とはせず、識別子ごとに必要なものを定める。
キャンセルできるかどうかの判定アルゴリズムは #5 (照会・キャンセル) の責務だが、判定結果を表すエラー識別子とステータスコードは契約が定義する。
各ケースの具体的なステータスコード、エラー識別子と分類の値、対処方針は Specifications で決定する。
`Retry-After` などの標準 HTTP ヘッダーで動的な情報を返すことは妨げない。

**Acceptance Criteria**:

| AC ID  | Scenario                                                       |
| ------ | -------------------------------------------------------------- |
| AC-003 | エラーレスポンスが共通形式で定義されている                     |
| AC-017 | 最小エラーケースのそれぞれに識別子とステータスコードが対応する |
| AC-022 | エラー識別子ごとに分類と対処方針が定義されている               |

### REQ-F-005: Notification Data Shape and States

- EARS Type: ubiquitous

```text
GIVEN 通知が API のリクエストまたはレスポンスに含まれる
THEN 本契約は、通知のデータ形状と状態の集合を定義すること (SHALL)。
     状態遷移規則は REQ-F-007 に従って定義し、遷移の内部の実現方法は定義しない。
```

**Rationale**: #7 (永続化) は契約のデータ形状と状態の集合に間接的に依存するため、これらを契約で確定しておく必要がある。状態の集合と状態遷移規則の区別は 1.3 Terms による。

**Acceptance Criteria**:

| AC ID  | Scenario                                           |
| ------ | -------------------------------------------------- |
| AC-008 | 通知のデータ形状と状態の集合が契約に定義されている |

### REQ-F-006: Room for Sibling Needs

- EARS Type: feature

```text
GIVEN 兄弟 issue (#4 (バッチ登録)、#6 (ローカルセキュリティ)) が冪等性やセキュリティに関するエラーを必要とする
  WHERE 契約がエラー識別子の命名規則と拡張規則を定義する
THEN 本契約は、エラー識別子の命名規則と拡張規則を定義し (SHALL)、
     兄弟 issue が既存のエラー識別子と共通エラー形式の必須メンバーを変更せずに、
     新しいエラー識別子を追加できるようにすること (SHALL)。
     拡張規則は、エラー識別子の追加と既存 API 操作の変更を区別して評価し (SHALL)、
     新しいエラー識別子の追加を後方互換とするのは、既存の成功条件・再送時の保証・既存クライアントに求める対処の
     いずれも変えない場合に限ること (SHALL)。
     既存クライアントから観測できる振る舞い、または既存クライアントに求める対処が変わる変更は、
     識別子の追加を伴うかどうかにかかわらず破壊的変更として扱うこと (SHALL)。
     拡張規則は、クライアントが未知のエラー識別子を受け取った場合の扱いとして、次を示すこと (SHALL)。
     - 分類が既知の契約に従って解釈できる場合は、分類に基づいて扱う
     - 分類が不明、または解釈できない場合は、HTTP ステータスコードを参照する
     - WHEN 対象の操作が冪等でなく、再送安全性を確認できない場合、その操作を無条件に自動で再試行しない
     - 未知のエラー拡張メンバーは無視する。既知のメンバーの意味は変えない
     それらのエラーを生む内部の実現方法は定義しない。
```

**Rationale**: 兄弟 issue が契約を壊さずに必要なエラーを追加できる余地を残すため。
識別子の追加でも、既存の成功条件や求める対処が変われば既存クライアントは変更なしに動作を続けられないため、無条件に後方互換とはしない (DR-04)。
HTTP ステータスコードだけでは再送安全性と処理結果の確定性を保証できないため、冪等でない操作の自動再試行を制限する。
命名規則は、兄弟 issue ごとに識別子が衝突しない構造 (責務ごとの区分など) とし、未知の識別子から分類を判別できるようにする。
具体的な命名規則は Specifications で決定する。

**Acceptance Criteria**:

| AC ID  | Scenario                                             |
| ------ | ---------------------------------------------------- |
| AC-012 | エラー識別子の追加が互換性の条件に従って評価される   |
| AC-023 | 未知のエラー識別子と拡張メンバーの扱いが示されている |

### REQ-F-007: Observable Guarantees and Internal Realization Boundary

- EARS Type: feature / unwanted behavior

```text
GIVEN 通知 API の振る舞いの結果が、リクエストまたはレスポンスを通してクライアントから観測できる
THEN 本契約は、インターフェースに加えて、外部から観測できる保証を定義すること (SHALL)。
     外部から観測できる保証は、少なくとも次を含むこと (SHALL)。
     - 各操作の再送時にクライアントから観測できる振る舞い (冪等性・重複排除の保証の有無と結果)
     - キャンセルの結果の意味
     - 状態遷移規則 (各状態で受け付ける操作と、操作の結果どの状態になるか)
     - 入力を拒否する条件のうち外部から観測できる判定結果 (どの入力をどのエラー識別子で拒否するか)
     - エラー識別子ごとのクライアントの対処方針 (REQ-F-004)
  NOT DO 兄弟 issue (#4、#5、#6、#7、#8) が担う内部の実現方法を契約に定義すること
THEN 本契約は、登録処理の原子性の実現方法、冪等性・重複排除の実現方法、バリデーションの判定アルゴリズム、
     照会・キャンセルの判定アルゴリズム、状態遷移の内部の実現方法、認証メカニズムの内部実装、ローカルセキュリティ、
     永続化を定義しないこと (SHALL NOT)。
```

**Rationale**: 兄弟 issue が後から観測できる振る舞いを決めると、契約が後から破壊的に変わる (DR-03)。
外部から観測できる保証は契約で先に定め、内部の実現方法は各兄弟 issue に委ねることで、責務の重複と矛盾を避ける。
どの入力が拒否され、どの状態でどの操作を受け付けるかはクライアントが観測できるため、判定結果と遷移規則は契約に含め、判定アルゴリズムだけを兄弟 issue に残す。
未確定の保証は Open Questions で管理し、合意した判断は DR に、確定した API の振る舞いは Specifications に記録する。
DR の Accepted は設計方針の採用を表し、関連する個別仕様がすべて確定したことは表さない。

**Acceptance Criteria**:

| AC ID  | Scenario                                               |
| ------ | ------------------------------------------------------ |
| AC-004 | 契約が内部の実現方法を定義していない                   |
| AC-019 | 外部から観測できる保証が操作ごとに契約に定義されている |

### REQ-F-008: Authentication Requirement Declaration

- EARS Type: ubiquitous

```text
GIVEN 各通知 API エンドポイントが契約に定義されている
THEN 本契約は、すべての通知エンドポイントが認証を必要とすることを宣言し (SHALL)、
     認証の外部仕様 (認証時にリクエストへ含める情報、資格情報を送る形式、認証失敗時の外部レスポンス) を定義すること (SHALL)。
     未認証リクエストへのレスポンスは、共通エラー形式とエラー識別子で定義すること (SHALL)。
     認証の失敗と認可の失敗を区別し、それぞれ別のエラー識別子で定義すること (SHALL)。
     認証メカニズムの内部実装 (資格情報の発行、保存、検証) とペアリングエンドポイントは定義しない。
```

**Rationale**: 認証済みクライアントのみが通知 API を利用できることを、契約として固定するため。
資格情報の送り方と認証失敗時の応答はクライアントが直接扱うため、外部から観測できる保証として契約が定義する (DR-03)。
認証メカニズムの内部実装は #6 (ローカルセキュリティ) が定義する。
認証方式によって外部仕様が変わる場合は、#6 と整合を確認する。
認証の失敗と認可の失敗を区別する理由は、クライアントの対処 (再認証か、操作の中止か) が異なる点にある。
通知を所有者ごとに分離するか (認可の単位) は Open Questions で扱う。

**Acceptance Criteria**:

| AC ID  | Scenario                                                                 |
| ------ | ------------------------------------------------------------------------ |
| AC-006 | 通知エンドポイントが認証必須として宣言されている                         |
| AC-013 | 未認証・未認可のリクエストへのレスポンスが共通エラー形式で定義されている |

### REQ-F-009: Contract as Single Source of Truth

- EARS Type: event-driven

```text
GIVEN 本契約が API の唯一の正 (single source of truth) である
  WHEN 兄弟 issue がインターフェースまたは外部から観測できる保証の変更を必要とする
THEN 契約を先に更新すること (SHALL)。
     それらを変更する実装の変更は、契約の変更と同じプルリクエストに含めるか、
     契約の変更がマージされた後に提出すること (SHALL)。
     契約を確定する前に、契約に書いた保証が各兄弟 issue の責務、実現可能性、既知の制約と矛盾しないことを確認すること (SHALL)。
     この整合確認の記録を Specifications に残すこと (SHALL)。
     記録は、保証と照合対象の兄弟 issue の組ごとに、照合結果を「整合」「矛盾あり」「未確認」のいずれかで示すこと (SHALL)。
     照合対象は #4 (バッチ登録)、#5 (照会・キャンセル)、#6 (ローカルセキュリティ) とし、
     #7 (永続化) は保証が永続化の責務へ依存する場合だけ加えること (SHALL)。
     契約の確定は、照合対象の保証に「未確認」が残っておらず、「矛盾あり」がすべて解消されていることを条件とすること (SHALL)。
     この確認と記録は、兄弟 issue の実装の完了や内部設計の確定を要求しない。
```

**Rationale**: 実装と契約の乖離を防ぎ、すべての関係者が同じ基準を参照できるようにするため。順序はプルリクエストのレビューで確認する。
契約の保証を実現するのは兄弟 issue であるため、確定前に整合を確かめ、確定後の契約変更を減らす (DR-03)。
記録の所在と照合結果の区別は DR-05 による。
e2e テストを担う #8 は契約を検証する側であり、照合対象に含めない。e2e テストで見つかった契約の矛盾は、契約の確定前に解消する。
記録の形式の詳細は Specifications で決定し、照合の具体的な手順は契約を確定するまでに決める。

**Acceptance Criteria**:

| AC ID  | Scenario                                          |
| ------ | ------------------------------------------------- |
| AC-009 | インターフェース変更時に契約が先に更新される      |
| AC-020 | 契約の確定前に兄弟 issue との整合が確認されている |

### REQ-F-010: Independent Contract Versioning

- EARS Type: feature

GIVEN API 契約が Keneek アプリのリリースバージョンとは別のバージョンを持つ

### REQ-F-011: Breaking Change Handling

- EARS Type: event-driven

```text
GIVEN 本契約が後方互換性を基本方針とする
  WHEN 破壊的変更が導入される
THEN 新しい API メジャーバージョンを導入し (SHALL)、既存クライアントへの影響を管理すること (SHALL)。
```

**Rationale**: 破壊的変更を既存クライアントから分離し、影響範囲を管理するため。
「影響を管理する」(UD-024) は、次の 3 つを行うことをいう。

- (a) 契約の Change History に変更内容を記録する
- (b) 旧 API メジャーバージョンが非推奨であることを契約に明示する
- (c) 旧バージョンから新バージョンへの移行手順を契約に記述する

破壊的変更の判断基準、非推奨期間、バージョン間の互換性確認方法は Specifications で決定する。

**Acceptance Criteria**:

| AC ID  | Scenario                                        |
| ------ | ----------------------------------------------- |
| AC-005 | 破壊的変更で API メジャーバージョンが新設される |

### REQ-F-012: Local Contract Validation

- EARS Type: event-driven

```text
GIVEN 契約ドキュメント (OpenAPI、JSON Schema) が存在する
  WHEN 開発者がローカルで契約検証を実行する
THEN 検証は、契約ドキュメントに違反 (1.3 Terms の定義による) がないかを検査し (SHALL)、
     違反があれば失敗を報告すること (SHALL)。
```

**Rationale**: 契約の品質を実装前に確認させるため。
契約は OpenAPI、JSON Schema、エラー仕様の 3 つからなるため、各成果物の標準適合だけでなく、成果物間の不一致も違反として検査する。
Keneek はオフラインでも動作するため、検証もネットワーク接続なしで完結させる。CI 統合は本モジュールの対象外。

**Acceptance Criteria**:

| AC ID  | Scenario                       |
| ------ | ------------------------------ |
| AC-007 | 契約違反があると検証が失敗する |

## 5. Non-Functional Requirements

### REQ-NF-001: Maintainability

契約ドキュメントは、プロジェクトの formatter (dprint) と linter の対象に含まれ、警告 0 件で通過しなければならない (MUST)。
ここでいう linter には、契約検証に使う linter を含む。

### REQ-NF-002: Testability

契約検証は、単一の pnpm スクリプトで完了し、失敗時には非ゼロの終了コードを返さなければならない (MUST)。

## 6. Constraints

### REQ-C-001: Standards Conformance

API 契約は OpenAPI 3.1.x と JSON Schema Draft 2020-12 に準拠しなければならない (MUST)。
OpenAPI ドキュメントは `openapi` フィールドで 3.1.x を、JSON Schema は `$schema` で Draft 2020-12 を宣言する。
OpenAPI の正確なパッチバージョンは Specifications で決定する。

### REQ-C-002: Independent Schema Validation

JSON Schema は OpenAPI とは独立に検証可能でなければならない (MUST)。ファイル構成と参照方法は Specifications で決定する。

### REQ-C-003: Local Validation Only

契約検証はローカル実行のみを対象とし、CI 統合は本モジュールの対象外とする。本モジュールは、契約検証を実行する CI ワークフローを追加しない。

### REQ-C-004: Formatter Target Placement

契約ドキュメントは、REQ-NF-001 を満たすため、プロジェクトの formatter および linter が対象から除外するディレクトリに配置してはならない (MUST NOT)。具体的な配置は Specifications で決定する。

### REQ-C-005: Authentication and Pairing Boundary

ペアリングエンドポイントおよび認証メカニズムの内部実装 (資格情報の発行、保存、検証) は #6 (ローカルセキュリティ) が定義する。
本契約はそれらを定義してはならない (MUST NOT)。
認証の外部仕様 (認証時にリクエストへ含める情報、資格情報を送る形式、認証失敗時の外部レスポンス) は本契約が定義する (REQ-F-008、DR-03)。
