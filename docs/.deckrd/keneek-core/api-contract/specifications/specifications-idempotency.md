## 1. Overview

### 1.1 Purpose

本書は、バッチ登録の冪等性と再送の保証の正本とする。DR-06 を具体化する。
ほかの分割ファイルは、再送と冪等性の保証を本書への参照と短い要約で示し、同じ保証を再定義しない。

担当する要件は次のとおりとする。

- REQ-F-001: バッチ登録の原子性の外部保証のうち、再送と回復に関わる部分
- REQ-F-007: 各操作の再送時に観測できる振る舞いのうち、バッチ登録の部分

本書は、振る舞いの規則と分類の意味を定義する。

## 2. Design Principles

### 2.1 保証の境界 (IP-0)

冪等性は、保持の保証の期間内の重複登録を防ぐ仕組みとする。
あらゆる通信の遅延や回復できない障害について、登録の成否を確定できることまでは保証しない。

本書のすべての規則は、この境界の内側で定める。ほかの分割ファイルも、この境界を超える保証を書かない。

- 保証する: 保持の保証が有効な間の重複登録の防止、成功結果の再現、各応答の意味の一貫性、回復が完了した場合の結果の整合
- 保証しない: 通信の遅延による到着時刻、保持の保証が終わった後の重複の防止、回復の完了とその期限、すべての論理操作の結果を確定できること

### 2.2 Design Assumptions

- 契約の利用者は PWA であり、通信は JSON over HTTP とする。
- 応答を受け取れなかった送信が、後からサーバーに届くことはあり得る。本書はこれが起きないことを前提にしない。
- クライアントの時計とサーバーの時計は一致しない。再送の開始の期限は、クライアントが最初の送信からの経過で判断する。

### 4.2 IP-2 応答の一貫性

| Rule ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-ID-C-201 | `specifications-errors.md` 4.1 の Step 1〜8 を通過したバッチ登録の送信には、キーの状態ごとに下の表のとおり応答すること (MUST)。Step 1〜8 で拒否した送信は R-ID-I-501 に従う                                                                                                                                                                                                                                     |
| R-ID-C-202 | 成功が確定したキーに同じ本文で送られたときは、初回の 201 と初回のレスポンス本文の写しを返し、新たな登録を行わないこと (MUST)。この再現は入力内容の検証より先に返す (`specifications-errors.md` R-ER-C-009)。通知の現在の状態は GET で取得する。同じ本文でも、成功が確定していないキーには 201 を再現しない (DR-06 決定 6)                                                                                       |
| R-ID-C-203 | `idempotency.key_conflict` は、成功が確定したキーに異なる本文が送られた場合だけに返すこと (MUST)。処理中または回復待ちのキーには返さない (DR-06 決定 8、`specifications-errors.md` R-ER-C-012)                                                                                                                                                                                                                  |
| R-ID-C-204 | 処理中または回復待ちのキーへの送信には、入力内容の検証で拒否されない場合、本文が同じでも異なっても `server.unavailable` を返し、新規の登録として処理しないこと (MUST)。入力内容の検証で拒否される場合は R-ID-C-205 に従う。この 503 は先行の登録処理の失敗を意味しない。入力内容の検証で拒否される送信の処理中にも、ほかの送信が 503 を受け取ることがある (DR-06 決定 7、`specifications-errors.md` R-ER-C-013) |
| R-ID-C-205 | 入力内容の検証の 400 は、R-ID-C-203 の 409 と R-ID-C-204 の 503 のどちらよりも先に返すこと (MUST)。本文が同じでも異なっても同じとする。優先順位の正本は `specifications-errors.md` 4.1 とする (DR-06 決定 7)                                                                                                                                                                                                    |
| R-ID-C-206 | 「同じ本文」(UD-IDM-009) の判定は、HTTP のメッセージ本文 (転送のための符号化を外したもの。Content-Encoding は identity だけ) のバイト列の比較で行うこと (MUST)。ハッシュの一致だけで同じと判定しないこと (MUST NOT) (DR-06 決定 10・決定 11)                                                                                                                                                                    |

キーの状態ごとの応答 (R-ID-C-201):

| キーの状態                        | 同じ本文                                                   | 異なる本文 (入力内容が有効)    | 異なる本文 (入力内容が不正) |
| --------------------------------- | ---------------------------------------------------------- | ------------------------------ | --------------------------- |
| 未記録                            | 新規の登録として処理する (入力内容が不正なら 400)          | 新規の登録として処理する       | 400 `request.invalid`       |
| 処理中                            | 503 `server.unavailable` (入力内容が不正なら 400)          | 503 `server.unavailable`       | 400 `request.invalid`       |
| 回復待ち                          | 503 `server.unavailable` (入力内容が不正なら 400)          | 503 `server.unavailable`       | 400 `request.invalid`       |
| 成功が確定                        | 初回の 201 と本文の写し (入力内容の検証より先。R-ID-C-202) | 409 `idempotency.key_conflict` | 400 `request.invalid`       |
| 登録なしが確定 (サーバー側で把握) | 新規の登録として処理する (入力内容が不正なら 400)          | 新規の登録として処理する       | 400 `request.invalid`       |

キーの状態の意味は UD-IDM-011 による。「登録なしが確定 (サーバー側で把握)」は UD-IDM-016 にあたる。
未記録と登録なしが確定のキーには、比較する先行の本文が無い (比較対象なし)。この 2 行では、本文の同じ・異なるは応答を分けず、入力内容の有効・不正だけが応答を分ける。

| R-ID-C-301 | クライアントは、送信ごとに下の表のとおり応答を分類すること (MUST)。表の右の列は、その応答だけから言えることを示す。1 つの応答だけで、論理操作が今後も登録されないとは判断しない。成功の確定 (クライアント) は、後から受け取った応答の分類によって変えない。登録なしの確定の扱いは R-ID-C-303 と R-ID-C-304 による (DR-06 決定 9)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| R-ID-C-302 | 再送は、同じキーと同じ本文のバイト列で行うこと (MUST)。再送を開始してよいのは、最初の送信から 24 時間以内とする (再送開始期限。UD-IDM-018)。この期限は再送を開始する期限であり、キーの照合が保持の保証の期間内に行われることは保証しない。`Retry-After` の待機は `specifications-errors.md` R-ER-C-037 に従う (SHOULD)。待機を終えると期限を過ぎる場合は、再送しないこと。期限は延長しない。その時点で結果が未確定の場合は、未確定のまま扱う (DR-06 決定 1・決定 9)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| R-ID-C-303 | C1〜C3 をすべて満たす場合に限り、クライアントは対象の論理操作 (K、B) による登録が成立していないと判断できる (登録なしの確定。UD-IDM-015)。この判断は、判断の対象とした送信についての結論とする。判断の後に同じ K・B で新しい送信を始めた場合、その送信の結果まで登録なしとは判断しない。これは、K で別の本文の登録が成立していないことまでは意味しない。サーバー側で把握する「登録なしが確定」(UD-IDM-016) とは区別する (DR-06 決定 9)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| R-ID-C-304 | 24 時間の経過そのものでは、結果の判断は変わらない。最初の送信から 24 時間を過ぎた後に受け取った応答も、R-ID-C-301 と R-ID-C-303 に従って判断する。結果の確定前にクライアントが停止しても、停止によって結果は確定しない。成功の確定 (クライアント。契約に適合する 201) は、後から受け取った 503 などの応答、24 時間の経過、停止によって未確定に戻らない。登録なしの確定は、R-ID-C-303 のとおり、判断の対象とした送信についての結論とする。論理操作の現在の結果は、その時点までのすべての送信にもとづいて判断する。登録なしの確定の後に同じ K・B で新しい送信を始めた場合は、その送信の応答も含めて判断し直す (契約に適合する 201 を受け取れば成功の確定とする)。一覧取得と単体取得は、論理操作の結果を確定する手段として保証しない (DR-06 決定 9、Scope)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| R-ID-C-305 | 同じ登録の意図を別の論理操作で登録し直すこと (UD-IDM-006) の可否は、新しい登録の送信を開始する時点で判断する。その時点までに開始した、先行の論理操作のすべての送信について C1〜C3 を満たす場合に限り、登録し直しの送信を開始してよい (R-ID-C-303)。登録なしを判断した後に、先行の論理操作の送信を追加で開始した場合は、過去の判断だけを根拠に登録し直さない。追加した送信も含めて、この条件を満たしてから登録し直す。登録し直しには新しいキーを推奨する。同じキーを別の本文で使うことは、DR-06 決定 1 が定める例外として、この登録し直しに限って許す。結果が確定しないまま本文やキーを変えて登録し直すことは安全と保証しない (重複登録になり得る)。先行の論理操作の成功が確定している場合は、登録し直さず、既存の成功結果を扱う。これらはクライアントの行動の条件とする。条件の成立を確かめる方法 (クライアント内部の排他制御など) は定めない。サーバーは、条件を満たさない登録し直しを拒否することを保証しない。冪等性はキー単位 (UD-IDM-001) であり、同じ登録の意図でも、キーの異なる論理操作の間の重複は防がない。登録し直しの後に、先行の論理操作の送信を新たに始めると、同じ登録の意図の登録が重複し得る。本契約はこれを防がない (DR-06 決定 3・決定 9)。無関係な新しい通知の登録は、別の登録の意図による独立した論理操作であり、新しいキーで送る。この制限を受けない (DR-06 決定 1・決定 9) |
| R-ID-C-306 | `idempotency.key_conflict` を受け取った送信は登録していないが、そのキーでは別の本文の成功が確定している。同じ登録の意図を新しいキーで登録し直す場合は、R-ID-C-303 と R-ID-C-305 に従う。先行の論理操作が未確定なら、新しいキーでの登録し直しは重複登録につながり得る                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

C1〜C3 (R-ID-C-303):

- C1: クライアントが、透過的な自動再送 (HTTP ライブラリ、Service Worker、プロキシ) を無効にしている。そのうえで、論理操作のすべての送信とその完了の状態を自ら管理している
- C2: すべての送信が応答を受け取っている。完了していない送信は無い。クライアントが中断した送信は、完了していない送信に数える
- C3: すべての応答が、API が生成した共通エラー形式の 4xx である

送信ごとの応答の分類 (R-ID-C-301):

| 応答                                                       | その送信について分かること                                 | この応答だけからの判断                |
| ---------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------- |
| 契約に適合する 201                                         | 成功 (新規の登録、または初回の再現)                        | 成功の確定 (クライアント。UD-IDM-013) |
| API が生成した共通エラー形式の 4xx (`code` を持つ)         | その送信は登録していない                                   | C1〜C3 を判定する                     |
| 409 `idempotency.key_conflict`                             | その送信は登録していない。K で別の本文の成功が確定している | C1〜C3 を判定する。K を使わない       |
| 503 を含む 5xx                                             | 分からない                                                 | この応答だけでは確定しない            |
| problem 形式でないエラー応答 (4xx・5xx)                    | 分からない                                                 | この応答だけでは確定しない            |
| 上のどれにも当てはまらない応答 (契約に適合しない 2xx など) | 分からない                                                 | この応答だけでは確定しない            |
| 応答なし                                                   | 分からない                                                 | この応答だけでは確定しない            |

### 4.6 実装で保証すべき事項 (R-ID-I)

本節の規則も、契約として拘束力を持つ (MUST)。本節は、サーバーが内部で維持しなければならない性質と、実現方法を #4・#7 へ委ねる境界を定める。
個々のレスポンスからは直接観測できない。照合は `specifications-governance.md` G-03、G-16、G-17 で行い、照合が済むまで確定した保証として扱わない (DR-05)。
