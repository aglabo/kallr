## 1. Overview

### 1.1 Purpose

通知 REST API が返すエラーと、API の認証に関する外部仕様を定義する。
対象は次の 5 つとする。

- 共通エラー形式
- エラー識別子 (`code`) の命名規則、分類、`type` との対応
- エラー識別子ごとの対処方針と、応答を受け取れない場合の対処
- エラー識別子の拡張規則
- 認証の外部仕様、および複数のエラー条件が同時に成立したときの外部応答の優先順位

PWA 開発者と Keneek 実装者 (issue #4〜issue #7) は、本仕様だけを見てエラー処理と認証の外部の振る舞いを実装できる。

### 1.2 Scope

本書は、振る舞いの規則と分類の意味を定義する。
実装の詳細は対象外とする。

## 2. Design Principles

### 2.1 Classification Philosophy

- エラーの分類とクライアントの対処は別の事柄として扱う (DR-04)。分類はエラーの種別を表す。対処は `code` ごとの対処方針が表す。
- 分類は `code` の接頭辞で表す。クライアントは未知の `code` からも分類を判別できる。各 `code` はちょうど 1 つの分類に属する。
- 対処方針は、再試行可能性・再送安全性・結果の確定性の 3 つの判断点として独立に持つ。HTTP ステータスコードだけでは対処を決めない。5xx を一律に再試行可能としない。
- 対処方針は契約 (本書) に置き、エラーレスポンスの拡張メンバーには載せない。
- `code` と `type` の対応は、契約全体で 1 か所 (本書 4.5 のエラーカタログ表) だけで管理する。
- Accepted の DR の決定は再定義しない。本書は、DR が specifications に委ねた事項だけを決める。

### 2.2 Design Assumptions

- 契約の利用者は PWA クライアントであり、通信は JSON over HTTP である。
- 本書が定める優先順位は、複数のエラー条件が同時に成立したときに返す外部応答の優先順位である。サーバー内部の判定順序を表さない。
- 通知は所有者ごとに分離しない (DD-ER-11)。認証済みクライアントは、すべての通知を同じ条件で扱える。この事項は解決済みとして記録する。
- 資格情報の送信形式として HTTP Bearer を **候補** とする。issue #6 との照合は「未確認」であり、確定した保証として扱わない (R-ER-C-052、DR-05)。
- 403 の発生条件の詳細、CORS プリフライトで許可する Origin の判定は issue #6 が決める。本書は外部の応答の形だけを定める。

<!-- textlint-disable ja-technical-writing/sentence-length -->

- 成功の記録の保持は、永続化の責務に依存する。issue #4・issue #7 との照合は「未確認」である。
  保持の内容は、サーバーで成功が確定した時点 (UD-IDM-014) から最低 24 時間、サーバー再起動後も保持することとする (`specifications-endpoints.md` R-EP-I-002)。

<!-- textlint-enable ja-technical-writing/sentence-length -->

- 本書でいう操作は、バッチ登録、一覧取得、単体取得、キャンセルの 4 つである。パス、メソッド、成功時の応答は `specifications-endpoints.md` が定める。
- 「(既定値・レビュー対象)」と付けた具体値は、仕様生成時の既定値であり、レビューで確認する。

### 2.4 Non-Goals

> **Derivation**: All items below originate from REQUIREMENTS Section "Out of Scope".

- 認証メカニズムの内部実装 (資格情報の発行、保存、検証) を定義しない ← REQ: Out of Scope (認証メカニズムの内部実装)
- ペアリングエンドポイントを定義しない ← REQ: Out of Scope (ペアリングエンドポイント)
- loopback、CORS、Origin チェックなど、ローカルセキュリティの内部の実現方法を定義しない ← REQ: Out of Scope (issue #6)
- 冪等性・重複排除の実現方法、バリデーションの判定アルゴリズム、登録処理の原子性の実現方法を定義しない ← REQ: Out of Scope (issue #4)
- 照会・キャンセルの判定アルゴリズム、状態遷移の内部の実現方法を定義しない ← REQ: Out of Scope (issue #5)
- 具体的な再試行のアルゴリズム (指数バックオフ、ジッター、最大試行回数) を定義しない。契約で保証する必要がある部分だけを本書が定める ← REQ: Out of Scope (再試行のアルゴリズム)
- 契約検証の CI 統合を定義しない ← REQ: Out of Scope (CI 統合)

### 2.7 DD to DR Promotion Criteria

> **Purpose**: Guidelines for determining when a DD should be promoted to a formal DR.
> Promotion is a **human judgment** — these criteria inform, not automate.

**Consider promoting a DD when:**

1. Cross-specification Impact — The decision affects multiple specifications or modules
2. Architectural Significance — The decision constrains future design choices
3. Non-trivial Alternatives — Multiple viable options existed
4. Stakeholder Visibility Required — The decision should be reviewable by external parties

**Keep as DD when:**

- Decision is local to this specification only
- No significant alternatives existed
- Rationale is self-evident from context

> **Action**: To promote, run `/deckrd dr --add` with the DD context,
> then update DD Status to `Promoted → DR-xx`.

## 3. Behavioral Specification

### 3.1 Input Domain

- Input Type: API が処理できる HTTP リクエスト (4 つの操作と、未知のパス・メソッドへのリクエストを含む)。および、クライアントが応答を受け取れない通信失敗
- Assumptions:
  - HTTP メッセージを受理できないプロトコルレベルのエラーは対象外とする
  - CORS プリフライトは認証優先規則の例外とし、4.10 で別に扱う
  - 認証方式は Bearer を候補とし、issue #6 との照合まで確定しない

### 3.2 Output Semantics

- Output Meaning: API が生成するエラー応答は、すべて `application/problem+json` で返る。クライアントは、安定した識別子である `code` で分岐する。応答を受け取れない場合はエラー識別子が得られず、処理結果は確定しない
- Possible Outcomes:
  - 本書 4.5 のエラーカタログ表に載る `code` を持つ problem 応答 (400、401、403、404、405、409、413、415、500、503)
  - 応答なし (タイムアウト、接続断など): 結果未確定として扱う
  - problem 形式でない応答 (プロキシなどが生成): エラー識別子を得られない場合として扱う

### 3.3 Interface Constraints

- プロトコル: HTTP 上の JSON (通知 REST API)。エラー応答はメディアタイプ `application/problem+json`
- 本書の対象範囲: 4 つの操作に共通のエラー応答と認証。操作ごとの成功応答、パス、メソッドは対象外
- 外部サービスの呼び出し: なし。共有データストア: なし
- 標準ヘッダー: 401 には `WWW-Authenticate`、405 には `Allow` を付ける (RFC 9110)

### 4.1 Error Response Precedence

API が処理できるリクエストで、複数のエラー条件が同時に成立したときは、次の順序で最初に成立した条件の応答を返さなければならない (MUST)。
この順序は、外部応答の優先順位を定める。サーバー内部の判定順序を定めない。

| Rule ID    | Step | Condition                                                                                                                                                                                                                                                                                           | Outcome                                                                                           |
| ---------- | ---: | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| R-ER-C-001 |    1 | リクエストが認証を満たさない                                                                                                                                                                                                                                                                        | 401 `auth.unauthenticated`                                                                        |
| R-ER-C-002 |    2 | リクエストのパスが、契約に定義されたどのパスにも該当しない                                                                                                                                                                                                                                          | 404 `request.route_not_found`                                                                     |
| R-ER-C-003 |    3 | パスは該当するが、そのパスで許可されないメソッドである                                                                                                                                                                                                                                              | 405 `request.method_not_allowed` (`Allow` 付き)                                                   |
| R-ER-C-004 |    4 | 認証済みだが、その操作を認可されていない                                                                                                                                                                                                                                                            | 403 `auth.forbidden`                                                                              |
| R-ER-C-005 |    5 | 本文を伴う操作で、Content-Type がサポート対象でない。または Content-Encoding が identity 以外である (ヘッダーが無い場合は identity とみなす)                                                                                                                                                        | 415 `request.unsupported_media_type`                                                              |
| R-ER-C-006 |    6 | 本文が上限を超える                                                                                                                                                                                                                                                                                  | 413 `request.payload_too_large`                                                                   |
| R-ER-C-007 |    7 | バッチ登録で Idempotency-Key ヘッダーがない                                                                                                                                                                                                                                                         | 400 `idempotency.key_missing`                                                                     |
| R-ER-C-008 |    8 | バッチ登録で Idempotency-Key の値が形式を満たさない                                                                                                                                                                                                                                                 | 400 `idempotency.key_invalid`                                                                     |
| R-ER-C-009 |    9 | バッチ登録で、成功が確定した Idempotency-Key に、同じ本文 (バイト列の完全一致) で再送された                                                                                                                                                                                                         | 201 と初回のレスポンス本文の写しを返す (早期応答。エラー応答ではない)                             |
| R-ER-C-010 |   10 | 本文が JSON として不正、または検証制約に違反する。クエリの値が不正である (未知の `state` 値を含む)                                                                                                                                                                                                  | 400 `request.invalid`                                                                             |
| R-ER-C-011 |   11 | 指定した通知 ID の通知が存在しない、または ID の形式 (文字と最大長) が不正である                                                                                                                                                                                                                    | 404 `notification.not_found`                                                                      |
| R-ER-C-012 |   12 | バッチ登録で、成功が確定した Idempotency-Key に、異なる本文を送った                                                                                                                                                                                                                                 | 409 `idempotency.key_conflict`                                                                    |
| R-ER-C-013 |   12 | バッチ登録で、処理中または回復待ちの操作がある Idempotency-Key に送った (本文が同じでも異なっても)                                                                                                                                                                                                  | 503 `server.unavailable`                                                                          |
| R-ER-C-014 |   13 | キャンセルを受け付けない通知を指定した。対象は `specifications-endpoints.md` R-EP-C-024・R-EP-C-025 が拒否する通知とし、`cancelled`・`dispatched`・`missed` の通知と、引き渡し処理の開始が確定し、終端状態がまだ確定していない `scheduled` の通知を含む。応答は R-ER-C-062 の `currentState` を持つ | 409 `notification.not_cancellable`                                                                |
| R-ER-C-015 |   14 | 上のどの条件も成立しないが、処理に失敗した (サーバー障害)                                                                                                                                                                                                                                           | 500 `server.internal`、または現在は処理できない (回復は保証しない)場合は 503 `server.unavailable` |

No reordering is permitted.

補足:

- 各 Step が属する段は次のとおりとする。
  - Step 1: 認証
  - Step 2〜4: ルーティング・メソッド・認可
  - Step 5〜6: メディアタイプ (Content-Encoding を含む)・本文サイズ
  - Step 7〜8: 入力検証 (Idempotency-Key ヘッダーの形式)
  - Step 9: 成功結果の早期応答 (R-ER-C-009)
  - Step 10: 入力検証 (入力内容)
  - Step 11〜13: リソース状態
  - Step 14: サーバー障害
- R-ER-C-009 はエラー応答ではない。Step 1〜8 の検査をすべて通過した送信にだけ適用する。
  入力内容の検証 (Step 10) より先に、初回の成功結果を再現する。
  DD-ER-05 の段の順序に対する唯一の例外とする (DR-06 決定 6)。
- R-ER-C-012 と R-ER-C-013 は、同じ Step 12 の中で、Idempotency-Key の状態に応じて排他的に分岐する。
  キーの状態が「成功が確定」と「処理中または回復待ち」の両方になることはないため、2 つの間に評価の優先順位を設けない。
- 入力内容の検証の 400 (R-ER-C-010) は、R-ER-C-012 の 409 と R-ER-C-013 の 503 のどちらよりも先に返す。
  本文が同じでも異なっても同じとする (DR-06 決定 7)。
- 形式が不正な通知 ID は、存在しない ID と同じ「リソース状態」の段 (Step 11) で扱う。形式の正しさは、応答と優先順位のどちらでも区別しない (DD-ER-10)。
- 本表は、複数のエラー条件が同時に成立したときの外部応答の優先順位の唯一の場所である。`specifications-endpoints.md` は本表を参照する。
- Step 14 は最下位である。上位の条件を判定できないほどの内部障害は、例外として `server.internal` または `server.unavailable` を返してよい (MAY)。
- 本文サイズの上限値と、バッチ登録の件数の上限値は `specifications-endpoints.md` が定める。

### 4.2 Precedence Application Conditions

| Rule ID    | Rule                                                                                                                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R-ER-C-016 | HTTP メッセージを受理できないプロトコルレベルのエラーと、接続層のエラーは、4.1 の優先順位と problem 形式の統一の対象外とする                                                               |
| R-ER-C-017 | 認証を満たさないリクエストには、パスの存在、メソッドの可否、リソースの状態を示す情報を応答に含めてはならない (MUST NOT)。未知のパスや存在しない通知への未認証リクエストも、常に 401 を返す |
| R-ER-C-018 | 同じ段の中で複数の条件が成立したときは、4.1 の表で step の小さい条件の応答を返す (既定値・レビュー対象)。同じ step の R-ER-C-012 と R-ER-C-013 は排他的な分岐であり、同時には成立しない    |

### 4.3 Common Error Format

| Rule ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-ER-C-019 | API が生成するエラー応答は、すべて RFC 9457 に従い、メディアタイプ `application/problem+json` で返さなければならない (MUST) (DR-01 決定 1、DD-ER-05)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| R-ER-C-020 | エラー応答は、`status`・`type`・`code` を必須メンバーとして持たなければならない (MUST)。`status` の値は HTTP レスポンスのステータスコードと一致しなければならない (MUST) (DR-01 決定 7)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| R-ER-C-021 | 全 `code` に共通する必須メンバーは上の 3 つに限り、これ以外の共通の必須メンバーは設けない (DD-ER-01)。特定の `code` に固有の必須拡張メンバーは、R-ER-C-062 に従う。`title`・`detail`・`instance` は任意とする。クライアントは、`title` と `detail` の文面を分岐の条件にしてはならない (MUST NOT)                                                                                                                                                                                                                                                                                                                                                                              |
| R-ER-C-022 | 拡張メンバーの追加を許容する。ただし、再試行可能性・再送安全性・結果の確定性などの対処方針を表す拡張メンバー (`retryable`・`action` など) を定義してはならない (MUST NOT) (DR-04 決定 2)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| R-ER-C-023 | `type` は `urn:keneek:problem:<code>` とする (DD-ER-03)。`type` の参照先を解決できることは要求しない (DR-01 決定 5)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| R-ER-C-024 | `type` と `code` は 1 対 1 に対応する。`type` は `code` から一意に決まり、`code` を正とする。`type` を変えることも、後方互換性を評価する変更である (DR-01 決定 6)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| R-ER-C-025 | 標準ヘッダーを維持する。401 には `WWW-Authenticate`、405 には許可するメソッドを示す `Allow` を必ず付ける。Content-Encoding が原因の 415 には `Accept-Encoding: identity` を付け、Content-Type だけが原因の 415 には `Accept-Encoding` を付けない (RFC 9110、DR-06 決定 11)                                                                                                                                                                                                                                                                                                                                                                                                    |
| R-ER-C-026 | `Retry-After` は 503 にだけ任意で付与してよい (MAY)。R-ER-C-013 の 503 にも付与してよい。値は秒数の非負整数とする (既定値・レビュー対象)。他の `code` の応答には付与しない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| R-ER-C-061 | API が生成するエラー応答は、どのメンバーにも実装の内部情報を含んではならない (MUST NOT)。内部情報の例は、スタックトレース、内部のファイルパス、データストアのクエリや内部で使う識別子、使用しているライブラリの名称やバージョンである (例示であり、これらに限らない)。API 契約が公開を定めた値 (API 契約で定義する通知 ID など) は、内部情報に当たらない。データストアが内部で使う識別子とは区別する。本規則は、エラー応答に新たな情報を含めることを求めない。API が生成しない応答 (R-ER-C-016) は対象にしない。開示を防ぐ実現方法は定めない (DR-10 決定 2、DR-03 決定 2)                                                                                                     |
| R-ER-C-062 | `notification.not_cancellable` (409) の応答本文は、拡張メンバー `currentState` を持たなければならない (MUST)。`currentState` は JSON string とし、値は `scheduled`・`dispatched`・`missed`・`cancelled` のいずれかとする。値は `specifications-endpoints.md` R-EP-C-021 の状態と同じで、別の語彙を作らない。値は、サーバーがキャンセルの可否を判定した時点の通知の状態であり、応答を受け取る時点の状態を保証しない。拒否の原因や操作の主体は表さない。`scheduled` の拒否が開始の確定した通知に限られることは `specifications-endpoints.md` R-EP-C-024 と 3.7 に従う。要求する対象は `notification.not_cancellable` に限り、他の code には要求しない (DR-17 決定 2〜5・決定 7) |

#### エラーカタログ表

対処方針の表記:

- 再試行可能性: 「可」は同じリクエストの再試行に効果がある。「条件付き」は条件を満たした場合だけ効果がある。「不可」は同じ内容では効果がない
- 再送安全性: 「安全」は再送しても副作用が重複しない。「要確認」は再送の前に状態を確認する
- 結果の確定性: 「確定」はその応答で当該リクエストの結果が確定している。「不明」は確定していない
- 空欄の判断点は、その `code` では規定しない (R-ER-C-034)

| `server.unavailable`             | `urn:keneek:problem:server.unavailable`             |  503 | `server`       | 次の 2 つの場合に返す。(1) 処理中または回復待ちの登録処理と競合した (R-ER-C-013)。このときサーバーは、その送信による登録を行わない。(2) その他の理由で現在は処理できない (回復は保証しない) (R-ER-C-015)。このときは登録の成否が確定しない場合がある。クライアントは (1) と (2) を区別できないため、どちらもこの応答だけでは結果を確定できないものとして扱う。確定済みの成功の確定 (クライアント) は変えない (DR-06 決定 7・決定 9)。再試行: 条件付き (GET は再試行してよい。バッチ登録は R-ID-C-302 の条件に従う。`Retry-After` が付いた場合は、その秒数が経過する前に再試行しないことが望ましい (R-ER-C-037)。再試行しても、回復や結果の確定は保証しない (R-ID-C-401))。再送安全性: GET は安全。バッチ登録の再送は `specifications-idempotency.md` R-ID-C-302 に従い、重複登録の防止の範囲は R-ID-C-101 による。キャンセルは要確認。結果: 不明 |

### 4.6 Handling Policy

| Rule ID    | Rule                                                                                                                                                                   |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-ER-C-034 | 再試行可能性・再送安全性・結果の確定性は、独立した判断点として扱う。3 つすべてを各 `code` の必須の属性にはしない。対処方針は、その `code` に必要な判断点だけを表に書く |
| R-ER-C-035 | クライアントは、HTTP ステータスコードだけで対処を決めてはならない (MUST NOT)。5xx を一律に再試行可能として扱ってはならない (MUST NOT)                                  |
| R-ER-C-036 | 対処方針は契約 (本書とカタログ) にだけ置く。エラーレスポンスの本文には載せない (R-ER-C-022)                                                                            |
| R-ER-C-037 | `Retry-After` が付いた 503 を受け取ったクライアントは、その秒数が経過する前に同じリクエストを再試行しないことが望ましい (SHOULD)                                       |

### 4.7 No-Response Handling

| Rule ID    | Rule                                                                                                                                                                                                                                                                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-ER-C-038 | 応答を受け取れない通信失敗 (応答の喪失、タイムアウト、接続断) は、problem 形式の失敗応答と区別する。エラー識別子が得られず、処理結果は「不明」として扱う                                                                                                                                                                                                          |
| R-ER-C-039 | 一覧取得と単体取得は、安全かつ冪等である。応答を受け取れなかったときは、同じリクエストを再試行してよい (MAY)                                                                                                                                                                                                                                                      |
| R-ER-C-040 | バッチ登録で応答を受け取れなかったとき、または `5xx` (503 を含む) を受け取ったときの扱いと再送の条件は、`specifications-idempotency.md` R-ID-C-301〜R-ID-C-304 に従う。`5xx` を登録されなかったことの確定とはみなさない。重複登録の防止の範囲は R-ID-C-101 による。一覧取得による状況の確認は補助的な案内であり、論理操作の成功または不成立を確定する手段ではない |
| R-ER-C-041 | キャンセルは、応答を受け取れなかったとき、または再送で `notification.not_cancellable` を受け取ったときは、自動で再送せず、単体取得で通知の状態を確認してから判断する。キャンセルが成功していれば状態は `cancelled` になる                                                                                                                                         |
| R-ER-C-042 | problem 形式でない応答 (プロキシなどが生成したもの) は、エラー識別子を得られない場合として扱う。この応答だけでは結果を確定できないものとして扱う。確定済みの成功の確定 (クライアント) は変えない (`specifications-idempotency.md` R-ID-C-301、R-ID-C-304)。HTTP ステータスコードを参照する場合も、R-ER-C-048 の制限に従う                                         |

### 4.8 Extension Rules

| Rule ID    | Rule                                                                                                                                                                                                                                                                                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-ER-C-043 | エラー識別子の追加と、既存 API 操作の変更を区別して評価する。識別子の追加であることだけを理由に、後方互換とは判断しない (DR-04 決定 8、9)。評価は下の表に従う                                                                                                                                                                                                    |
| R-ER-C-044 | 既存の `code`、`type`、HTTP ステータス、分類の変更と削除は、破壊的変更として扱う (R-ER-C-024、R-ER-C-030)                                                                                                                                                                                                                                                        |
| R-ER-C-045 | 新しい `code` を追加するときは、同じ変更でエラーカタログ表に、`type`、HTTP ステータス、分類、対処方針を含む 1 行を追加する。既存の `code` と共通エラー形式の必須メンバーは変更しない                                                                                                                                                                             |
| R-ER-C-046 | 新しい `code` の HTTP ステータスは、既存のクライアントが解釈できるステータスコードの意味から外れてはならない (MUST NOT)                                                                                                                                                                                                                                          |
| R-ER-C-047 | クライアントは未知の `code` を受け取ったとき、次の順で扱う。(1) `code` の形式が R-ER-C-027 を満たし、category が本書の一覧にあれば、分類に基づいてエラーの種別を解釈する。(2) category が未知、または `code` の形式が解釈できない場合は、HTTP ステータスコードを参照する。分類に基づく扱いは、再試行の可否を分類だけで決めない (DD-ER-08)                        |
| R-ER-C-048 | WHEN 対象の操作が冪等でなく、再送安全性を確認できない場合、クライアントはその操作を無条件に自動で再試行してはならない (MUST NOT)。再送安全性を確認できる操作は、一覧取得と単体取得とする。バッチ登録の再送は `specifications-idempotency.md` R-ID-C-302 の条件で許されるが、重複登録の防止の範囲は R-ID-C-101 に限られる。キャンセルは確認できない操作として扱う |
| R-ER-C-049 | クライアントは、未知のエラー拡張メンバーを無視する (MUST)                                                                                                                                                                                                                                                                                                        |
| R-ER-C-050 | 既知のメンバー (`status`・`type`・`code`・`title`・`detail`・`instance` を含む) の意味を変えてはならない (MUST NOT)。拡張メンバーを新しく追加することは、既知のメンバーの意味を変えない限り後方互換な変更である                                                                                                                                                  |
