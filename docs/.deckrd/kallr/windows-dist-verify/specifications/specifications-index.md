## 1. 概要

### 1.1 目的

Windows で OS の予約通知 (AddToSchedule) を、未パッケージ + HKCU 登録の配布形式で利用できるかを確認する検証 (Issue #19) の仕様を定める。
仕様は 4 つのファイルに分割する。この索引には、各ファイルの担当範囲、要件との対応、共通の前提、決定記録、未解決事項をまとめる。

### 1.2 範囲

この仕様全体では、Windows Distribution Verify の振る舞いの規則を定める。
実装の詳細は対象外とする。具体的な規則は各分割ファイルに記載し、この索引には記載しない。

用語は `universal-dictionary.md` (UD-RSV-001〜UD-REC-003) に従う。
この仕様で使う用語は、予約、予約一覧、Tag、Group、登録時刻、通知時刻、マシン ID、対応表、置換、置換前の予約、置換後の予約、置換の失敗状態、通知可否の確認、Mock、記載なし、未確認、未明確の 17 語。

## 2. 設計方針

### 2.1 分類方針

- 検証対象の振る舞いは、OS に依存しない部分と OS 固有の部分に分ける。OS 固有の部分は、インターフェースの背後に置く。
- 予約の一覧と対応表は別々の保存先であり、食い違うことがある。各ファイルは、食い違いを隠さず状態として報告する。
- 未確認の事項は推測で埋めず、未確認のまま残す。

### 2.2 設計上の前提

- 配布形式は未パッケージ + HKCU 登録、検証対象は Dart FFI とする (DR-01, DR-02)。
- CLI は一度に 1 プロセスだけ実行する。2 つの CLI プロセスの同時実行は対象外とする。SQLite のトランザクションは、DB が壊れないことだけを保証する。
- 本検証のコードは `poc/` 配下にのみ置く (REQ-C-001, REQ-F-018)。

### 2.3 外部設計の概要

> **根拠**: 外部設計の対話 (Phase E) と、利用者が確認した設計方針 (Phase D) に基づく。

### 2.4 対象外

> **根拠**: 以下はすべて REQUIREMENTS の「Out of Scope」に基づく。

- Windows 以外の OS ← REQ: Out of Scope #1
- `apps/` と `packages/` への PoC コードの配置 ← REQ: Out of Scope #2
- MSIX + Dart と AOT exe の検証 (未確認事項として記録する) ← REQ: Out of Scope #3
- 任意の測定の合否判定 ← REQ: Out of Scope #4
- Android など Windows 以外での通知可否の確認の実装 (インターフェースは OS 非依存にする) ← REQ: Out of Scope #5
- `mapToastKey` の採用 (ハッシュで Tag を短縮しない) ← REQ: Out of Scope #6

### 2.7 DD を DR に昇格する基準

> **目的**: DD を正式な DR に昇格するかどうかを判断するための指針。昇格は人が判断し、自動では行わない。

**昇格を検討する場合:**

1. 複数の仕様またはモジュールに影響する
2. 将来の設計の選択肢を縛る
3. 実際に複数の選択肢があった
4. 外部の関係者によるレビューが必要

**DD のまま残す場合:**

- この仕様の中だけで完結する
- 大きな代替案がなかった
- 根拠が文脈から明らかである

> **Action**: 昇格するときは `/deckrd dr --add` を実行し、DD の Status を `Promoted → DR-xx` に更新する。
> IDX-DD-01 (SQLite の採用) と IDX-DD-04 (終了コード) は複数ファイルに影響するため、昇格の候補とする。

## 3. 振る舞いの仕様

### 3.1 入力

- 入力の種類: CLI のコマンドと、各コマンドのオプション
  - 例: --batch、--alarm、--at、--title、--aumid、--db、--display-name、--recorded-*
- 前提:
  - 文字列の入力は UTF-8 に対応する (REQ-NF-004)
  - `--aumid` は OS に触れるすべてのコマンドで必須で、既定値を持たない。`--batch` と `--alarm` も既定値を持たない (IDX-DD-10)
  - `--db <path>` は任意で、対応表を使うすべてのコマンドの保存先を差し替える (IDX-DD-11)
  - Tag と Group の文字数は UTF-16 code unit 数で数える
  - 各コマンドの入力の詳細は、対応する分割ファイルが定める

### 3.2 出力と終了コード

- 出力の意味: 終了コード、予約一覧、対応表の内容、および結果の記録
- 取りうる結果:
  - 0: 成功
  - 1: 使い方の誤り (必須オプションの欠落など)
  - 2: 失敗 (OS または DB の失敗、Tag の重複の再生成の上限超過、見つからない、一括再登録での個別の失敗、記録の不一致または未明確)
  - 3: 通知できない状態 (AUMID の未登録、DisplayName が空、通知設定が無効)。add、show、re-register-all が返す

### 3.3 コマンドと分割ファイルの対応

| コマンド                                        | 詳細を定めるファイル          |
| ----------------------------------------------- | ----------------------------- |
| add / cancel / list / re-register-all           | specifications-schedule.md    |
| show / register-reg / unregister-reg / w5-check | specifications-environment.md |

## 4. 判定規則

分割ファイルにまたがる評価の順序を、コマンドごとに示す。各段階の詳細は、右の列のファイルが定める。
この節の ID は、索引の規則であることを示す接頭辞 IDX- を付ける。分割ファイルの規則は、接頭辞 TAG-、SCH-、ENV-、VER- で区別する。

評価は、各表の Step の順に行う。

### 4.1 add の評価順序

| Rule ID   | Step | Condition                                                              | Outcome                                                        | 詳細        |
| --------- | ---: | ---------------------------------------------------------------------- | -------------------------------------------------------------- | ----------- |
| IDX-R-001 |    1 | 最初に通知可否の確認をし、通知できない状態である                       | 終了コード 3 で終了。予約も HKCU への書き込みもしない          | environment |
| IDX-R-002 |    2 | 通知できる状態で、対応表と予約一覧から既存の予約の有無を調べる         | 新規、置換、発火後の新規のいずれかに分類                       | schedule    |
| IDX-R-003 |    3 | Tag を生成し、予約一覧の Group=kallr と対応表の Tag との重複を確認する | 重複なら再生成。3 回を超えたら終了コード 2 で終了              | tag         |
| IDX-R-004 |    4 | 新規の場合                                                             | 予約を追加してから、対応表を更新                               | schedule    |
| IDX-R-005 |    4 | 置換の場合                                                             | 置換後の予約を追加し、対応表を更新してから、置換前の予約を削除 | schedule    |

IDX-R-004 と IDX-R-005 は、分類 (Step 2) の結果に応じて、どちらか一方だけを実行する。

### 4.2 cancel の評価順序

| Rule ID   | Step | Condition         | Outcome                                                                                   | 詳細     |
| --------- | ---: | ----------------- | ----------------------------------------------------------------------------------------- | -------- |
| IDX-R-006 |    1 | cancel を実行する | 予約を削除してから、対応表の記録を削除。削除が「対象が無い」(発火済み) を返したら成功扱い | schedule |

### 4.3 re-register-all の評価順序

| Rule ID   | Step | Condition                                        | Outcome                             | 詳細     |
| --------- | ---: | ------------------------------------------------ | ----------------------------------- | -------- |
| IDX-R-007 |    1 | 最初に通知可否の確認をし、通知できない状態である | 終了コード 3 で終了。何も登録しない | schedule |
