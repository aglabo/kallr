> **本書の位置付け**
> 本書は、モジュール keneek-core/api-contract の用語と概念の唯一の正本とする。
> すべての設計工程 (requirements、decision records、specifications、implementation、tasks) が、本書を共有する。
> 本書を参照すれば、どの DR や仕様を読んでも、同じ用語を同じ意味で解釈できる。
> 本書は設計判断の代替物ではない。判断は DR、要求・保証・振る舞いは requirements と specifications、実現と検証は implementation と tasks が定める。

## 1. 本書の規則

### 1.1 扱うもの

- 本書は、概念の定義、同一性、概念どうしの関係、視点を定め、安定した UD-ID を割り当てる。
- 行動の義務 (MUST・SHOULD など)、振る舞いの条件、保証の範囲、期間の起点や長さなどの具体値は定めない。それらの正本は、「関連規則」に挙げる文書とする。
- 概念を識別する本質的な性質は、定義に残す。
- ほかの文書は、用語の意味を定義し直さず、UD-ID で参照する。ほかの文書が、本書と異なる意味で用語を使うことは認めない。
- 本書の定義と Accepted の DR が食い違う場合は、どちらが誤っているかを個別に検証して解消する。本書を正本とすることを理由に、DR を暗黙に読み替えない (8 章)。
- 本書だけを直して済ませない。定義を変えるときは、参照する文書を同じ変更単位で整合させる。

### 1.2 項目の意味

用語ごとに見出し `UD-NNN 用語` を立て、その直後の段落に定義を書く。続けて次の項目を示す。

| 項目       | 意味                                                                           |
| ---------- | ------------------------------------------------------------------------------ |
| 抽象度     | 1.3 の 5 段階                                                                  |
| 立場       | その概念を誰の視点で使うか (クライアント・サーバー・共通)                      |
| 確定状況   | 1.4 の 3 区分                                                                  |
| 上位概念   | この概念が、その一種または値である概念                                         |
| 構成要素   | この概念を構成する概念                                                         |
| 状態       | この概念がとる状態を表す概念                                                   |
| 対立・区別 | 意味が異なるのに取り違えやすい概念。同義の言い換えを禁止するための項目ではない |
| 関連       | 上の関係にあたらない、関係する概念                                             |
| 定義根拠   | 定義の意味の根拠となる記述                                                     |
| 関連規則   | この概念を使って、判断・義務・保証・具体値を定める DR の決定・要件・規則       |

- 上位概念・構成要素・状態は、いずれもその用語から見た相手だけを書く。逆向きの関係は書かない。例えば、状態の値の用語には上位概念として状態の概念を書き、状態の概念の側には値の用語を挙げない。
- 上位概念・構成要素・状態・対立・区別・関連・関連規則は、該当しない場合に省略する。
- UD-ID は見出しの先頭に置く。番号は振り直さず、廃止した番号も再利用しない。番号の順と見出しの並びは一致しなくてよい。
- 定義根拠の「移行元」は、本書へ定義を移す前に定義を持っていた文書の版を指す。

### 1.3 抽象度

| 抽象度     | 内容                         |
| ---------- | ---------------------------- |
| 原則       | 保証の範囲と方針の概念       |
| 概念       | 成果物、主体、操作の単位     |
| 状態・判断 | 状態、区分、判断の結果       |
| 時間・範囲 | 期限、期間、時点、識別の範囲 |
| 具体       | 値、形式、個々の応答         |

### 1.4 確定状況

| 区分                      | 意味                                                                    |
| ------------------------- | ----------------------------------------------------------------------- |
| 確定                      | 意味が確定している                                                      |
| 確定 (実現可能性は未確認) | 意味は確定しているが、兄弟 issue などが実現できるかの照合が済んでいない |
| 未確定                    | 意味または内容が、まだ決まっていない                                    |

## 2. 契約と保証

- 関連: UD-002、UD-003
- 定義根拠: 移行元 requirements.md v1.5.1 1.3

### UD-004 内部の実現方法

外部から観測できる保証を、サーバーが内部でどう実現するか。例えば、トランザクション、判定アルゴリズム、状態遷移の内部の実現方法、認証メカニズムの内部実装、永続化を含む。

- 立場: 共通

### UD-007 違反 (契約検証)

- 関連: UD-008
- 定義根拠: 移行元 requirements.md v1.5.1 1.3
- 関連規則: requirements.md REQ-F-012、AC-007

## 4. エラー

### UD-013 共通エラー形式

API 自身が生成するエラーレスポンスの、単一の共通形式。RFC 9457 (Problem Details for HTTP APIs) を基にする。

- 抽象度: 具体
- 立場: 共通
- 確定状況: 確定
- 対立・区別: 中継装置が返す、problem 形式でない応答
- 関連: UD-014、UD-018
- 定義根拠: 移行元 requirements.md v1.5.1 1.3、DR-01
- 関連規則: DR-01 (必須メンバーと拡張メンバー)、requirements.md REQ-F-003、`specifications-errors.md` R-ER-C-019

### UD-014 エラー識別子

エラーの種別を機械的に判別するための、Keneek が定める文字列。HTTP ステータスコードより細かい粒度で、エラーを区別する。

- 確定状況: 確定
- 対立・区別: `type` (URI)、HTTP ステータスコード
- 関連: UD-013、UD-015、UD-016、UD-017
- 定義根拠: 移行元 requirements.md v1.5.1 1.3
- 関連規則: DR-01 (`code` メンバーに入れる)、requirements.md REQ-F-004、`specifications-errors.md` R-ER-C-030 (安定性)

### UD-015 エラー分類

### UD-016 対処方針

- 定義根拠: 移行元 requirements.md v1.5.1 1.3
- 関連規則: DR-04、requirements.md REQ-F-004

- 関連規則: `specifications-idempotency.md` R-ID-C-301、`specifications-errors.md` R-ER-C-042

## 8. DR との不整合と解消の記録

本書の定義と Accepted の DR の記述の食い違いを、どちらが誤っているかの検証と、解消の結果とともに記録する。
解消と記すのは、解消後の DR の本文を照合して確かめた場合に限る。照合の対象は `decision-records.md` v1.4.2 とする。

### 8.1 決定 1: キーと論理操作の対応

- 箇所: DR-06 決定 1 (v1.4.1)「Idempotency-Key は、1 つの論理操作を表す」「論理操作ごとに新しいキーを作り」
- 食い違い: UD-031 では、同じキーと別の本文は別の論理操作となる。
- 検証: DR-06 の中の食い違いとした。決定 9 は、登録なしの確定の後に、同じ登録の意図を別の本文で登録し直すことを許す。
  Alternatives が退けたのは、1 回の 4xx を根拠にしたキーの再利用だけとする。決定 1 の文言が、決定 9 の場合を書き落としていた。辞書は正しい。
- 扱い: 決定 1 に、決定 9 の例外を明記する (refine。判断の意味は変えない)。
- 状態: 解消。v1.4.2 の決定 1 は「Idempotency-Key は、本文と組になって、1 つの論理操作 (キー K と本文 B の組) を識別する」と書く。
  例外は「決定 9 が許す登録し直し」だけとしている。
  UD-031・UD-055 と一致する。同じキーを別の本文で使える条件は DR-06 と R-ID-C-305・306 が定め、本書は定めない。

### 8.2 決定 4: 論理操作と登録の意図

- 箇所: DR-06 決定 4 (v1.4.1)「論理操作 (キー K と本文 B が表す登録の意図)」
- 食い違い: 括弧内は、論理操作と登録の意図を同じものとして読める。
- 検証: 決定 9 は「同じ登録の意図を、新しいキーや別の本文で登録し直す」と書き、両者を区別している。決定 4 の括弧内の表現が不正確だった。辞書は正しい。
- 扱い: 括弧内を UD-031 の意味に直す (refine)。
- 状態: 解消。v1.4.2 の決定 4 は「論理操作 (キー K と本文 B の組で識別される操作)」と書いている。UD-031 と一致する。

### 8.3 決定 3・決定 9: 成功の確定

- 箇所: DR-06 決定 3 (v1.4.1)「成功の確定から最低 24 時間」と、決定 9 の「成功の確定」
- 食い違い: 同じ語を、サーバーの状態 (決定 3) とクライアントの判断 (決定 9) の 2 つの意味で使っていた。
- 検証: Rationale は、保持期間を「サーバーで成功が確定した時点から数える」と明記している。決定 3 の文言が、どちらの意味かを示していなかった。辞書は 2 つの概念 (UD-041・UD-042) に分けて正しい。
- 扱い: 決定 3 を「サーバーで成功が確定した時点から」、決定 9 を「成功の確定 (クライアントの判断)」に直す (refine)。
- 状態: 解消。v1.4.2 の決定 3・決定 4 は「サーバーで成功が確定した時点から」と書き、決定 9 は「クライアントの判断として、契約に適合する 201 による成功の確定」と書いている。
  決定 6・決定 8・決定 13 の「成功が確定」は、キーの状態 (UD-042) の意味で使われている。
  決定 9 にある 24 時間の経過の扱いは、用語の意味ではなく規則の食い違いなので、本書の範囲外とした。`decision-records.md` v1.5.0 の決定 9 と R-ID-C-304 で解消している。

### 8.4 決定 2・決定 3・決定 7: 操作と登録処理

- 箇所: DR-06 決定 2 (v1.4.1)「同じキーの同時の操作」、決定 3「結果が確定していない操作」、決定 7「処理中または回復待ちの操作」
- 食い違い: 「操作」が、論理操作 (UD-031) ではなく、登録処理 (UD-035) を指していた。
- 検証: 同じ決定を具体化した R-ID-I-101・102・204 は「登録処理」と書いている。決定の文言が不正確だった。辞書は正しい。
- 扱い: 「操作」を「登録処理」に直す (refine)。
- 状態: 解消。v1.4.2 の決定 2・決定 3・決定 7 と Alternatives は「登録処理」と書いている。
