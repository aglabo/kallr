## 1. 目的

`redesign-plan.md` の判定ゲート (7.1) を通すため、次を実機で確かめる。API の呼び出しが成功するだけでは合格にしない。

- Windows: 採用する配布形式で、予約通知が使えるか (Q6、Q9、Q10)
- Android: アラームの発火から通知の表示までを、永続ストアを使った短時間の処理で行えるか (Q11)
- Android: PWA から Keneek を起動し、登録要求を処理し、対応する結果を PWA へ返せるか (Q8)
- Windows と Android: 任意のサイトが通知を予約できないよう、呼び出し元を検証できるか (Q12)

## 2. 進め方

- PoC のコードは、本流の `apps/` や `packages/` に入れない。検証用のブランチで git 管理する (`redesign-plan.md` 第 10 章)
  - Windows: `chore-3/poc/windows-notification` (名前は `deckrd-rule-workflow.md` の規則に合わせる)
  - Android: `chore-3/poc/android-notification`
- 結果は `redesign/poc-results-windows.md`・`redesign/poc-results-android.md` (`workspaces/` 配下) に残す。測定値、使った端末と OS のバージョン、成否、気付いた制約を書く
- 公式文書で確認できなかった事項は「記載なし」と書き、推測で補わない。実機で確かめた結果が出るまで、保証や制約として契約に採用しない
- 各 PoC 項目に、`os-notification-api-survey.md` (以下、調査メモ) の対応節を書く。調査メモで『未確認』とされた事項が、どの項目で実機検証されるかを追えるようにする
- 実行の順序: PoC-W0 → PoC-W。PoC-A1・A2 は PoC-W と並行できる。PoC-A4・A5 は PoC-A1・A2 の後
- Git の操作はユーザーが行う
- `W1`・`A1` などの ID は PoC の中のラベルであり、テストケース ID (`test_scope`) ではない。`deckrd-rule-testing-guidelines.md` の対象外とする

| W7 | Windows の再起動またはログオフの後の予約                                                               | 再起動またはログオフの後も予約が残り、時刻に通知が出るかを確認する。残らない場合は、一括再登録で復旧できるかを確認し、契約に書く保証しない事項として記録する (ゲートでは結果の記録を求める)  | 6.1      |

#### W4 の検証

(a) 未発火の置換: 元の時刻の前に、同じ ID で日時を変えて `add` する。元の時刻に通知が出ず、新しい時刻に 1 回だけ出る。

(b) 発火後の登録: 元の時刻を過ぎて発火した後の同じ ID の登録は、置換ではなく新しい予約として扱う。

(c) ID の長さ: `batchId`・`alarmId` を Tag/Group の文字数の制約に当てはめる。文字数の上限は調査メモで記載なしのため、実機で確かめる。収まらない場合の対応づけ (ハッシュなど) を決める。

(d) 置換の方式: 次のどちらが必要かを記録する。契約の『置換』は、OS の原子的な置換機能と同じとは限らない。

- 同じ Tag/Group で `AddToSchedule` するだけで置換される (調査メモは、この場合の挙動を記載なしとしている)
- 既存の予約を `RemoveFromSchedule` で取り消してから、再登録する必要がある

(e) 失敗時の状態: (d) の方式ごとに、操作の途中で失敗させたときの結果を、次の 4 つの状態のどれになるかで記録する。異常終了は、各段階の間にプロセスの kill を差し込んで再現する。

| 状態         | 内容                                            |
| ------------ | ----------------------------------------------- |
| 旧予約が残る | 古い予約だけが OS に残る。新しい予約は無い      |
| 新予約だけ   | 新しい予約だけが OS に残る。古い予約は無い      |
| 両方残る     | 古い予約と新しい予約が両方残る (二重になる)     |
| どちらも無い | 古い予約も新しい予約も OS に残らない (予約消失) |

取り消しの後に再登録する方式では、取り消しと再登録の間の異常終了で『どちらも無い』が起き得る。この可能性を記録する。
これは Q5 (永続ストアと OS 予約の不整合) に直接関わる。永続ストアに残る内容と、OS の状態の組み合わせを記録し、一括再登録で補正できるか (旧予約が残る・どちらも無い) と、補正できないか (両方残る) を判断する。

追加で測る事項 (合否には含めない):

- 過去の時刻を指定したときの動作 (調査メモは、過去の時刻をエラーの原因に挙げ、例外の種類は記載なし)
- 配信猶予 (PC の停止中に時刻を過ぎた通知)。仕様には採用しない。理由は上の『配信猶予についての扱い』に書いた
- 予約一覧の取得
- 件数の上限 (調査メモは、4096 件を超えた場合の失敗を記載)

### PoC-W6: PWA からの呼び出しと呼び出し元の検証 (Q9、Q12)

調査メモ: 6.5。

localhost のサーバーとして動かし、ブラウザの PWA から `fetch` で登録できるか。次を確かめる。

- CORS・Private Network Access・Local Network Access の制約、サーバーが動いていないときの挙動を記録する。起動方法 (ログオン時の常駐、CLI からの起動) の比較に使う
- 呼び出し元の検証 (必須) として、許可した Origin からの登録は受理し、許可していない Origin (任意のサイト) からの登録は拒否される。拒否したときの応答を記録する
- 認証の外部仕様 (#6) との整合を確認する
- 公開ページから localhost を呼ぶときの許可の確認 (Local Network Access の権限) で、PWA から localhost を呼べない場合は不合格とする。回避の方式を記録する。
  調査メモは、サーバー側が送るヘッダーの要否とインストール済み PWA の扱いを記載なしとしているため、実機で確かめる。現在の Chrome の状態 (調査メモの出典は 2025-09-29 更新) も、実機で確かめる

## 4. PoC-A: Android

テストデータは PoC-W と同じ。実機を使う (エミュレーターでは、Doze や省電力の挙動を確かめられない場合がある)。

### 状態の区別 (A1 の試験条件)

Android では、次の状態を区別する。「強制終了」とだけ書かない。

| 状態          | 意味                                | A1 の扱い                                                      |
| ------------- | ----------------------------------- | -------------------------------------------------------------- |
| Activity 終了 | UI を閉じた状態                     | 合格条件に含める                                               |
| プロセス終了  | アプリのプロセスが存在しない状態    | 合格条件に含める。`am kill` など OS による通常の終了で再現する |
| Force Stop    | OS がアプリを強制停止した状態       | 別のケースとして検証し、結果を記録する。合格条件には含めない   |
| 端末再起動    | `AlarmManager` の予約が失われる状態 | A6 で扱う                                                      |

### 合格条件

| #   | 内容                                                                                               | 確認方法                                                                                                                                                                                                                                      | ゲート     | 調査メモ |
| --- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | -------- |
| A1  | `AlarmManager` → `BroadcastReceiver` → `NotificationManager`。通知内容は `PendingIntent` の extras | Activity 終了とプロセス終了の後に、指定時刻に通知が出る。`PendingIntent` の同一性は Intent の data (ID を含む URI) で決め、extras は同一性に使われない前提で、`FLAG_UPDATE_CURRENT` により同じ同一性の `PendingIntent` の extras を更新できる | 必須       | 6.3      |
| A1b | (別ケース) Force Stop の後の動作                                                                   | Force Stop の後に、予約された通知が出るか。出ない場合は、その制約を記録する。調査メモは記載なし                                                                                                                                               | 記録       | 6.3      |
| A2  | A1 と同じ経路で、通知内容は永続ストア (SQLite) から取得する                                        | extras には ID だけを入れ、Receiver がストアから title を取得して通知を出す。処理時間を測る (`onReceive` は約 10 秒の制限)                                                                                                                    | 必須       | 6.3      |
| A3  | (参考) Receiver から Dart Core をヘッドレスで起動する                                              | 起動時間を測り、Receiver の処理時間の制限に収まるかを確認する。収まらない場合は A2 の方式を採る                                                                                                                                               | 参考       | 6.3      |
| A4  | PWA → Intent / App Links → Keneek の起動、登録要求の処理、呼び出し元の識別                         | 下の A4・A5 の三段階の検証                                                                                                                                                                                                                    | 必須       | 6.4      |
| A5  | PWA が対応する登録結果を受け取る                                                                   | 下の A4・A5 の三段階の検証                                                                                                                                                                                                                    | 必須       | 6.4      |
| A6  | 再起動後のアラーム                                                                                 | 端末を再起動し、アラームが消えること、保存済みデータからの一括再登録で復旧することを確認する。調査メモは、再起動で全アラームが取り消されること、`BOOT_COMPLETED` での復元にアプリの起動歴が要ることを記載                                     | 記録       | 6.3      |
| A7  | 過去の時刻と権限                                                                                   | 過去の時刻を指定した動作 (調査メモ: 即座に発火する)、Doze 中の発火を記録する。正確なアラームの権限 (`SCHEDULE_EXACT_ALARM` など) は、利用者が取り消せることとストアの制限を確認し、採用する方針 (必須とするか、近似の時刻で許すか) を決める   | 方針の決定 | 6.3      |
| A8  | 同一 ID の置換とキャンセル                                                                         | 同じ `PendingIntent` の識別 (Intent の data などに ID を含める) で、置換とキャンセルが効く                                                                                                                                                    | 必須       | 6.3      |

A2 は、永続ストアを前提にした新アーキテクチャの成立を確かめる条件です。A1 だけが成功しても、A2 が成功しなければゲートを通過しない。

### A4・A5: 起動・登録・応答の三段階

PWA 連携は、次の三段階を独立して検証する。Intent / App Links でアプリを起動できたことを、双方向の通信の成立とみなさない。

| 段階 | 内容                             | 合格条件                                                                                                    | 項目 | 調査メモ |
| ---- | -------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---- | -------- |
| 起動 | PWA から Keneek を起動する       | PWA のリンクから Keneek が起動し、パラメーターを受け取れる。『アプリが開いた』だけでは次の段階に進めない    | A4a  | 6.4      |
| 登録 | バッチ登録要求を渡し、処理する   | 受け取った登録要求を処理し、要素ごとの結果 (`ok`・`skipped`・`failed`) が永続ストアと OS の予約に反映される | A4b  | 6.3、6.4 |
| 応答 | PWA が対応する登録結果を受け取る | PWA が、自分の要求に対応する結果を受け取る (下の応答プロトコル)                                             | A5   | 6.4      |

調査メモは、アプリから Web ページへ結果を返す仕組みを、確認した範囲に見つけていない。応答の段階は、起動と登録が成功しても成立しない可能性がある。
App Links で必要なドメインの配信 (`assetlinks.json`、https のドメイン) を誰が行うか、localhost や私的なオリジンの PWA から使えるかも、起動の段階で確認する。調査メモは、どちらも記載なし。

#### A4c: 呼び出し元の識別と要求ごとの認可 (Q12)

- 許可した呼び出し元 (Keneek に関連づけたサイトの PWA) から登録できる
- 許可していない呼び出し元 (任意のサイト) からの登録は拒否される
- 調査メモのとおり、App Links はドメインの所有とアプリの関連づけを検証する仕組みで、個々の要求や呼び出し元の認証は記載がない。呼び出し元を識別する手段 (`getReferrer` など) も記載なし。
  呼び出し元を識別できない場合は、要求ごとの認可方式 (トークン、要求の署名、利用者の確認など) を検証し、方式と結果を記録する。どちらもできない場合は不合格とする

#### A5: 結果の返却経路の候補と、応答プロトコルの検証

| 候補                                                               | 確かめること                                                                                   |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| (1) 起動後だけ一時的にローカル HTTP サーバーを立て、PWA が取得する | 起動の待ち時間、ポートの取得、PWA からの接続 (CORS・Local Network Access の権限)、処理後の停止 |
| (2) App Links で起動し、結果を登録元の URL へ返す                  | 結果を載せる方法 (クエリ・fragment・リダイレクト)、サイズの上限、PWA 側の受け取り              |
| (3) Web Share Target など                                          | 結果を返す手段があるか (調査メモは、共有元のページへ応答を返す仕組みを記載なしとしている)      |

候補ごとに、次の応答プロトコルを検証する。

| 項目                 | 合格の条件                                                                                                                                                                                                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 要求と応答の対応づけ | PWA が、1 回の操作と 1 回の結果を、要求 ID で対応づけられる                                                                                                                                                                                                                                |
| 部分成功             | バッチの要素ごとの成否 (`batchId`・`alarmId` ごとの `ok`・`skipped`・`failed`) を返せる                                                                                                                                                                                                    |
| 同時要求             | 複数の要求を同時に送っても、結果が混線しない                                                                                                                                                                                                                                               |
| 結果不明             | 通信や画面遷移が失敗したとき、PWA が「結果不明」と判断できる。その後の確認や再実行の手段がある                                                                                                                                                                                             |
| 秘匿                 | App Links の戻り先の URL に、通知の内容や認証情報をそのまま含めない。要求 ID を使う方式も比較する                                                                                                                                                                                          |
| 結果の確認操作       | 結果不明のとき、通常の通知取得 (取得・一覧 API。v1 に含めない) とは別の確認操作で、要求 ID に対応する処理結果だけを確認できるか。必要な場合は、次を調査項目として記録する: 結果の保存主体 (Keneek の永続ストアか、PWA か)、保持期間、結果の取得経路。これらの方式は、この PoC で確定しない |

合格: 1 つ以上の経路が、上の全項目を満たす。

## 5. ゲートへの対応

| 判定ゲート (`redesign-plan.md` 7.1)                                     | 満たす条件                                                                                                        |

| Windows の採用する配布形式で W1〜W4 が成功し、W5 の制約が記録されている | W1〜W4 が通る。W5 と W7 の記録が揃っている。予約通知 API が使えない場合は、TS1 と TS2 の両方が通る                |

## 6. 結果の文書の構成

各 PoC の結果は、次の項目で書く。

- 環境 (端末または OS のバージョン、ツールのバージョン、使ったコミットまたはブランチ)
- 手順と結果 (成否)
- 測定値
- 制約と気付き
- 調査メモで『未確認』とされた事項が、実機でどうだったか
- 設計への影響 (Q の決定、契約に書く保証しない事項)
