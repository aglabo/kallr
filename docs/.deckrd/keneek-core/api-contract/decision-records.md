## DR-01: 共通エラー形式に RFC 9457 を採用し、`type` と `code` を 1 対 1 で対応させる - 2026-11-14 06:41:00

**Phase**: review-harden
**Status**: Accepted

### Context

通知 REST API の契約には、共通エラー形式がまだ決まっていない。
REQ-F-003 は、すべてのエラーレスポンスに共通する単一の形式を求めている。
その形式は、HTTP ステータスコードとエラー識別子をメンバーとして持ち、拡張メンバーの追加を許容しなければならない。
また REQ-F-003 は、RFC 9457 (Problem Details for HTTP APIs) を第一候補として評価し、採否と理由を記録することを求めている。

共通エラー形式が決まらないと、Specifications で次を定められない。

- 各エラーケースのエラー識別子と HTTP ステータスコード (REQ-F-004)
- エラー識別子の命名規則と拡張規則 (REQ-F-006)

契約には、検証の環境による制約がある。
契約は、ネットワーク接続と外部 URL への参照を必要とせずに、開発者の端末上で検証する (REQ-F-012)。

RFC 9457 の仕様には、本決定に関わる次の性質がある (一部の抜粋)。

- `type` は、Problem Type を識別する URI 参照である。省略すると `about:blank` とみなす
- `type` の URI は、参照先を解決できなくてもよい
- `status` メンバーは任意である
- 拡張メンバーを追加できる

### Decision

1. 決定 1: 共通エラー形式は RFC 9457 に従う。メディアタイプは `application/problem+json` とする。
2. 決定 2: `type` は、RFC 9457 に従う Problem Type の URI として使う。
3. 決定 3: `code` は、Keneek が独自に定める安定したエラー識別子を表す拡張メンバーとする。
   `code` は、requirements.md 1.3 Terms の「エラー識別子」にあたる。
   `code` は、`type` の URI の命名方式から独立させる。
4. 決定 4: `type` と `code` は 1 対 1 で対応させる。対応は Specifications の 1 か所で管理する。
5. 決定 5: `type` の URI に、参照先を解決できることを要求しない。
6. 決定 6: `type` の URI も契約の一部とする。`type` の URI を変えるときは、後方互換性への影響を評価する。
7. 決定 7: `status`・`type`・`code` は、Keneek のエラー契約の必須メンバーとする。
   `status` の値は、HTTP レスポンスのステータスコードと一致させる。
   Specifications は、この 2 点を必須として明記する。

### Scope

- Applies to: 通知 REST API の契約が定義するすべてのエラーレスポンス
- Not decided here:
  - `type` の URI の方式と具体的な値 → specifications
  - `code` の命名規則と具体的な値 → specifications (REQ-F-006)
  - `type` と `code` の対応を管理する場所 → specifications
  - `status`・`type`・`code` 以外の必須メンバーの一覧 → specifications
  - 各エラーケースの HTTP ステータスコード → specifications (REQ-F-004)
  - エラー区分と、変更の互換性の分類 → 未定 (エラー区分を決める DR を追加する)

### Alternatives Considered

- 独自のエラー形式を定める。既存の標準とツールを再利用できず、クライアントとリンタの実装が増えるため不採用。
- `type` だけを使い、`code` を設けない。識別子を二重管理せずに済む利点はある。
  しかし、Keneek が独自に定めるエラー識別子を、URI の命名方式から独立して持つことができない。そのため不採用。
- `code` だけを使い、`type` を使わない。`type` は RFC 9457 が定める Problem Type の標準の識別子である。
  使わないと RFC 9457 の標準的な使い方から外れるため不採用。
- RFC 9457 に従わず、`status` と `code` だけの最小形式にする。将来の拡張メンバーとの整合を自前で保つ必要があるため不採用。

### Rationale

RFC 9457 を採用する最大の理由は、HTTP API のエラー表現の標準に従い、実装・検証・ドキュメントの重複を減らせる点にある。
RFC 9457 は拡張メンバーを許す。
そのため、REQ-F-003 が求める拡張メンバーの追加と、REQ-F-006 が求めるエラー識別子の追加を、標準の範囲で表せる。

`code` を `type` と別に持つ目的は、URI の命名方式とアプリケーションのエラー識別子を切り離すことにある。
`type` は Problem Type の URI として RFC 9457 に従わせる。
`code` は Keneek のエラー識別子として、URI の方式とは別に安定させる。
2 つの識別子の食い違いは、対応を 1 か所で 1 対 1 に管理することで防ぐ。

`type` の URI に解決できることを要求しない理由は、契約をネットワーク接続なしで検証するためである (REQ-F-012)。
RFC 9457 は、解決できない `type` の URI を許している。

`status` を必須にする根拠は REQ-F-003 にある。REQ-F-003 は、HTTP ステータスコードをメンバーとして持つことを求めている。
RFC 9457 では `status` は任意だが、必須にしても RFC 9457 に反しない。
`status` の値が HTTP レスポンスのステータスコードと食い違うと、1 つのレスポンスから 2 つの異なるステータスを読み取れてしまう。両者を一致させる理由はこの点にある。

`type` と `code` を必須にする理由は、両者を決定 2〜4 で識別子として定めたことにある。
`type` を省略すると `about:blank` とみなされ、`type` と `code` の 1 対 1 の対応が失われる。

### Consequences

- Positive:
  - クライアントは、RFC 9457 に対応した既存のエラー処理とツールを再利用できる
  - `code` は `type` の URI の方式に依存しないため、クライアントは安定した識別子で分岐できる
  - 契約の検証が、`type` の URI の参照先に依存しない
  - エラーレスポンスは常に `status`・`type`・`code` を持ち、`status` は HTTP レスポンスのステータスコードと一致する
- Negative:
  - メディアタイプが `application/json` と異なるため、OpenAPI で明示的に定義する必要がある
  - `type` と `code` の 2 つの識別子を、対応を保ったまま管理する負担がある
  - `type` の URI の変更も、後方互換性を評価する対象になる
- Revisit Trigger:
  - `type` と `code` の 1 対 1 対応を維持できないエラー要件が発生したら、本 DR を見直す
  - 新しい通信方式またはメディアタイプの追加によって、RFC 9457 に基づく共通エラー形式を維持できなくなったら、本 DR を見直す

## DR-02: バッチ登録のレスポンスは all-or-nothing の形状とし、部分成功を表す形状を持たない - 2026-11-14 06:42:57

**Phase**: review-harden
**Status**: Accepted

### Context

バッチ登録のレスポンスを all-or-nothing の形状にする理由が、まだ記録されていない。
バッチ登録は、リクエストで `notifications` 配列を受け取り、複数の通知を 1 回で登録する操作とする (REQ-F-001)。
REQ-F-001 と AC-010 は、レスポンスを all-or-nothing を前提とした形状にすることを要件として定めている。
一方で requirements.md v1.1.0 の Design Decisions の要約では、この方針に対応する Decision Record が無い。

requirements.md v1.1.0 の REQ-F-001 の Rationale は、形状を固定する理由を次のように書いていた。

- 形状を先に固定しておけば、バッチ登録の振る舞いを担う兄弟 issue が all-or-nothing や冪等性を実装するときに、契約を変更せずに済む

セカンドオピニオンのレビューは、この理由が弱いと指摘した。
冪等性とセキュリティは、ヘッダーとエラーに影響する。
そのため、レスポンスの形状を固定しても、契約を変えずに済むとは限らない。

requirements.md v1.1.0 の時点では、バッチ登録の振る舞いについて、本契約と兄弟 issue の間に次の境界を置いていた (REQ-F-007、requirements.md 1.2 Scope の Out of Scope)。

- 本契約は、レスポンスの形状をインターフェースとして定義する
- all-or-nothing の実現方法、冪等性、バリデーションルールは、バッチ登録の振る舞いを担う兄弟 issue が定義する

### Decision

1. 決定 1: バッチ登録のレスポンスは all-or-nothing の形状とする。
   レスポンスは、バッチ全体の成功と失敗の 2 つの形状だけを持つ。
2. 決定 2: 成功時のレスポンスは、入力の各要素に 1 対 1 で、入力と同じ順序で対応する通知ごとの結果を持つ。
   通知ごとの結果は、通知 ID と状態を含む。
3. 決定 3: 失敗時のレスポンスは、共通エラー形式 (DR-01) の単一のエラーとする。
   要素ごとの結果は含まない。
4. 決定 4: 一部の要素だけが成功したことを表すレスポンス形状は定義しない。

### Scope

- Applies to: 通知 REST API の契約が定義するバッチ登録のレスポンスの形状。本 DR が決めるのはレスポンスの形状だけとする
- Not decided here:
  - 再送時の振る舞い (冪等性) → DR-03 決定 6。冪等性は、本 DR とは別の保証として扱う
  - 登録処理の原子性は、責務によって次の 2 つに分けて委ねる。レスポンスの形状は、登録処理の原子性を保証しない
    - 外部から観測できる原子性の保証 → API 契約として specifications (DR-03 決定 1、REQ-F-001)
    - 登録処理での原子性の実現と保証 → バッチ登録の振る舞いを担う兄弟 issue #4 (REQ-F-007)
  - all-or-nothing の実現方法 (トランザクションなど) → バッチ登録の振る舞いを担う兄弟 issue #4 (REQ-F-007)
  - バリデーションルール (requirements.md 1.3 Terms) は、責務によって次の 2 つに分けて委ねる
    - 入力を受け付ける条件・拒否する条件と、拒否に使うエラー識別子 → specifications (REQ-F-007)。外部から観測できる判定結果として、API 契約が定義する
    - 判定アルゴリズムと内部の検証処理 → バッチ登録の振る舞いを担う兄弟 issue #4 (REQ-F-007)
  - 通知ごとの結果の具体的なメンバーと、成功時の HTTP ステータスコード → specifications
  - 失敗時のエラー識別子と HTTP ステータスコード → specifications (REQ-F-004)

### Alternatives Considered

- 部分成功を表すレスポンスにする。クライアントが要素ごとの結果を解釈する必要があり、再送の扱いも複雑になるため不採用。
- レスポンスの形状をバッチ登録の実装に委ねる。契約が実装の後に変わり、PWA の開発を先行できなくなるため不採用。
- 成功時に通知 ID の配列だけを返す。状態を別に取得する必要があり、入力との対応も曖昧になるため不採用。

### Rationale

all-or-nothing を採用する理由は、クライアントがバッチ全体の成功と失敗を一意に解釈できる点にある。
レスポンスが成功と失敗の 2 つの形状しか持たないため、クライアントは部分成功を表すレスポンス形状を解釈する必要がない。
ただし、実際に一部だけが登録された状態が生じないことはレスポンス形状だけでは保証できず、兄弟 issue #4 の登録処理の原子性保証を前提とする。
成功時は、入力と同じ順序で 1 対 1 に結果が並ぶ。そのため、クライアントは各結果がどの入力要素のものかを、追加の照合なしに特定できる。
失敗時は、共通エラー形式 (DR-01) の単一のエラーが返る。そのため、クライアントは他の操作と同じエラー処理でバッチの失敗を扱える。

requirements.md v1.1.0 の REQ-F-001 の Rationale にあった「契約を変更せずに済む」は、採用の理由にしない。
冪等性とセキュリティはヘッダーとエラーに影響する。そのため、レスポンスの形状を固定するだけでは契約の変更を防げない。
再送時の振る舞いは、本 DR と切り離し、外部から観測できる保証として DR-03 決定 6 で扱う。

### Consequences

- Positive:
  - クライアントは、バッチ全体の成功と失敗を一意に解釈できる
  - 成功時の結果を、入力の要素と順序で対応付けられる
  - 失敗時のレスポンスを、他の操作と同じ共通エラー形式の処理で扱える
  - レスポンス形状の契約テストでは、バッチ全体の成功形状と失敗形状を検証し、部分成功形状を要求しない
- Negative:
  - 部分成功を表すレスポンス形状が無いため、クライアントは要素ごとの成功と失敗の情報を得られない
  - 登録処理の原子性は、レスポンスの形状だけでは保証されない。外部から観測できる原子性の保証は API 契約に含まれる。
    登録処理での原子性は、バッチ登録の振る舞いを担う兄弟 issue #4 が実現し、保証しなければならない
- Revisit Trigger:
  - バッチ登録の API 契約において、要素単位の成功・失敗を区別して返す必要が生じたら、本 DR を見直す

- requirements/requirements.md: REQ-F-007
- requirements/requirements.md: AC-010
- decision-records.md: DR-01
- decision-records.md: DR-03
- GitHub Issue: #3

## DR-03: 外部から観測できる振る舞いの保証を API 契約に含め、内部の実現方法は兄弟 issue に委ねる - 2026-11-14 06:50:35

**Phase**: review-harden
**Status**: Accepted

### Context

契約がどこまでを定めるかの境界が、外部から観測できる振る舞いについて決まっていない。
requirements.md v1.1.0 の REQ-F-007 は、契約をインターフェースの定義に限定している。
同じ要件は、冪等性、照会・キャンセルの判定ロジック、状態管理 (状態遷移)、ローカルセキュリティなどを兄弟 issue の責務として契約から外している。
本 DR に関わる兄弟 issue は次の 3 つとする (Out of Scope に挙がる兄弟 issue の一部)。

- #4 (バッチ登録)
- #5 (照会・キャンセル)
- #6 (ローカルセキュリティ)

セカンドオピニオンのレビューは、この境界では外部から観測できる事項まで兄弟 issue の決定に任されると指摘した。
指摘した事項は次の 3 つとする。

- 冪等性は、再送時のヘッダーと衝突エラーに影響する
- 認証は、資格情報の渡し方に影響する
- キャンセルは、結果の意味に影響する

これらを兄弟 issue の決定に任せると、契約が後から変わる。

バッチ登録の再送時の振る舞いも、この境界の上にある。
DR-02 は、バッチ登録のレスポンスを all-or-nothing の形状に決めた。
DR-02 は、冪等性をレスポンスの形状とは別の保証として扱い、再送時の振る舞いを外部から観測できる保証を決める DR に委ねている。

### Decision

1. 決定 1: 外部から観測できる振る舞いの保証は、API 契約に含める。
2. 決定 2: 保証を内部でどう実現するかは契約に定めず、兄弟 issue に委ねる。
3. 決定 3: 保証ごとに独自の状態 (`Agreed`・`Provisional` など) を付けて管理する方式は導入しない。
4. 決定 4: 未確定の事項は Open Questions として管理する。合意した判断は DR に記録する。
5. 決定 5: 契約を確定する前に、兄弟 issue との整合を確認する。
6. 決定 6: バッチ登録の再送時の振る舞い (冪等性) のうち、外部から観測できる部分は決定 1 に従って契約に含める。
   冪等性は、DR-02 が決めたレスポンスの形状とは別の保証として扱う。

### Scope

- Applies to: 通知 REST API の契約が定義するすべての操作の、外部から観測できる振る舞い。
  バッチ登録の再送時の振る舞い、キャンセルの結果、認証の資格情報の渡し方を含む
- Not decided here:
  - 契約に含める保証の具体的な一覧 → specifications (未確定の間は Open Questions で管理する)
  - 再送時の振る舞いの具体的な内容 (再送の結果が属するレスポンスの区分、再送を識別するリクエストヘッダーの有無など) → specifications
  - キャンセルの結果の具体的な意味 (キャンセル後の通知の状態、キャンセル済みの通知を再びキャンセルしたときに成功とするかエラーとするか) → specifications
  - 認証に必要なリクエスト上の情報、資格情報の送信形式 (HTTP ヘッダー名・配置を含む)、認証失敗時の外部応答 → specifications
    - 資格情報の発行・保存・検証など、認証メカニズムの内部実装 → 兄弟 issue #6
    - 認証方式によって外部仕様が変わる場合は、仕様を確定する前に issue #6 と整合を確認する
  - REQ-F-007 の要件文の改訂 (1.3 Terms の「インターフェース」「振る舞い」との整合を含む)、AC-004・US-003 の改訂、および REQ-C-005 の認証責務との整合確認 → requirements.md (4 本の DR の完成後にまとめて実施する。本 DR では変更しない)
  - 兄弟 issue との整合を確認する具体的な方法 → 未定 (契約を確定するまでに決める)
    - 整合確認は兄弟 issue の実装完了や内部設計の確定を要求しない
    - API 契約の各保証について、兄弟 issue の責務、実現可能性、既知の制約に矛盾がないことを確認する
  - 冪等性、照会・キャンセルの判定ロジック、状態管理 (状態遷移)、認証メカニズムの実現方法 → 各兄弟 issue (#4、#5、#6)

### Alternatives Considered

- 契約をインターフェースの定義だけに保ち、兄弟 issue が後から契約に保証を追加する。
  契約の変更が破壊的になりやすく、クライアントへの影響を管理できないため不採用。
- 契約が振る舞いをすべて定義する。兄弟 issue と責務が重複し、記述が矛盾する可能性のため不採用。
- 兄弟 issue の内部設計や実装の完了を待ってから契約を確定する。
  契約が実装の基準にならず、PWA の開発を先行できないため不採用。
  ただし、Decision 5 に従う責務・実現可能性・既知の制約の整合確認は、契約確定前に実施する。
- 外部から観測できる保証を契約に含め、保証ごとに `Agreed`・`Provisional` の状態を付ける。
  未確定と合意済みの区別は、Open Questions と DR ですでに表せる。
  独自の状態を加えると、同じ区別を 2 つの仕組みで持つことになるため不採用。

### Rationale

外部から観測できる振る舞いを契約に含める最大の理由は、契約が後から変わる原因を、契約の側で先に押さえること。
再送時のヘッダー、衝突エラー、資格情報の渡し方、キャンセルの結果の意味は、いずれもクライアントがレスポンスやリクエストを通して直接扱う。
これらを兄弟 issue が後から決めると、契約の変更が破壊的になりやすい。
破壊的変更には、新しい API メジャーバージョンと移行手順の記述が必要になる (REQ-F-011)。

内部の実現方法を兄弟 issue に委ねる理由は、REQ-F-007 が避けようとした責務の重複と矛盾を、改訂後も避けることにある。
契約が定めるのは結果として観測できる点に限る。
トランザクションや判定ロジックは、契約で定めた保証を満たす範囲で兄弟 issue が選べる。
認証に必要なリクエスト上の情報、資格情報の送信形式、認証失敗時の外部応答はクライアントが扱う API 契約として specifications に定義する。
資格情報の発行・保存・検証などの内部メカニズムは issue #6 に委ねる。認証方式が外部仕様に影響する場合は、issue #6 と整合を確認する。

独自の状態管理を導入しない理由は、未確定の事項と合意した判断を、既存の Open Questions と DR で区別できることにある。
Open Questions は requirements.md などにある未解決事項を管理し、DR は合意した設計判断とその理由を記録する。
specifications は、確定した API の動作仕様を管理する。
DR の `Accepted` はその DR の設計方針が採用されたことを意味し、関連する個別仕様のすべてが確定したことを意味しない。
Open Questions の事項を解決した際には、必要な判断を DR に記録し、具体的な API 契約を specifications に反映する。

契約の確定前に兄弟 issue との整合を確認する理由は、契約が定める保証を実現するのが兄弟 issue であることにある。
整合確認は兄弟 issue の実装や内部設計の完了を待つものではなく、契約上の保証に対する責務、実現可能性、既知の制約の矛盾を確認するものとする。
確定前に整合を確かめれば、確定後に契約を変える必要を減らせる。
確定後に兄弟 issue が契約の変更を必要とした場合は、REQ-F-009 に従い契約を先に更新する。

### Consequences

- Positive:
  - 兄弟 issue の決定によって、確定後の契約が破壊的に変わる可能性が下がる
  - クライアントは、再送、キャンセル、認証の結果を契約だけを見て扱える
  - 兄弟 issue は、外部から観測できる保証を満たす範囲で実現方法を選べる
  - 未確定の事項と合意した判断の管理が、Open Questions と DR に一本化される
- Negative:
  - 契約されている範囲が広がり、specifications で決める事項が増える
  - 契約を確定する前に、兄弟 issue との整合を確認する手間がかかる
  - REQ-F-007 の要件文、AC-004、US-003 は「インターフェースのみ」を前提にしているため、本 DR に合わせて改訂する必要がある
  - REQ-C-005 は認証メカニズムとクライアント向け認証インターフェースの境界について整合性を確認する必要がある
  - requirements.md の改訂は 4 本の DR が完成した後にまとめて行うため、それまでは既存記述との不整合が残る
- Revisit Trigger:
  - 外部から観測できる振る舞いと内部の実現方法の責務分離が成立せず、API 契約と兄弟 issue の責務が重複または欠落する場合、本 DR を見直す
  - 兄弟 issue の実現方法の変更が、契約に含めた保証の変更を繰り返し求めるようになったら、本 DR を見直す

## DR-04: エラーの分類とクライアントの対処を分離し、エラー識別子の追加を無条件に後方互換としない - 2026-11-14 07:06:34

**Phase**: review-harden
**Status**: Accepted

### Context

エラーの区分と、エラー識別子の変更の互換性が決まっていない。
DR-01 は、この 2 つを、エラー区分を決める DR に委ねている。

requirements.md v1.1.0 の REQ-F-006 は、エラー識別子の追加を常に後方互換な変更として扱う。
同じ要件は、クライアントが未知のエラー識別子を受け取ったときに、HTTP ステータスコードで処理を続けられることを求めている。
AC-012 は、識別子の追加を契約バージョンの MAJOR を上げずに行えることとしている。

requirements.md 1.3 Terms は、後方互換性を「既存クライアントが変更なしに動作し続けられること」と定義している。
その対象は、リクエスト、レスポンス、エラー形式、エラー識別子とする。
破壊的変更のときは、新しい API メジャーバージョンを導入する (REQ-F-011)。

セカンドオピニオンのレビューは、REQ-F-006 について次の 2 点を指摘した。

- HTTP ステータスコードへのフォールバックだけでは、クライアントが再試行・再認証・入力の修正のどれを選ぶかを保てない場合がある
- 「識別子の追加」と「既存の操作の意味の変更」を区別しなければならない。たとえば、以前は成功したリクエストが新しいエラーを返すようになる変更がある

ハードニングのレビューは、分類を 5 つに固定し、5xx を再試行の分類とする案を出した。
本 DR は、この案を採らずに、分類とクライアントの対処を分ける。

再送時の振る舞いについては、DR-03 決定 6 が、外部から観測できる部分を契約に含めると決めている。

### Decision

1. 決定 1: エラーの分類と、クライアントの対処方法を分離する。各エラー識別子は、ちょうど 1 つの分類に属する。
2. 決定 2: クライアントの対処方法は、エラー識別子 (`code`) ごとに、API 契約の一部として specifications に定める。
   RFC 9457 のエラーレスポンスに、対処方法を表す拡張メンバー (`retryable`・`action` など) を加えない。
3. 決定 3: クライアントの対処方法では、次の 3 つを独立した判断点として区別する。
   - 再試行可能性: 同じリクエストを再試行することに効果があるか
   - 再送安全性: 再送によって副作用を重複させるおそれはあるか
   - 結果の確定性: クライアントがリクエストの処理結果を確定できるか

   3 つすべてを、各エラー識別子の必須の属性とはしない。各識別子に必要な対処方針は specifications に定める。
4. 決定 4: クライアントの対処方法を、HTTP ステータスコードだけで判断しない。5xx を一律に再試行可能として扱わない。
   各 `code` の仕様が、対処に必要な条件を示す。
5. 決定 5: エラー識別子を得られない場合の扱いも、契約に定める。
   応答を受け取れない通信失敗は、結果が確定しない場合の扱いに含める。
6. 決定 6: 再送時の重複防止を API が保証する場合、その外部契約は各操作の契約として specifications に定める (DR-03 決定 6)。
   重複防止の内部の実現方法は、担当する兄弟 issue に委ねる。
   本 DR が扱うのは、クライアントがその保証をどう解釈し、エラーが起きたときにどう対処するかに限る。
7. 決定 7: `Retry-After` などの標準の HTTP ヘッダーで、動的な情報を提供することは妨げない。
8. 決定 8: 新しいエラー識別子の追加と、既存の API 操作の変更を区別して評価する。
   識別子の追加であることだけを理由に、後方互換と判断しない。
   新しいエラー識別子の追加を後方互換とするのは、既存の API 操作の次のいずれも変えない場合に限る。
   - 成功条件
   - 再送時の保証
   - クライアントに求める対処
9. 決定 9: 既存クライアントから観測できる振る舞い、または既存クライアントに求める対処が変わる変更は、破壊的変更として評価する。
   識別子の追加を伴うかどうかは問わない。
10. 決定 10: クライアントは、未知のエラー識別子を、次の順で扱う。
    - その識別子の分類が既知の契約に従って解釈できる場合に限り、分類に基づいて扱う
    - 分類が不明な場合、または解釈できない場合は、HTTP ステータスコードを参照する

    HTTP ステータスコードだけでは、再送安全性と処理結果の確定性を保証できない。
    そのため、再送安全性を確認できない冪等でない操作を、無条件に自動で再試行しない。
11. 決定 11: クライアントは、未知のエラー拡張メンバーを無視する。既知のメンバーの意味は変えない。

### Scope

- Applies to: 通知 REST API の契約が定義するすべてのエラーと、エラー識別子を得られない通信失敗に対するクライアントの対処。
  エラー識別子とエラー拡張メンバーの変更の互換性の評価を含む
- Consistency: DR-01 が決めた `type` と `code` の対応、および DR-03 決定 6 (再送時に観測できる振る舞いを契約に含める) と整合させる。
  本 DR はどちらも変更しない
- Not decided here:
  - 分類の具体的な名前と一覧 → specifications
  - エラー識別子の一覧と、各識別子の対処方針 → specifications (REQ-F-004、REQ-F-006)
  - 未知のエラー識別子から分類を判別する方法 → specifications (REQ-F-006 の命名規則)
  - エラー識別子を得られない場合の具体的な扱い → specifications
  - 各操作の再送時に観測できる具体的な振る舞い → specifications (DR-03 決定 6)
  - 重複防止の仕組みの実現方法 → 担当する兄弟 issue (バッチ登録の再送は #4)
  - 再試行を許す条件・再送安全性・待機の条件など、API 契約が保証する事項 → specifications
  - 指数バックオフ・ジッター・最大試行回数などの具体的な再試行のアルゴリズム → クライアントの実装
    (API 契約で保証する必要のある部分に限り specifications)。本 DR は特定のアルゴリズムを固定しない
  - `Retry-After` などの標準の HTTP ヘッダーを使うかどうかと、使う場合の意味 → specifications
  - エラー以外を含む、破壊的変更と非破壊的変更の判断基準の全体 → specifications (REQ-F-011)
  - REQ-F-006 と AC-012 の改訂 → requirements.md (4 本の DR の完成後にまとめて実施する。本 DR では変更しない)

### Alternatives Considered

- エラー識別子の追加をすべて後方互換とし、未知の識別子は HTTP ステータスコードだけで処理する。
  HTTP ステータスコードだけでは、クライアントが再試行・再認証・入力の修正のどれを選ぶかを保てない。
  また、以前は成功したリクエストが新しいエラーを返すような、既存の操作の意味を変える追加まで後方互換に含まれる。そのため不採用。
- エラー識別子を追加するたびに、契約バージョンの MAJOR を上げる。
  識別子を追加する自由がなくなり、兄弟 issue が必要なエラー識別子を追加できなくなる (REQ-F-006)。そのため不採用。
- エラーレスポンスに `retryable`・`action` などの拡張メンバーを加え、対処方法をレスポンスで伝える。
  対処方法は `code` ごとに specifications で契約として定める。
  レスポンスにも載せると、同じ情報を specifications とレスポンスの 2 か所で持つことになる。
  また、再試行可能性・再送安全性・結果の確定性は独立した判断点であり (決定 3)、単一のフラグでは表せない。そのため不採用。
  これは、対処方法を表す拡張メンバーを採らない判断に限る。
  RFC 9457 の拡張メンバー全般を禁止するものではない (拡張メンバーの追加は DR-01 が認め、未知のメンバーの扱いは決定 11 が定める)。
- ハードニングのレビューが出した、分類を 5 つに固定する案を採る。5 つの分類は、入力の修正 (4xx の検証エラー)、再認証 (401)、不存在 (404)、状態の競合 (409)、再試行 (5xx) とする。
  5xx を一律に再試行とすると、再試行可能性・再送安全性・結果の確定性を区別できない。
  分類が対処を兼ねるため、分類と対処を分離できない。そのため不採用。

### Rationale

分類や HTTP ステータスコードだけでは、クライアントの取るべき対処を特定できない。これが、分類と対処を分離する最大の理由となる。
同じ 5xx でも、再試行に効果があるか、再送で副作用が重複するか、処理結果を確定できるかは異なりうる。
3 つの判断点を区別すれば、クライアントは副作用を重複させずに対処を選べる。

対処方法を `code` ごとに specifications で定め、レスポンスに載せない理由は、対処方法が契約の一部であることにある。
クライアントは、契約を見て `code` ごとの対処を実装できる。
共通エラー形式は、DR-01 が決めた RFC 9457 の形のまま保てる。

エラー識別子を得られない場合の扱いを定める理由は、その場合には `code` ごとの対処を使えないことにある。
応答を受け取れない通信失敗では、クライアントは処理結果を確定できない。

識別子の追加を無条件に後方互換としない理由は、1.3 Terms の後方互換性の定義にある。
互換性を決めるのは変更の形 (識別子の追加かどうか) ではなく、既存クライアントへの影響となる。
既存の成功条件・再送時の保証・既存クライアントに求める対処のどれかが変わると、既存クライアントは変更なしに動作を続けられなくなる。
そのため、この変更は定義上、後方互換ではない。
一方で、この 3 つを変えない追加は、既存クライアントに影響しない。兄弟 issue は、この範囲で MAJOR を上げずに識別子を追加できる。

未知の識別子を、HTTP ステータスコードより先に分類で扱う理由は、HTTP ステータスコードだけでは対処の選択を保てないことにある。
分類に基づく扱いを、既知の契約に従って解釈できる場合に限る理由は、解釈できない分類から対処を推測すると誤った対処を選ぶおそれがあることにある。
HTTP ステータスコードは、再送安全性と処理結果の確定性を示さない。
再送安全性を確認できない冪等でない操作を自動で再試行しない理由は、再送で副作用が重複するおそれを避けることにある。
具体的な再試行のアルゴリズムをクライアントの実装に委ねる理由は、契約が保証すべきなのは再試行を許す条件であり、試行の間隔や回数の決め方ではないことにある。

未知の拡張メンバーを無視する理由は、拡張メンバーを追加できる余地を残すことにある (REQ-F-003、DR-01)。
既知のメンバーの意味を変えると、既存クライアントの解釈が変わる。そのため、意味は変えない。

### Consequences

- Positive:
  - クライアントは、`code` ごとに契約で定めた対処を選べる
  - 5xx を一律に再試行しないため、冪等でない操作で副作用を重複させるおそれが減る
  - 共通エラー形式は、DR-01 の RFC 9457 の形のまま保たれる
  - 兄弟 issue は、成功条件・再送時の保証・既存クライアントに求める対処を変えない範囲で、MAJOR を上げずに識別子を追加できる
- Negative:
  - specifications は、各エラー識別子の対処方針と、エラー識別子を得られない場合の扱いを定めなければならない
  - 識別子を追加するたびに、成功条件・再送時の保証・既存クライアントに求める対処を変えないかを評価する手間がかかる
  - レスポンスが対処方法を運ばないため、クライアントは `code` ごとの対処を契約から取り込んで持つ必要がある
  - REQ-F-006 と AC-012 は、識別子の追加を常に後方互換とし、HTTP ステータスコードへのフォールバックだけを示している。
    本 DR に合わせて、4 本の DR の完成後にまとめて行う requirements.md の改訂で改める必要がある。それまでは既存記述との不整合が残る
- Revisit Trigger:
  - 同じ `code` でもリクエストごとに対処が変わり、`code` ごとの定義と標準の HTTP ヘッダーでは対処を伝えられなくなったら、本 DR を見直す
  - 識別子の追加の多くが破壊的変更と評価され、兄弟 issue が必要なエラーを追加できなくなったら、本 DR を見直す

## DR-05: 契約確定前の兄弟 issue との整合確認は、保証ごとの照合結果を記録として Specifications に残す - 2026-11-14 07:43:22

**Phase**: review-harden
**Status**: Accepted

### Context

契約確定前の兄弟 issue との整合確認について、何をもって「確認した」とするかの基準と、確認の記録の置き場所が決まっていない。
DR-03 決定 5 は、契約を確定する前に兄弟 issue との整合を確認すると決めた。
DR-03 は、整合確認の範囲を次のように定めている。

- 兄弟 issue の実装の完了や内部設計の確定を要求しない
- API 契約の各保証について、兄弟 issue の責務、実現可能性、既知の制約に矛盾がないことを確認する

一方で、確認の具体的な方法は DR-03 では決めていない。

requirements.md v1.2.1 の REQ-F-009 は、DR-03 決定 5 を要件として定めている。
REQ-F-009 に紐づく AC-020 は、整合確認の結果として、矛盾がないと確認されていることを求める。
fix レビューは、AC-020 について次の 2 点が定まっていないと指摘した。

- 何をもって「確認されている」とするかの判定基準
- 確認の記録を置く場所

requirements.md の Open Questions には「兄弟 issue との整合を確認する具体的な方法をどうするか (契約の確定までに決める)」が残っている。
この項目の Owner は契約メンテナとしている。

兄弟 issue と API 契約の関わり方は、issue によって異なる。

- #4 (バッチ登録)、#5 (照会・キャンセル)、#6 (ローカルセキュリティ) は、DR-03 が外部から観測できる保証に関わる兄弟 issue として挙げた 3 つ
- #7 (永続化) は、requirements.md 1.2 Scope で、契約のデータ形状と状態の集合を通じて契約に間接的に依存するとされている

### Decision

1. 決定 1: 契約確定前の兄弟 issue との整合確認は、記録として残す。本 DR は DR-03 決定 5 を具体化するものであり、DR-03 を置き換えない。
2. 決定 2: 整合確認の記録は Specifications に置く。
3. 決定 3: 記録は、契約の各保証について、照合対象の兄弟 issue との照合結果を持つ。
   照合結果は、保証と照合対象の組ごとに、次の 3 つを区別する。
   - 整合
   - 矛盾あり
   - 未確認

   記録の存在だけでなく、保証ごとの照合結果と未解決の矛盾も、記録から検証できなければならない。
4. 決定 4: 基本の照合対象は、#4 (バッチ登録)、#5 (照会・キャンセル)、#6 (ローカルセキュリティ) の 3 つとする。
5. 決定 5: #7 (永続化) は、API 契約の保証が永続化の責務へ依存する場合だけ、その保証の照合対象に加える。
6. 決定 6: 契約を確定するときは、照合対象の保証について次の 2 点を条件とする。
   - 照合が完了している (照合結果に「未確認」が残っていない)
   - 未解決の矛盾が残っていない (「矛盾あり」の照合結果は、すべて解消されている)
7. 決定 7: 整合確認とその記録に、兄弟 issue の実装の完了や内部設計の確定を要求しない。

### Scope

- Applies to: 通知 REST API の契約を確定する前に行う、兄弟 issue との整合確認とその記録
- Consistency: DR-03 決定 5 と、DR-03 Scope が定めた整合確認の範囲 (責務・実現可能性・既知の制約) に従う。
  本 DR は DR-03 を置き換えない。DR-03 と同じく、兄弟 issue の実装の完了や内部設計の確定を要求しない
- Responsibility boundary with #8 (e2e テスト):
  - #8 は照合対象に加えない。#8 は API 契約を検証する側の責務を持つ
  - e2e テストで見つかった契約の矛盾は、契約の確定前に解消する
- Not decided here:
  - 記録の形式の詳細 (記録の構成、項目の書き方、照合結果の 3 つの区別の表し方など) → specifications
  - 照合の具体的な手順 (誰がどう照合するか) → requirements.md の Open Questions (Owner: 契約メンテナ)。契約の確定までに決める
  - REQ-F-009 の要件文と AC-020 の改訂 → requirements.md

### Alternatives Considered

- 判定基準を定めず、プルリクエストのレビューでの目視確認に任せる。
  記録が残らず、確認したかどうかを後から検証できないため不採用。
- 兄弟 issue ごとの承認を、契約確定の条件にする。
  兄弟 issue の設計の確定を事実上要求することになる。
  これは、確認に兄弟 issue の内部設計の確定を求めないとする REQ-F-009 に反するため不採用。
- 整合確認の記録を decision-records.md に置く。
  DR は設計判断とその理由を記録する文書であり、保証ごとの照合結果の一覧とは性質が異なる。
  また、DR の `Accepted` は設計方針の採用を表し、個別の仕様の確定を表さない (DR-03)。
  照合結果を DR に置くと、仕様の確定と DR の採用を混同しやすくなるため不採用。

### Rationale

記録を Specifications に置く最大の理由は、照合する保証そのものが Specifications で確定することにある。
DR-03 は、未確定の事項を Open Questions に、合意した設計判断を DR に、確定した API の動作仕様を Specifications に記録すると整理した。
保証と照合結果を同じ場所に置けば、確定する保証ごとに照合結果を対で追える。
記録が Deckrd のドキュメントの中にあれば、プルリクエストのレビューで記録の存否と内容を確認できる。

保証ごとの照合結果と未解決の矛盾まで検証できるようにする理由は、AC-020 の判定基準を定めることにある。
記録があるだけでは、どの保証をどの兄弟 issue と照らし合わせたかが分からない。
保証ごとの照合結果と未解決の矛盾が読み取れれば、矛盾が解消されたかを契約の確定時に判定できる。
「未確認」と「整合」を区別する理由は、照合していない保証を整合と取り違えないことにある。
この区別があれば、契約の確定時に照合が完了したかを判定できる。

基本の照合対象を #4、#5、#6 とする理由は、DR-03 がこの 3 つを外部から観測できる保証に関わる兄弟 issue として挙げていることにある。
永続化を担う #7 は、契約のデータ形状と状態の集合を通じて、間接的に契約へ依存する。
そのため、#7 を照合対象に加えるのは、保証が永続化の責務へ依存する場合に限る。
e2e テストを担う #8 は、API 契約を検証する側の責務を持ち、照合する側ではない。
そのため、#8 は照合対象に加えず、e2e テストで見つかった契約の矛盾を契約の確定前に解消することで扱う。

照合の具体的な手順を本 DR で決めない理由は、記録に求める条件と、照合を進める手順を分けて扱えることにある。
手順は requirements.md の Open Questions で契約メンテナが決める。

### Consequences

- Positive:
  - AC-020 の「確認されている」を、記録の存在と内容、照合の完了 (「未確認」が残っていない)、未解決の矛盾が残っていないことで判定できるようになる
  - Specifications の中で、確定した保証とその照合結果を対にして追える
  - 兄弟 issue の実装や内部設計の完了を待たずに、契約を確定できる
- Negative:
  - Specifications は、契約の各保証について照合結果の記録を持たなければならない
  - 保証ごとに、永続化の責務に依存するかを判断し、#7 を照合対象に加えるかを決める手間がかかる
  - REQ-F-009 と AC-020 は、記録とその所在を定めていない。本 DR に合わせて requirements.md を改訂する必要があり、それまでは既存記述との不整合が残る
  - 照合の具体的な手順は未定のまま残り、契約の確定までに決める必要がある
- Revisit Trigger:
  - 内部設計の確定を整合確認の前提とする必要が生じ、決定 7 の再検討が必要になったら、本 DR を見直す
  - #4、#5、#6、#7 以外の兄弟 issue の責務に依存する保証が API 契約に現れたら、照合対象の範囲を見直すために本 DR を見直す
