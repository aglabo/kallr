## 1. Overview

### 1.1 Purpose

本書は、通知 REST API 契約の「統治」にあたる外部保証を定義する。対象は次の 4 つとする。

- 契約が唯一の正であることと、変更の順序
- 兄弟 issue との整合確認の記録の形式と、契約を確定する条件
- 契約バージョン、API メジャーバージョン、破壊的変更の扱い
- 契約成果物の構成、配置、ローカル検証の入口と、その保証の範囲

エンドポイント、データ形状、エラー仕様そのものの定義は、他の分割ファイルが担当する。

### 1.2 Scope

本書は、振る舞いの規則と分類の意味を定義する。
実装の詳細は対象外とする。

担当する要件は次のとおりとする。

- REQ-F-009、REQ-F-010、REQ-F-011、REQ-F-012
- REQ-NF-001、REQ-NF-002
- REQ-C-001、REQ-C-002、REQ-C-003、REQ-C-004、REQ-C-005

## 2. Design Principles

### 2.1 Classification Philosophy

本書には 2 種類の「分類」がある。どちらも内部の実現方法ではなく、外部から観測できる影響で判断する。

- 変更の分類について。契約の変更が破壊的か非破壊的かは、変更の形式で決めない。既存クライアントから観測できる振る舞い、または既存クライアントに求める対処が変わるかどうかで決める (DR-04 決定 8、9)。
- 照合結果の分類について。保証と照合対象の組ごとに「整合」「矛盾あり」「未確認」を区別する。照合していないものを「整合」と扱わない。未確認の事項を暗黙の保証に変換しない (DR-05)。

### 2.2 Design Assumptions

- 現時点で、契約成果物、検証ツール、HTTP サーバーのコードは存在しない。本書の検証に関する記述は、実装前の要求仕様である。
- 兄弟 issue (#4、#5、#6、#7) との照合結果は、初期状態をすべて「未確認」とする。G-04〜G-06 については、issue #5・#7 の下書きを用いた照合結果を 3.3.3 に記録している。その他の組は未確認である。
- Keneek アプリのリリースバージョンと契約バージョンは別の値であり、互いに影響しない。
- 本書は Accepted の DR の決定を変更しない。DR が specifications に委ねた事項だけを決める。
- 「(既定値・レビュー対象)」と付けた値は、Spec 生成時の既定値であり、レビューで確認する。

### 2.7 DD to DR Promotion Criteria

> **Purpose**: Guidelines for determining when a DD should be promoted to a formal DR.
> Promotion is a **human judgment** — these criteria inform, not automate.

**Consider promoting a DD when:**

1. Cross-specification Impact — The decision affects multiple specifications or modules
2. Architectural Significance — The decision constrains future design choices
3. Non-trivial Alternatives — Multiple viable options existed
4. Stakeholder Visibility Required — The decision should be reviewable by external parties

**Keep as DD when:**

- Decision is local to this specification only
- No significant alternatives existed
- Rationale is self-evident from context

> **Action**: To promote, run `/deckrd dr --add` with the DD context,
> then update DD Status to `Promoted → DR-xx`.

## 3. Behavioral Specification

### 3.1 Input Domain

- Input Type: 契約成果物 (OpenAPI ドキュメント、独立した JSON Schema、エラーカタログ) への変更案。整合確認の照合結果。ローカル検証の対象となる 3 つの成果物
- Assumptions:
  - 変更案は、インターフェースまたは外部から観測できる保証に影響するものと、影響しないもの (説明文の修正など) の両方を含む
  - 照合結果は、保証と照合対象の兄弟 issue の組ごとに与えられる
  - 検証の実行環境には、ネットワーク接続がない場合を含む

### 3.2 Output Semantics

- Output Meaning: 変更の分類、決定される契約バージョンの変化、契約を確定してよいかの判定、ローカル検証の結果 (違反の報告と終了コード)
- Possible Outcomes:
  - 変更は破壊的変更と分類され、契約バージョンの MAJOR が上がり、新しい API メジャーバージョンが導入される
  - 変更は非破壊的な追加と分類され、契約バージョンの MINOR が上がる
  - 変更は明確化のみと分類され、契約バージョンの PATCH が上がる
  - 契約は確定してよい (照合対象の保証に「未確認」がなく、「矛盾あり」がすべて解消されている)
  - 契約は確定できない (「未確認」または未解消の「矛盾あり」が残っている)
  - ローカル検証は成功する (違反なし)
  - ローカル検証は失敗する (違反を報告し、非ゼロの終了コードを返す)

### 3.3 Consistency Record (REQ-F-009、DR-05)

#### 3.3.1 記録の置き場所と構成

整合確認の記録は、本書の 3.3 に置く。decision-records.md には置かない (DR-05 決定 2)。

記録は、保証と照合対象の兄弟 issue の組ごとに、次の項目を持つ。

| 項目       | 内容                                                                                                        |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 保証 ID    | 3.3.3 の表の G-NN                                                                                           |
| 照合対象   | #4 (バッチ登録)、#5 (照会・キャンセル)、#6 (ローカルセキュリティ)、条件付きで #7 (永続化)                   |
| 照合結果   | 「整合」「矛盾あり」「未確認」のいずれか                                                                    |
| 根拠       | 照合した兄弟 issue の責務、実現可能性、既知の制約のうち、結果の根拠にした記述の参照。「未確認」では空でよい |
| 矛盾の内容 | 結果が「矛盾あり」のときだけ記す。矛盾の内容と、解消の状況 (未解消 / 解消済み) を含む                       |

#### 3.3.2 照合結果の意味

| 照合結果 | 意味                                                                                   |
| -------- | -------------------------------------------------------------------------------------- |
| 整合     | 保証が、照合対象の責務、実現可能性、既知の制約と矛盾しないことを、根拠とともに確認した |
| 矛盾あり | 保証が、照合対象の責務、実現可能性、既知の制約のいずれかと矛盾することを確認した       |
| 未確認   | まだ照合していない。または、照合の根拠を得られていない                                 |

#### 3.3.3 初期の記録表

初期の記録は、全行を「未確認」から始めた。v2.1.0 で G-04〜G-06 の内容を改訂し、issue #5・issue #7 の下書きと照合した結果を記録した (下の「照合の記録」)。
v2.3.0 で G-04 に DR-14 の保証を加えた。DD-GV-13 により、G-04 の照合結果は「未確認」とする (改訂前も「未確認」だった)。ほかの行は、まだ照合していない。

#### 3.3.4 契約を確定する条件

- 照合結果に「未確認」が残っていない
- 「矛盾あり」の照合結果が、すべて解消されている

### 3.4 Contract Versioning (REQ-F-010)

- 契約バージョンは、OpenAPI ドキュメントの `info.version` に宣言する (DD-GV-01)。
- 形式は SemVer の `MAJOR.MINOR.PATCH` で、3 つの非負整数をドットで区切る。初期値は 1.0.0 (既定値・レビュー対象)。
- 契約バージョンは Keneek アプリのリリースバージョンとは別の値であり、互いに影響しない。アプリだけを変更しても契約バージョンは変わらない。契約だけを変更した変更では、契約バージョンを更新し、アプリのリリースバージョンの宣言は変更しない。
- Deckrd ドキュメントの frontmatter `version` (ドキュメントバージョン) は、契約バージョンとは無関係である。
- 更新規則は次のとおりである。

| 変更の分類                                  | 契約バージョン | API メジャーバージョン |
| ------------------------------------------- | -------------- | ---------------------- |
| 破壊的変更                                  | MAJOR を上げる | 新しいメジャーを導入   |
| 既存クライアントに影響しない追加            | MINOR を上げる | 変えない               |
| 意味を変えない明確化 (説明文、例の修正など) | PATCH を上げる | 変えない               |

#### API メジャーバージョンの識別

- API メジャーバージョンは URL パスの先頭の `/v1` で識別する (DD-GV-02)。
- パスの数字は、契約バージョンの MAJOR と一致する。
- 同じ MAJOR の間は、パスを変えない。破壊的変更のときだけ `/v2` のように新しいパスを導入する。

### 3.5 Breaking and Non-breaking Change Criteria (REQ-F-011)

> 判断の根拠は DR-04 決定 8、9 である。既存クライアントから観測できる振る舞い、または既存クライアントに求める対処が変わる変更は、破壊的変更とする。識別子の追加を伴うかどうかは問わない。
> 成功レスポンス (登録済み通知と応答本文) へのメンバーの追加と、既存メンバーの変更の扱いは DR-15 による。
> 本表は既定値であり、レビュー対象である。

| 変更の内容                                                                                                                                                                                                                                                                 | 分類       | 根拠                                                                             |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | -------------------------------------------------------------------------------- |
| 既存の操作 (パス、メソッド) の削除、または名前の変更                                                                                                                                                                                                                       | 破壊的     | 既存クライアントが呼び出せなくなる                                               |
| 既存のリクエストへの必須項目 (パラメータ、ヘッダー、フィールド) の追加                                                                                                                                                                                                     | 破壊的     | これまで成功したリクエストが失敗する                                             |
| 既存フィールドの削除、型・形式・意味の変更                                                                                                                                                                                                                                 | 破壊的     | 既存クライアントの解釈が変わる (成功レスポンスのメンバーについては DR-15 決定 3) |
| 検証制約の厳格化 (要素数や文字列長の上限引き下げ、許可する値の削除など)                                                                                                                                                                                                    | 破壊的     | これまで成功したリクエストが新しいエラーになる                                   |
| 成功条件の変更、または成功・失敗のレスポンス形状の変更 (成功と失敗の 2 つの形状の構成の変更、部分成功を表す形状の追加など)。成功レスポンスへのメンバーの追加は、この行ではなく「成功レスポンス (登録済み通知と応答本文) へのメンバーの追加」の行と、表の下の注記で評価する | 破壊的     | 成功条件・レスポンスの解釈が変わる (DR-02、DR-15 決定 5)                         |
| 既存の HTTP ステータスコードの変更                                                                                                                                                                                                                                         | 破壊的     | 既存クライアントの分岐が変わる                                                   |
| 既存のエラー識別子 (`code`)、`type`、分類の変更または削除                                                                                                                                                                                                                  | 破壊的     | 既存クライアントの分岐が変わる (DR-01 決定 6)                                    |
| エラー識別子ごとの対処方針 (再試行可能性・再送安全性・結果の確定性) の変更                                                                                                                                                                                                 | 破壊的     | 既存クライアントに求める対処が変わる                                             |
| 再送時の保証の変更 (保持期間の短縮、同じ結果を返す範囲の縮小など)                                                                                                                                                                                                          | 破壊的     | 再送時の保証が変わる                                                             |
| 状態の追加、削除、意味の変更。状態遷移規則の変更                                                                                                                                                                                                                           | 破壊的     | 既存クライアントの状態の解釈が変わる                                             |
| 認証の外部仕様の変更 (資格情報の送信形式、認証失敗時の応答)                                                                                                                                                                                                                | 破壊的     | 既存クライアントに求める対処が変わる                                             |
| 複数のエラー条件が成立したときの外部応答の優先順位の変更                                                                                                                                                                                                                   | 破壊的     | 既存クライアントが観測する応答が変わる                                           |
| API メジャーバージョンの識別方法の変更                                                                                                                                                                                                                                     | 破壊的     | 既存クライアントの呼び出し先が変わる                                             |
| 新しいエラー識別子の追加。ただし、既存の成功条件・再送時の保証・既存クライアントに求める対処を変えない                                                                                                                                                                     | 非破壊的   | 既存クライアントに影響しない (DR-04 決定 8)                                      |
| 新しいエラー識別子の追加。ただし、これまで成功したリクエストを新しいエラーにする、または求める対処を変える                                                                                                                                                                 | 破壊的     | 既存の成功条件または求める対処が変わる (DR-04 決定 8、9)                         |
| 成功レスポンス (登録済み通知と応答本文) へのメンバーの追加。ただし、既存メンバーの型・意味・必須性と、既存クライアントに求める動作を変えない                                                                                                                               | 非破壊的   | クライアントは未知のメンバーを無視する (DR-15 決定 1・決定 2)                    |
| 成功レスポンスへのメンバーの追加に伴い、既存メンバーの型を非互換に変える、既存メンバーの意味を変える、または既存クライアントに新たな処理を求めるもの                                                                                                                       | 破壊的     | 既存クライアントの解釈または求める対処が変わる (DR-15 決定 3、DR-04 決定 9)      |
| 新しい操作 (エンドポイント) の追加                                                                                                                                                                                                                                         | 非破壊的   | 既存の操作に影響しない                                                           |
| 省略可能で、省略時の振る舞いを変えないリクエスト項目の追加                                                                                                                                                                                                                 | 非破壊的   | 既存のリクエストの結果が変わらない                                               |
| 検証制約の緩和 (上限の引き上げなど)                                                                                                                                                                                                                                        | 非破壊的   | これまで成功したリクエストが失敗しない                                           |
| 説明文、例の修正で、意味を変えないもの                                                                                                                                                                                                                                     | 明確化のみ | 観測できる振る舞いが変わらない                                                   |

成功レスポンスへのメンバーの追加が非破壊的の行の条件を満たさないことだけを理由に、その変更を破壊的とはしない。
破壊的の行にあたらない変更は、冒頭の判断の根拠 (DR-04 決定 8、9) に従って分類する。

既存メンバーの必須性の変更は、メンバーの追加として評価しない。一律に破壊的ともしない。
既存クライアントから観測できる振る舞いと、既存クライアントに求める対処への影響で、冒頭の判断の根拠 (DR-04 決定 8、9) に従って分類する (DR-15 決定 3)。

エラーレスポンスの拡張メンバーの追加に関する具体的な互換性条件は、`specifications-errors.md` R-ER-C-050 に従う。
本表では当該規範を再定義しない (DR-15 決定 4)。
`notification.not_cancellable` の応答への拡張メンバー `currentState` の追加 (DR-17) は、この条件 (R-ER-C-050) で評価した。

判断に迷う変更は、破壊的変更として評価する。非破壊的と判断する場合は、判断の根拠をレビューで確認する。

### 3.6 Deprecation and Migration (REQ-F-011)

破壊的変更を導入するとき、契約は既存クライアントへの影響を次のように管理しなければならない。

1. Change History への記録。破壊的変更の内容を、契約の Change History に記録する。
2. 非推奨の明示。旧 API メジャーバージョンの各操作を、OpenAPI の `deprecated` で非推奨と明示する。あわせて、非推奨であることを契約の説明に記す。
3. 移行手順の記述。旧バージョンから新バージョンへの移行手順を、契約に記述する。

Change History、非推奨の説明、移行手順の記述場所は、OpenAPI ドキュメントの `info.description` とする (DD-GV-06、既定値・レビュー対象)。

非推奨期間は次のとおりである (DD-GV-05、既定値・レビュー対象)。

- 非推奨を明示した契約を公開してから、少なくとも 1 回の MINOR リリース分は、旧 API メジャーバージョンと新バージョンを併存させる。
- 期間は暦時間ではなく、契約の版の単位で数える。

### 3.7 Compatibility Check (REQ-F-011)

互換性確認は、旧版と新版の契約を比較するレビューで行う (DD-GV-07、既定値・レビュー対象)。

- 3.5 の判断基準表の各項目に該当する差分がないことを確認する。
- 非破壊的と判断する変更では、旧版の例 (example) が新版のスキーマに引き続き適合することを確認する。
- 非破壊的と判断する変更では、旧版のエラーカタログの全識別子が新版に残り、`type`、HTTP ステータスコード、分類、対処方針が変わっていないことを確認する。

版間の比較は、現時点では自動検証の範囲に含めない。

### 3.8 Artifact Structure and Placement (REQ-C-002、REQ-C-004)

| -------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |

  - ファイル名に、常に無視される語 (`api-key` など) を含めない。

### 3.10 Local Validation Guarantee (REQ-F-012、REQ-NF-002)

| 違反の種類                                                             | 検出の対象                           |

## 4. Decision Rules

Sequential within each category, stable. 旧 R-GV-NNN は 4.4 の対応表のとおり廃止し、再利用しない。

本章は、規則を契約として確定すべき事項 (`R-GV-C-NNN`)、実装で保証すべき事項 (`R-GV-I-NNN`)、将来の拡張案 (`R-GV-X-NNN`。
規範ではない) に分類する。
分類の基準は `specifications-index.md` 4.1 による。

### 4.1 Evaluation Order

契約の変更は、次の順序で評価する。
Evaluation MUST follow this order:

| Rule ID    | Step | 分類 | Condition                                                                     | Outcome                                                                                                                                 |
| ---------- | ---: | ---- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| R-GV-C-001 |    1 | 契約 | 兄弟 issue が、インターフェースまたは外部から観測できる保証の変更を必要とする | 契約を先に更新する。実装の変更は、契約の変更と同じプルリクエストに含めるか、契約の変更がマージされた後に提出する (MUST)                 |
| R-GV-C-002 |    2 | 契約 | 契約と実装の記述が食い違う                                                    | 契約を正とする。実装を契約に合わせるか、契約を先に更新してから実装を変更する (MUST)                                                     |
