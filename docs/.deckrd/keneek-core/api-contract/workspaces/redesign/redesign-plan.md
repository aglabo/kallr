## 1. 目的と経緯

旧設計 (要件 v1.5.3、DR-01〜DR-18、仕様 4 文書) は、永続化とスケジューリングを持つ常駐サーバーを前提にしていた。
Keneek (将来は Kallr) の実態は、PWA・CLI などの入力を OS の通知 IF に渡すアダプターです。旧設計は過剰なため、新設計に移行します。

本書は設計チェーンに属さず、ID を採番しない。規範文書ではなく、設計移行の根拠と手順の記録です。
`workspaces/redesign/` に置き、git で追跡する。移行が完了した後は削除せず、完了済みの移行記録として残す。
PoC の手順は `poc-plan.md`、結果は `poc-results-windows.md`・`poc-results-android.md` (同じ場所) に置く。

## 2. 新設計の前提

### 2.1 確定

| 項目             | 決定                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------ |
| 時刻の監視と発火 | OS に任せる。Keneek は常駐スケジューラーや時刻の監視ループを作らない                                               |
| 共通の機構       | Windows と Android に共通するのは、アラームによる予約時刻の管理だけ。OS 固有の予約処理はアダプターで分ける         |
| 永続化           | Keneek は単純な永続ストアだけを持つ。保存するのは、バッチ ID・アラーム ID・発火時刻・タイトル・本文・URL・登録結果 |
| 再起動後の復旧   | 自動復旧は行わない。保存済みの予約データを、利用者の操作で一括して再登録する                                       |
| ID               | 2 層。バッチ ID (`batchId`) とアラーム ID (`alarmId`)                                                              |
| 契約の利用者     | PWA (REMINDER を含む) と CLI                                                                                       |
| 公開する状態     | 公開しない。保存する内部の管理情報は契約に出さない                                                                 |

### 2.2 実行形態 (方針。PoC で成立を確認する)

| 項目         | Windows                                                                                                          | Android                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 呼び出し元   | CLI と PWA。localhost の Web サーバーを呼ぶ                                                                      | PWA。Intent / App Links でアプリを起動する (CLI は対象外)                                   |
| 常駐         | サーバーの常駐は PWA を受けるなら必要 (Q9)                                                                       | 常駐しない。必要なときだけ起動し、処理が終われば止まる                                      |
| UI           | 不要                                                                                                             | Flutter。設定 UI と PWA からの操作の受付だけ                                                |
| 時刻管理     | `ScheduledToastNotification` (OS が予約を保持)。使えない場合の代替は Task Scheduler (Q6)                         | `AlarmManager` (OS がアラームを保持。内容は Keneek が持つ)                                  |
| 発火時の処理 | OS が通知を表示する。Keneek は不要                                                                               | `BroadcastReceiver` が起動し、通知内容を永続ストアから取得して `NotificationManager` に渡す |
| 実装言語     | Dart を第一候補とする。.NET は Windows の予約 API の成立条件の検証に使う (Q10)。Flutter のランナーは必須ではない | 通知処理は Kotlin、共通ロジックは Dart Core の見込み (Q11)                                  |

- 表の『OS が予約を保持』『OS がアラームを保持』は方針であり、W2・W7・A1 で確かめるまで事実として扱わない
- アラーム発火時に Flutter の UI を起動しない (Android 10 以降は、バックグラウンドからの Activity の起動に制限があるとされる。第 5 章で確認する)
- 共通ロジック (バッチ登録、ID 管理、永続化) は、HTTP サーバーから切り離した Dart Core とする案がある。PWA の Intent は Core を直接呼び、HTTP サーバーは必須にしない
- この分割は実装方式であり、契約には書かない。ただし、永続ストアを Kotlin と Dart の双方が読む場合、データモデルの共有が必要になる (Q11)

## 3. 新設計の契約の範囲 (v1 案)

契約は 2 層で書く。この分離は維持する。

- 操作とデータモデル (トランスポートに依存しない): 登録、キャンセル、一括再登録、各項目の意味、エラーの分類
- HTTP の対応づけ (OpenAPI): Windows の localhost サーバー。Android の対応づけは未定 (Q8)

| 操作       | 内容                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 登録       | バッチ ID の下に複数のアラームを登録する。要素ごとに成否を返す (部分成功を許す)                                                                  |
| キャンセル | バッチ ID またはアラーム ID を指定して予約を取り消す                                                                                             |
| 一括再登録 | 保存済みの予約データを OS へ再登録する。OS 再起動後に利用者が操作する。対象は全件、または `batchId` で絞る。失敗したアラームだけを対象にもできる |

- 取得・一覧は v1 に含めない。必要になった時点で、後方互換な追加として加える
- 失敗したアラームだけの再登録は v1 に含める。専用の retry API は作らず、一括再登録の対象の指定で表す
- `Idempotency-Key` は廃止する。同一 `batchId` と `alarmId` による登録は、既存の未発火予約の置換として扱う。
  過去に発火・表示された通知の取り消しと、再送結果の同一性は保証しない。冪等性の保証ではなく、置換の規則である。新 DR に明記する
- 維持する旧設計: RFC 9457 の共通エラー形式 (旧 DR-01)、エラーの分類と対処の分離 (旧 DR-04)、認証状態と内部情報を開示しない (旧 DR-10)、
  外部から観測できる保証だけを契約にする原則 (旧 DR-03)。いずれも新 DR として改めて採用する

## 4. 論点

### 4.1 決定済み

| #  | 論点                         | 決定                                                                                                                                                                                                            |
| -- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q1 | 部分成功                     | 許す。要素ごとの成否を返す。旧 DR-02 (all-or-nothing) を新 DR で置き換える                                                                                                                                      |
| Q2 | 過去の `fireAt`              | 再登録しない。結果は `skipped` (理由 `fire_at_elapsed`) とし、OS 登録の失敗 (`failed`) と区別する。時刻の比較は、各アラームを OS に渡す直前にも行う                                                             |
| Q3 | 一括再登録の対象             | 全件が既定。`batchId` で絞れる                                                                                                                                                                                  |
| Q4 | キャンセルの粒度             | バッチ単位とアラーム単位                                                                                                                                                                                        |
| Q5 | 永続ストアと OS 予約の不整合 | (a) 保存済みだが OS への登録が未完了、(b) OS には登録できたが結果の反映が未完了: 一括再登録で補正する。(c) キャンセル処理中の異常終了: 自動では解消しない。キャンセル済みのデータは再登録の対象から除外する     |
| Q7 | ID の名前空間                | 旧 ID は再利用しない。DR は DR-19 から、用語は UD-059 から (旧辞書に UD-056〜UD-058 が宣言済みのため)。要件・規則は未使用の名前空間を選び、使用前に `grep` で未使用を確認する (document-model の名前空間の規則) |

### 4.2 未決 (PoC の結果に依存するものを含む)

| #   | 論点                                                                                                                             | 推奨案 / 確認方法                                                                                                                                                                                                               |
| --- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q6  | Windows の予約通知が、採用する配布形式で使えるか。使えない場合の代替                                                             | PoC-W (必須ゲート)。代替の候補は Windows の Task Scheduler に通知コマンドを起動させる方式 (OS に時刻管理を委譲する原則は保てる)                                                                                                 |
| Q8  | Android で PWA が Keneek を呼ぶ経路と、結果 (要素ごとの成否の JSON) を PWA へ返す経路。Intent は HTTP と同等の通信手段ではない   | PoC-A4・A5 で比較。候補: (1) 起動後だけ一時的にローカル HTTP サーバーを立てる、(2) App Links で起動し結果を登録元 URL へ返す、(3) Web Share Target など                                                                         |
| Q9  | Windows のサーバーの起動方法。PWA が localhost を呼ぶには、サーバーが動いている必要がある                                        | ログオン時に常駐させる案を基本とする。CLI からの起動や、プロトコルハンドラーによる起動は PoC-W の後に検討                                                                                                                       |
| Q10 | Windows のサーバーの実装言語 (Dart、.NET、他)                                                                                    | Dart を第一候補とする。.NET で予約 API の成立条件を調べ、Dart の FFI から使えるかを PoC-W0 で確かめる                                                                                                                           |
| Q11 | Android の通知処理 (Receiver) を Kotlin だけで書くか、Dart Core を起動するか。永続ストアのスキーマを Kotlin と Dart で共有するか | PoC-A2・A3。Kotlin で短時間に SQLite を読み、通知を表示する方式を第一候補とする                                                                                                                                                 |
| Q12 | 呼び出し元の検証。任意のサイトが端末に通知を予約できないようにする方法                                                           | **必須ゲート**。許可した呼び出し元と、拒否すべき呼び出し元の両方を、PoC-A4・A5 と PoC-W6 で検証する。App Links はサイトとアプリの関連付けを検証するが、個々の登録要求を認可しない。#6 (ローカルセキュリティ) の範囲と整合させる |

## 5. 事実の確認 (契約に書く前)

主張の多くは、公式文書に基づくものとして伝えられたが、repo の調査メモ (`workspaces/os-notification-api-survey.md`) には予約に関する記述がない。
次を公式文書で確認し、結果をその調査メモに追記する。確認できなかった事項は「記載なし」とし、推測で補わない。

- Windows: `ToastNotifier.AddToSchedule`・`GetScheduledToastNotifications`・`RemoveFromSchedule`、Tag と Group による置き換え、
  WinRT を既定とするアプリに限る制約 (通常のデスクトップアプリは予約トーストを使えないとされる点を含む)、配信猶予 (5 分とされる主張は、確認したページに記載がなく未確認。仕様上の保証や制約には採用しない)、
  パッケージ化していないアプリの識別子 (AUMID)、Task Scheduler で通知コマンドを起動する方式
- Android: `AlarmManager` と `PendingIntent` による予約、`FLAG_UPDATE_CURRENT`、同一性の判定 (Intent の extras は使われない)、
  再起動によるアラームの消失、正確なアラームの権限、過去の時刻を指定したときの動作、
  バックグラウンドからの Activity の起動の制限、`BroadcastReceiver` の処理時間の制限 (`goAsync()` を含む)、
  Intent / App Links の PWA からの起動

推奨する PoC の実施順序:

1. 公式 API の調査結果を `os-notification-api-survey.md` に追記する (第 5 章)
2. Windows の PoC-W0 で実装方式を絞る
3. PoC-W と Android の PoC-A1・A2 を進める
4. Android の PWA 連携と、呼び出し元の検証 (Q12) を検証する
5. 判定ゲートを通過した後に、旧設計を退避する

### 7.1 判定ゲート

次の 5 条件をすべて満たしたとき、新アーキテクチャが成立したと判定し、旧設計の退避を許可する。

- [ ] Windows: 採用する配布形式で、PoC-W の W1〜W4 が成功し、W5 の制約 (アプリの識別子、インストール方式、実行権限) が記録されている。
      W4 では ID の Tag/Group への対応づけが制約内で成り立つ。W7 (再起動またはログオフの後の扱い) の結果が記録されている
- [ ] Android: A1・A2・A8 が成功している。A7 の正確なアラームの権限の扱いについて、採用する方針が決まっている
- [ ] Android: PWA 連携の起動 (A4a)・登録 (A4b)・応答 (A5) の三段階が、それぞれ独立して成立している。起動できただけで双方向の通信の成立とはみなさない。
      成立の条件に、呼び出し元の識別または要求ごとの認可 (A4c) を含む
- [ ] 呼び出し元の検証 (Q12): Windows は W6、Android は A4・A5 で、許可した呼び出し元は受理し、拒否すべき呼び出し元は拒否する。検証の手段がないという結果は、ゲートを通過しない
- [ ] Q6・Q8〜Q12 が『決定』として結果の文書に書かれている。新しい DR は設計チェーンの外 (`workspaces/`) を参照できないため、決定の内容を DR に再掲する

失敗した場合は、旧設計を退避する前に代替方針を決める。

- Windows で予約通知が使えない場合: Task Scheduler による方式 (タスクの起動 TS1 と、利用者へのトースト表示 TS2 を別々の合格条件にする)、またはアプリが時刻を保持する方式を検討する
- Android で結果を PWA に返せない場合: 操作の受理と結果の返却を分ける契約を検討する

## 8. 旧設計から引き継がないもの

状態の集合 (`scheduled`・`dispatched`・`missed`・`cancelled`) と状態遷移、読み取りの一貫性、`currentState`、開始確定の一意性、
冪等性のキー管理と回復、一覧・単体取得、兄弟 issue (#4・#5・#7) との照合記録 (G-01〜G-19)、互換性の判断基準表の大半。
必要になれば、新しい DR として個別に採用する。

## 9. リスク

- Windows の予約通知が使えない場合、「時刻の監視は OS」の前提が崩れる。PoC-W をゲートにし、代替の Task Scheduler も候補にする
- Android で PWA に結果を返す経路が成立しない場合、HTTP を前提にした契約の書き方が変わる。契約を 2 層にしておく (第 3 章)
- 呼び出し元の検証が不十分だと、任意のサイトが通知を予約できる。Q12 をゲートにする
- Android の `BroadcastReceiver` の処理時間と、バックグラウンドの起動制限。通知の表示だけの短時間処理に留め、Dart エンジンの起動は必要性を測ってから判断する
- 永続ストアの共有 (Kotlin と Dart) で、データモデルの食い違いが起きる。スキーマを 1 か所で定義する
- 部分成功の応答の形は複雑になり得る。要素ごとの成否と ID だけに絞る
