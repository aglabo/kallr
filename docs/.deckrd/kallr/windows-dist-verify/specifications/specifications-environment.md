## 1. 概要

### 1.1 目的

この文書は、通知可否の確認と AUMID の登録管理の振る舞いを定める。
あわせて、W5 の記録の完備条件と、記録と実態の整合チェックの振る舞いを定める。
対象の要件は REQ-F-002、REQ-F-010、REQ-F-011、REQ-F-021 の 4 件。

### 1.2 範囲

この仕様書は、Windows Distribution Verify (environment) の振る舞いの規則と分類の意味を定める。
実装の詳細は対象外とする。用語は `universal-dictionary.md` の定義に従う。

- 範囲内:
  - 通知可否の確認、AUMID の登録・削除・存在確認
  - add の事前確認、Windows 向けの確認の判定規則
  - W5 の記録の完備条件、W5 の整合チェック
  - 関連する CLI コマンド (register-reg / unregister-reg / w5-check / show)
- 範囲外:
  - 予約の追加・置換・取り消し (詳細は `specifications-schedule.md`)
  - Tag の生成 (詳細は `specifications-tag.md`)
  - 検証手順と結果の追記 (詳細は `specifications-verification.md`)

## 2. 設計方針

### 2.1 分類方針

通知可否の確認は、読み取りだけで「通知できる」か「通知できない」かを分類する。

- 「通知できない」は想定した状態であり、異常とせず値で返す。
- OS やレジストリの読み取りそのものの失敗は、「通知できない」と区別して失敗として扱う。
- 判定できない状態を「通知できる」に倒さない。未知の値は失敗とする。
- 確認は読み取り専用とする。確認のために登録を作ったり直したりしない。
- W5 の合否は、記録の完備だけで決める。
- 整合チェックの不一致は、記録の誤りとして報告する。W5 の不合格にはしない。
- 「記録が完備していること」と「記録が実態と一致すること」は別の事柄とする。
  前者は W5 の合否を決め、後者は w5-check が報告する。

### 2.2 設計上の前提

- 配布形式は未パッケージ + HKCU 登録とする (DR-01)。
- 登録に管理者権限は不要。これは過去の PoC 結果による。
- 集中モードとロック状態は、確認の対象に含まない (REQ-F-002)。
- PoC の未パッケージの実行では、通知設定は Enabled を返した。無効にしたときの値は未確認 (Section 7)。

過去の PoC (Windows 11 10.0.22621) では、次の 3 点を確認した。

- 登録なしで add は成功するが、通知は表示されない。
- HKCU に DisplayName を登録すれば、ショートカットなしで通知が表示される。
- 登録を削除した後も、通知設定は有効のまま返る。ただし通知は表示されない。

したがって、通知設定の値だけでは通知できるかを判定できない。
登録の存在と DisplayName の確認を併用する。

### 2.3 外部設計の概要

> **根拠**: 外部設計の対話 (Phase E) と、利用者が確認した設計方針 (Phase D) に基づく。

#### 機能の分割

#### 構成要素の関係

```text
+--------+     +-----------+     +----------------+
|  CLI   | --> | Pre-check | --> | Environment IF |
+--------+     +-----------+     +----------------+
    |                              ^            ^
    |                              |            |
    |                      +--------------+  +------+
    +--------------------> | Windows impl |  | Mock |
    |  (register-reg,      +--------------+  +------+
    |   unregister-reg,           |
    |   show, w5-check)           v
    |                      [HKCU registry]
    v                      [Notification setting]
+----------+

+----------+
```

- add の事前確認は、予約一覧と対応表を参照する前に実行する。確認が不可なら、後続の手順は実行しない。
- add の事前確認以外の CLI コマンドも、IF だけを使う。Windows 実装を直接呼ばない。

```text
[AUMID] --> [Registration lookup] --> [DisplayName check] --> [Setting check] --> [Availability]
                  |                         |                      |
                  v                         v                      v
          (not registered)          (DisplayName empty)     (disabled / unknown)
            stop, ok=false           stop, ok=false         ok=false / failure
```

## 3. 振る舞いの仕様

### 3.1 入力

- Input Type:
  - AUMID: アプリを識別する文字列
  - DisplayName: 通知に表示するアプリ名の文字列 (登録時のみ)
  - W5 の記録値: AUMID、インストール方式、実行権限の 3 項目 (w5-check では `--recorded-*` で受け取る)
- Assumptions:
  - AUMID は空でない。空の AUMID は使い方の誤りとする。
  - AUMID は OS に触れるすべてのコマンドで `--aumid` として必須で、既定値を持たない (ENV-DD-08)。
  - DisplayName は登録時に空でない。register-reg では `--display-name` で受け取る。
  - 空白だけの DisplayName は、空と同じに扱う (ENV-DD-07)。
  - 実行権限の値は `user` と `administrator` の 2 つとする (ENV-DD-12)。
  - AUMID と DisplayName は UTF-8 入力に対応する (REQ-NF-004)。非 ASCII 文字は登録の前後で変わらない。
  - 登録の場所は、現在のユーザーのレジストリ (HKCU) の AUMID 登録領域に限る。システム全体の領域には触れない。

<!-- impl-note: 登録先は HKCU\Software\Classes\AppUserModelId\<aumid>、値名は DisplayName。
     (CODEBASE CONTEXT: w03.dart の register-reg と同じ場所) -->

### 3.2 出力と終了コード

通知可否の確認は、次の 5 項目を持つ結果を返す。

| 項目                                | 内容                                                                                                                                                 |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 登録の有無 (registered)             | HKCU に AUMID の登録があるか                                                                                                                         |
| DisplayName の有無 (displayNameSet) | 空でない値があるとき真                                                                                                                               |
| 通知設定 (setting)                  | 有効、またはアプリ単位・ユーザー設定・グループポリシー・マニフェストのいずれかによる無効。確認を途中で打ち切ったときは「未評価」(値なし) (ENV-DD-10) |
| 通知できるか (ok)                   | 登録あり、DisplayName あり、かつ通知設定が有効のときだけ真                                                                                           |
| 理由 (reason)                       | ok が偽のとき、通知できない理由を示す                                                                                                                |

取りうる結果は次の 7 つ。

- 通知できる (ok=真)
- 通知できない: 未登録
- 通知できない: DisplayName が空
- 通知できない: 通知設定が無効 (4 種の無効のいずれか)
- 失敗: レジストリまたは OS の読み取りの失敗 (原因のコードを保つ)
- 失敗: 通知設定が未知の値
- 使い方の誤り: AUMID が空

     ENV-DD-03 / ENV-DD-10 により、打ち切った場合の setting は値なし (null 許容) とする。 -->

### 3.3 インターフェースの操作 (REQ-F-021)

OS 非依存の通知環境 IF は、次の 4 操作を持つ。

| Operation  | Meaning                                                                    | Write |
| ---------- | -------------------------------------------------------------------------- | ----- |
| 確認       | AUMID を受け取り、Section 3.2 の結果を返す。「不可」は値で返す             | なし  |
| 登録       | AUMID と DisplayName を受け取り、登録を作る。既存なら DisplayName を上書く | あり  |
| 削除       | AUMID の登録を削除する                                                     | あり  |
| 登録の確認 | AUMID の登録が存在するかを真偽で返す。DisplayName の有無は問わない         | なし  |

- Kallr の本体 (add / cancel など) は、この IF だけを使う。レジストリと OS の API を直接呼ばない。
- IF は Mock に差し替えられる。Mock を使うと、add の成否は Mock の戻り値に従い、レジストリと OS の API は呼ばれない (AC-013)。
- Mock は、通知できる状態、未登録、DisplayName が空、4 種の無効のそれぞれを返せる。これにより add の判断を自動テストで確認できる。

### 3.4 Windows での実装方針 (REQ-F-021)

Windows 実装は、2 つの観測で確認する。

- HKCU の登録: AUMID の登録の存在と DisplayName の値
- 通知設定: その AUMID の通知の送信元が返す、通知の有効・無効

登録・削除・登録の確認・確認の読み取りは、FFI でレジストリを操作して実現する。外部コマンドの出力に頼らない。
レジストリの操作が失敗したときは、OS が返したエラーコードを保った失敗として扱う。

<!-- impl-note: advapi32 の RegOpenKeyExW / RegQueryValueExW / RegCreateKeyExW / RegSetValueExW /
     RegDeleteKeyW / RegCloseKey を FFI で呼ぶ。通知設定は ToastNotifier.Setting (仮想関数テーブル 8, get_Setting)。
     w03.dart の登録は reg.exe 経由で、読み取り・存在確認の実装はまだない (CODEBASE CONTEXT)。
     失敗は RegistryException(Win32 error code)。 -->

### 3.5 CLI コマンド (本仕様書の対象)

| Command        | Required options            | Behavior                                                                                                            | Exit code                                                                         |
| -------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| register-reg   | `--aumid`, `--display-name` | IF の登録を呼ぶ。事前確認はしない                                                                                   | 0 成功 / 1 使い方の誤り (欠落、空白だけの値) / 2 レジストリの失敗                 |
| unregister-reg | `--aumid`                   | IF の削除を呼ぶ                                                                                                     | 0 成功 / 1 使い方の誤り / 2 レジストリの失敗、または登録が無い (見つからない)     |
| show           | `--aumid`                   | IF の確認の結果 (Section 3.2 の 5 項目) を表示する。何も書き込まない                                                | 0 ok=真 / 1 使い方の誤り / 2 読み取りの失敗 / 3 ok=偽 (通知できない状態)          |
| w5-check       | `--aumid`                   | ENV-R-015 の整合チェックを実行し、項目ごとの結果を報告する。`--recorded-*` で記録した値を受け取る。何も書き込まない | 0 すべて完備かつ一致 / 1 使い方の誤り / 2 失敗、不一致、または未明確 (記録の誤り) |

終了コードの体系は次のとおり。

- 0: 成功
- 1: 使い方の誤り
- 2: 失敗 (OS・DB)
- 3: 通知できない (AUMID の未登録、DisplayName が空、通知設定が無効)

規則は次のとおり。

- 終了コード 3 を返すのは、通知可否の確認の結果が不可のときだけ。
  add の事前確認 (ENV-R-008)、show (ENV-R-018)、re-register-all の最初の確認 (`specifications-schedule.md`) がこれに当たる。
- 終了コード 3 の意味は環境の確認の結果に限り、通知が実際に表示されるかの確認は含まない。
- OS に触れるコマンドの `--aumid` は必須で、欠落は使い方の誤り (終了コード 1) とする (ENV-R-017)。
- 例外から終了コードへの変換は、CLI の入口の 1 か所で行う。

     RegistryException(win32 error code), ArgumentError。 -->

### 4.1 通知可否の確認の評価順

Evaluation MUST follow this order:
